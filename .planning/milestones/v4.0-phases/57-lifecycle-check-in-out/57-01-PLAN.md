<planning_decisions>
## Discretion points resolved here (CONTEXT.md "Claude's Discretion")

**PD-01 — Assignment fields are a polymorphic pair, not one per target type.**
The asset carries `assignedToType` (`"user"` | `"location"`) plus `assignedToId`. RESEARCH.md
Open Question 1 recommended a single new `assignedToUserId` field with `locationId` doing double
duty for location checkouts. That is rejected here because it makes a location checkout
indistinguishable from a catalogued home location (both would show only a `locationId`), and it
forces check-in to branch on which of two fields is populated. The polymorphic pair gives
check-in one uniform clear and gives Phase 61 one field pair to render. D-02 is still honored
exactly: a location checkout **also** overwrites `locationId`, because `locationId` means "where
the asset currently is."

**PD-02 — The overdue-audit report route is multi-segment.**
RESEARCH.md proposed `GET /api/assets/overdue-audit`. That is a single-segment sibling of
`asset_endpoints.py`'s `GET /api/assets/{asset_id}` (line 158) and would resolve correctly only
because the ITAM routers happen to register first — the exact stale-ordering fragility
RESEARCH.md Pitfall 4 warns about. The route is therefore `GET /api/assets/reports/overdue-audit`
(57-03), which cannot be captured by `{asset_id}` or by `{asset_id}/metrics` under any
registration order.

**PD-03 — `return_document=ReturnDocument.AFTER` on both guarded transitions.**
The handler returns the asset's new state to the caller, so AFTER is the useful projection. The
guard semantics are identical either way: a `None` return means the filter did not match.

**PD-04 — History entries store references, never denormalized personal data.**
An entry records `targetId` (and `targetType`) plus `actorUsername`, never the target user's
email, display name, department, or any other copied attribute. The collection is append-only,
so anything copied into it is copied permanently.
</planning_decisions>

| 1 | ITAM-LIFE-02 | unclassified | Checkout is a dedicated action endpoint, never a general-purpose asset PATCH. A **missing** `lifecycleStatus` key (every pre-existing agent-discovered asset) counts as `deployable`, so agent assets are checkoutable. | 2 | ITAM-LIFE-03 | unclassified | Check-in is gated on `lifecycleStatus == "deployed"` and returns 409 otherwise, so an `archived`/`retired`/`disposed`/`broken` asset is never silently resurrected into stock by a stray check-in. | 3 | ITAM-LIFE-04 | adjacency | Two history entries carrying an identical `ts` both persist as separate documents. Entries are never merged, deduplicated, or collapsed on equal timestamps — a same-millisecond check-in and check-out are two hand-offs and read back as two rows. **+truth** | 57-02 |
| 4 | ITAM-LIFE-04 | empty | An asset with no history reads as HTTP 200 with an empty list, never 404 and never a null body. | 5 | ITAM-LIFE-04 | ordering | History is returned newest-first under a deterministic **total** order: the sort is `ts` descending with `_id` descending as the tiebreak, so entries with an identical `ts` come back in a stable, repeatable sequence rather than in whatever order the storage engine happens to yield. **+truth** | 57-02 |
| 6 | ITAM-LIFE-05 | unclassified | "Overdue" is `lastAuditedAt` strictly older than now minus 365 days (D-03's fixed 12 months); an asset audited exactly at the cutoff instant is **not** yet overdue. An asset never audited falls back to `createdAt`. An asset with **neither** — every agent-discovered asset, which the heartbeat upsert never gives a `createdAt` — is included and labelled `ageBasis: "unknown"` with a null `daysOverdue`, never silently omitted from the population and never presented as a precisely-aged overdue row. **+truth** | 57-03 |
