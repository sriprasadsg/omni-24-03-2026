## Frontend wiring (ROADMAP "UI hint: yes")

User-management UI already exists and is wired — audited, do not rebuild:

| Component | Lines | Role |
|-----------|-------|------|
| `components/SettingsUsersTab.tsx` | 130 | users table, search, edit/delete/reset-password buttons (presentational, props from `SettingsDashboard.tsx`) |
| `components/AddUserModal.tsx` | 92 | create-user form |
| `components/EditUserModal.tsx` | 83 | edit-user form |

Backed by `services/apiService.ts`:
- `fetchUsers()` → `GET /users`
- `addUser()` → `POST /users` with `{email, password, full_name, role, tenantId}` — **already sends `tenantId` and `role`**, which is exactly what Task 1 items 1-2 are adding server-side. The UI is ahead of the backend here; Task 1 closes the gap rather than requiring UI changes.
- `updateUser()` → `PUT /users/{id}` with `{full_name, role, password}`
- `deleteUser()` → `DELETE /users/{id}`

**Two known frontend gaps, both explicitly out of scope for this plan:**
1. `resetPassword()` in `services/apiService.ts` is a stub (`return true`) — the reset-password button in `SettingsUsersTab` does nothing. Fixing it needs a backend reset endpoint plus a UI flow for delivering the new credential; that is its own slice, not part of ITAM-USR-01 CRUD.
2. `addUser()` / `updateUser()` / `deleteUser()` each silently fall back to mutating a local `USERS` array when the backend call fails, so the UI can show success for a write that never persisted. Removing those mock fallbacks is a frontend-service change owned by Phase 70 (which owns `services/apiService.ts` across all four of its plans).

Both are recorded here so the executor does not "discover" them and expand scope; note them in the SUMMARY as follow-ups.
