<task type="auto" tdd="true">
  <name>Task 3: Make TokenData and rbac_service scope-aware</name>
  <files>
    backend/auth_types.py
    backend/rbac_service.py
    backend/tests/test_api_key.py
  </files>
  <behavior>
    - Test 1: TokenData() constructed with no arguments has scopes None and auth_source "session" — every existing caller that builds TokenData positionally or by keyword keeps working unchanged.
    - Test 2: has_permission("view:itam") admits a TokenData with auth_source "api_key" whose scopes contain "view:itam" and whose role grants "view:itam".
    - Test 3: has_permission("manage:itam") raises HTTPException 403 for a TokenData with auth_source "api_key" whose role grants "manage:itam" but whose scopes are ["view:itam"] — the key's scopes narrow the role, they never widen it.
    - Test 4: has_permission("manage:itam") raises HTTPException 403 for an api_key TokenData whose scopes contain "manage:itam" but whose role does NOT grant it — a key cannot grant its owner a permission the owner lacks.
    - Test 5: a super_admin whose role resolves to the "*" wildcard is still restricted by an api_key TokenData's scopes; a session TokenData for the same user is not.
    - Test 6: a TokenData with auth_source "session" (scopes None) behaves exactly as it does today for both has_permission and require_role — no regression in the existing permission matrix.
    - Test 7: require_role(["admin"]) raises HTTPException 403 for an api_key TokenData with role "admin" whose scopes lack the "admin:itam" scope, and admits it when the scope is present.
    - Test 8: a key whose scopes list is empty is denied every permission check.
  </behavior>
  <action>
    Close the scope-enforcement gap this plan's must_haves depend on. Today backend/auth_types.py TokenData has only username, role, tenant_id, mfa_verified, and backend/rbac_service.py resolves permissions purely from role — so a scoped key currently inherits its owner's full role.

    1. In backend/auth_types.py, extend the TokenData dataclass with two new optional fields appended AFTER the existing ones so positional construction at every current call site is unaffected:
       - scopes: Optional[List[str]] = None  (None means "not scope-restricted"; a list means the request is narrowed to exactly those scopes)
       - auth_source: str = "session"  (set to "api_key" by api_key_auth.validate_key)
       Import List from typing alongside the existing Optional/Dict/Any import.
       Do NOT give scopes a mutable default; use None, and treat None and a populated list as semantically distinct (None = unrestricted, [] = nothing permitted).

    2. In backend/rbac_service.py, add a private helper on RBACService, `_scopes_allow(user, required_permission) -> bool`, that returns True when user.scopes is None, otherwise returns True only when required_permission is present in user.scopes or user.scopes contains the wildcard "*".

    3. Rewrite the inner dependency of has_permission() so scope narrowing is applied as an intersection with role permissions, in this order:
       a. resolve role permissions via the existing get_user_permissions(user)
       b. if the role check fails (required_permission absent and no "*" in permissions), raise the existing 403 with the existing detail message — role remains the outer bound
       c. then, if _scopes_allow(user, required_permission) is False, raise HTTPException 403 with detail f"API key scope does not permit: {required_permission}"
       The wildcard "*" from get_user_permissions must be evaluated BEFORE the scope check so a super_admin key is still narrowed by its scopes (behavior test 5).

    4. Apply the same narrowing to require_role(): after the existing role/super_admin logic admits the user, and only when user.auth_source is "api_key", require that the token scopes include the admin-equivalent scope for the allowed roles. Map roles to their gating scope with a module-level dict (admin/Tenant Admin/super_admin -> "admin:itam"; itam_admin -> "admin:itam"; everything else -> no additional scope requirement). Raise 403 with a scope-specific detail when the scope is absent.

    5. Wire backend/api_key_auth.py validate_key to populate both new fields on the TokenData it returns (scopes from the key record, auth_source "api_key"). Session/JWT construction in authentication_service.py is left untouched — it inherits the defaults.

    6. Add the behavior tests above to backend/tests/test_api_key.py under a TestScopeEnforcement class.

    Constraint: do not change the signature or return type of get_user_permissions() — 64-02 extends the same file in wave 1 and other ITAM endpoints call it.
  </action>
