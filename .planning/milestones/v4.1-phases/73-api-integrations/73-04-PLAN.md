<objective>
Generalise the existing remediation-to-ticketing bridge so ITAM events can create Jira issues and ServiceNow incidents, and expose the manual half of D-10 as a real endpoint.

This implements D-09 (a new ITAM-event alert-shape adapter alongside the existing `_task_to_alert_shape`, with `create_jira_ticket`, `create_servicenow_incident` and the close-loop status polling reused unmodified), the manual "Create Ticket" half of D-10, and D-11 (reuse the tenant's existing connection config, no new settings surface). Per Claude's Discretion the adapter lives in `ticketing_bridge.py` itself rather than a sibling module — it sits directly beside the adapter it mirrors, and `ticketing_bridge.py` is small enough to absorb it without approaching this project's file-size limit.

Explicitly NOT in scope: D-12's CMDB-style asset synchronisation into Jira issues or ServiceNow configuration items. This plan builds the ticket-per-event path only.

Purpose: plan 73-05's two automatic triggers and plan 73-06's row action both call into what this plan builds, so the adapter and its persistence contract must be settled and tested before either.
Output: the ITAM alert-shape adapter, an entity-aware ticket-creation orchestrator with a dedup guard, additive ticket fields on the asset-request model, and a registered manual create-ticket route.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ITAM console / API client → `POST /api/itam/tickets` | Untrusted entity kind, entity id and provider selection cross into code that performs an authenticated outbound call on the tenant's behalf |
| backend → Jira REST API / ServiceNow Table API | Tenant business data and tenant-held credentials cross to a third party |
| `ticketing_configs` document → connector call | Long-lived third-party credentials are read out of storage into an outbound request |
