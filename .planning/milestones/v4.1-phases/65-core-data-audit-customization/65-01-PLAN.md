<objective>
Deliver ITAM-DAT-01 (Custom Fields Engine) as a working, user-reachable surface: an ITAM admin can view, add, edit, and remove the custom-field definitions attached to an asset Model, from inside the existing ITAM console.

Purpose: the validation half of this engine already exists and is already wired (`itam_catalog_service.validate_fieldsets` is called by the catalog create/update path; `validate_custom_field_values` is called by the manual-asset create path). What does not exist is any way for a human to *author* those definitions — today a fieldset can only be set by hand-crafting a PATCH body. This plan closes that gap and adds the one missing read route (flattened field definitions + per-key usage counts) that plan 65-03's CSV column mapping also consumes.

Output: one new backend read route, two new pure functions in the existing catalog service, a new `CustomFieldsManager.tsx` panel reachable from the Catalog tab's Models view, two new API client functions, and backend + frontend test files.

Non-goal (deliberate, per 65-RESEARCH.md's Anti-Patterns and `itam_catalog_service.py`'s own module docstring): this plan does NOT introduce a `custom_field_definitions` collection or any cross-model field registry. Fieldsets stay embedded on the `asset_models` document, which is the MVP boundary Phase 56 chose on purpose.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api/itam/catalog/*` | Authenticated but untrusted JSON: fieldset definitions authored by a console user cross into server-side storage and become the validation contract for every future asset write. |
| ITAM console user → tenant data | An authenticated user of tenant A must never read or mutate tenant B's asset models or asset counts. |
| stored fieldset definition → asset write path | Definitions written here are later consumed by `validate_custom_field_values` on the manual-asset create path (and, from plan 65-03, on the CSV import path). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-65-01-01 | Tampering | `PATCH /api/itam/catalog/models/{id}` fieldset body | medium | mitigate | Every write continues to pass through `_validate_asset_model_references` → `itam_catalog_service.validate_fieldsets`. Task 2 explicitly forbids a client-side copy of that validation, so there is exactly one enforcement point and it is server-side. |
| T-65-01-02 | Elevation of Privilege | new `GET /models/{model_id}/fields` route | high | mitigate | Route declares `Depends(_require_itam_admin)` — the same `manage:assets` gate the rest of `itam_catalog_endpoints.py` uses. No new role-string set is introduced (65-RESEARCH.md Pitfall 4). |
| T-65-01-03 | Information Disclosure | model lookup + `usageCounts` asset counting | high | mitigate | Both the `asset_models.find_one` and every `assets.count_documents` go through the tenant-isolated `get_database()` wrapper, which injects `tenantId`; the raw `db._db` handle is never used in this plan. A cross-tenant `model_id` therefore 404s rather than leaking definitions or counts. |
| T-65-01-04 | Denial of Service | `usageCounts` fan-out (one count query per declared key) | low | mitigate | Key count is capped at 50 per request with a `usageCountsTruncated` flag; the whole block is wrapped in a logged `try/except` so a slow or failing count degrades to `{}` instead of hanging the definitions read. |
| T-65-01-05 | Repudiation | catalog model edits made through the new manager | medium | transfer | Audit logging for catalog writes is delivered by plan 65-02 (D-02), which backfills `log_itam_action` into `itam_catalog_endpoints.py`'s create/update/delete routes. This plan deliberately adds no second audit path. |
| T-65-SC | Tampering | npm/pip package installs | high | accept | This plan installs no packages. The phase as a whole introduces no new backend dependency, and 65-RESEARCH.md's `[SUS]`-flagged `react-i18next` is not installed anywhere in this phase — plan 65-04 uses a hand-rolled locale context instead, so the flagged package never enters the tree. No legitimacy checkpoint is required. |
