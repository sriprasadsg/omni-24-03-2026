<objective>
Deliver ITAM-SET-01 (Global Settings UI), ITAM-SET-02 (Branding/Theming) and ITAM-SET-03 (Localization) as one coherent, ITAM-console-scoped settings surface.

Purpose: the ITAM console has six-to-eight tabs of operational surface and no place to configure any of it. This plan adds that place, persists it with the same `system_settings` pattern the rest of the platform uses, applies the branding to the console so the setting is observably real, and adds a working language switch for the console's own labels.

Output: two new backend modules, router registration, a new Settings tab with `SettingsPanel.tsx`, a small hand-rolled locale provider, and backend + frontend tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/itam/settings` | Untrusted values that will later be interpolated into the console's own markup (a logo URL into an `img src`, a colour into a style attribute) cross into persistent storage. |
| tenant A → tenant B's settings document | One `system_settings` collection holds every tenant's document plus a global-fallback document with no `tenantId` field at all. |
| non-admin console user → settings write | The ITAM console is reachable by more roles than should be able to reconfigure it. |
