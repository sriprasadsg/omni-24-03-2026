## Frontend wiring (ROADMAP "UI hint: yes")

Role-management UI exists but is **only half-wired** — audited:

| Component | Lines | State |
|-----------|-------|-------|
| `components/SettingsRolesTab.tsx` | 67 | renders roles list (props from `SettingsDashboard.tsx`) |
| `components/RoleEditorModal.tsx` | 229 | full permission-matrix editor |

`services/apiService.ts` `fetchRoles()` does read the backend (`GET /roles`), but `saveRole()` is a **pure in-memory mock** — it mutates a module-level `ROLES` array and returns, with no HTTP call. So an admin can edit a role's permissions in `RoleEditorModal`, see it "save", and have the change vanish on reload.

**Deliberately deferred, not overlooked.** This plan is backend-only for three reasons:
1. Item 3 of Task 1 (`get_user_permissions(role) -> list[str]`) is precisely the read-side contract `RoleEditorModal` needs to render an accurate matrix — shipping it is the prerequisite for wiring, and the wiring can then be done without further backend work.
2. Persisting role edits needs a role-write endpoint with its own authorization story (who may grant which permission), which is adjacent to but distinct from ITAM-USR-02's "RBAC enforcement" requirement.
3. `services/apiService.ts` is owned end-to-end by Phase 65's plans; a competing edit here would collide.

Record in the SUMMARY that `saveRole()` remains a mock so it is not mistaken for working persistence during UAT of this phase.
</frontend_scope>
