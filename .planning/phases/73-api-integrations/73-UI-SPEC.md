# Phase 73 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Per 73-CONTEXT.md and 73-RESEARCH.md, this phase is almost entirely backend wiring (API-key auth swap, inline webhook dispatch, a new ticketing-bridge adapter). The **entire** frontend surface is three small additions to two already-styled, already-shipped ITAM console panels, plus a one-line data addition to an unrelated existing dashboard — there is no new page, route, nav entry, or ITAM Console tab:

1. **`components/WebhookManagement.tsx`** — extend the existing `availableEvents: WebhookEvent[]` array with the 8 new ITAM event-type strings from D-05 (ITAM-API-02 / D-14). Pure data change; the array is already rendered by fully-built, unmodified markup (checkbox list, `font-mono` labels) — no new component, no new styling.
2. **`components/itam/LifecyclePanel.tsx`** — add a manual "Create Ticket" row action to the assets table's existing trailing action cell (ITAM-API-03 / D-10), plus a compact ticket-reference display once a ticket exists (from either the manual action or D-10's automatic `asset.audit_overdue` trigger).
3. **`components/itam/RequestsPanel.tsx`** — the identical manual "Create Ticket" row action + ticket-reference display added to the asset-requests table's trailing action cell (covers both the manual case and D-10's automatic "stuck pending approval" trigger).

No shadcn, no new icon library, no new color system — this contract is 100% reuse of patterns already live in the exact three files being touched (and one directly-adjacent file, `RemediationTaskModal.tsx`/`43-UI-SPEC.md`, for the one genuinely new interaction — a provider-choice affordance — that has a direct in-codebase precedent).

## Spacing Scale

Declared values (must be multiples of 4) — all sourced from `LifecyclePanel.tsx`/`RequestsPanel.tsx`, the exact files this phase edits; no new values introduced off the 4-point grid:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gap inside the ticket-reference display (`gap-1`, matches `ClockIcon`/timestamp pairing convention elsewhere in the console); vertical padding on the **new** ticket-provider badge (`py-1`, see below) |
| sm | 8px | Dropdown menu item padding (`px-3 py-2` rounds to this scale contribution); badge horizontal padding (`px-2`); gap between the **new** "Create Ticket" text link and its adjacent sibling row action (`ml-2`, see below) |
| md | 16px | Inherited unchanged — table cell/card padding (`p-4`), not touched by this phase |
| lg | 24px | Inherited unchanged — page container padding (`p-6`), not touched by this phase |

Legacy values (pre-existing, unchanged, untouched by this phase — **not** used by this phase's new elements):
- `mr-3`/`ml-3` (12px) — the existing gap between the three pre-existing row-action text links (`Check In`/`Check Out`, `Mark Audited`, `Label`). This phase does not carry this value forward: the **new** "Create Ticket" link uses `ml-2` (8px), staying on the 4-point grid, for its gap from the adjacent legacy action. This makes the gap before "Create Ticket" marginally tighter than the gaps between the three legacy actions — an accepted, deliberate trade-off, since this is new markup this phase authors, not an edit to alignment-critical legacy code.
- `py-0.5` (2px) — the existing badge/status-pill vertical padding (`STATUS_COLORS`/`STATUS_STYLES` pattern, `px-2 py-0.5`), unchanged and untouched by this phase. The **new** ticket-provider badge does not reuse this value: it uses `py-1` (4px) instead, staying on the 4-point grid (color/border/opacity formula is still cloned verbatim from `STATUS_COLORS` — only the vertical padding differs). This makes the new badge marginally taller than the pre-existing status pills in the same row — an accepted, deliberate trade-off for the same reason.

## Color

No new dominant/secondary background is introduced — this phase adds row-level affordances inside already-styled, already-shipped tables. Values below are 100% reuse of the existing dark ITAM console palette (`72-UI-SPEC.md`'s declared system).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#111827` (`bg-gray-900`) | Inherited unchanged — console page background |
| Secondary (30%) | `#1f2937` (`bg-gray-800`) with `#374151` (`border-gray-700`) | Inherited unchanged — table container background; also the new provider-choice dropdown menu background (clones `LifecyclePanel.tsx`'s existing Label dropdown: `bg-gray-800 border border-gray-700 rounded-lg shadow-xl`) |
| Accent (10%) | `cyan-600`/`cyan-500` (tenant-brandable per `72-UI-SPEC.md`) | **Not used by this phase's new UI at all.** The existing "Add Asset"/"New Request" top-of-panel CTAs keep their accent color unchanged; the new "Create Ticket" row action is deliberately **not** accent-colored (see below) — this phase does not expand the accent-reserved list. |
| Destructive | `#dc2626` (`text-red-400`) | Reused verbatim, unchanged — the "Failed to create ticket" error toast text only (via the existing `showToast(..., 'error')` convention). No new destructive action: ticket creation is additive and non-blocking, identical to `43-UI-SPEC.md`'s D-04 reasoning — no delete/unlink-ticket action exists in this phase's scope. |

**"Create Ticket" row-action color:** `text-gray-400 hover:text-gray-200` — the same neutral/secondary color already used for the structurally closest sibling actions in the same cell, `Mark Audited` and `Label` (both are secondary, non-primary row actions in `LifecyclePanel.tsx`). Explicitly **not** cyan (accent is reserved for the panel's one primary CTA per row-group, "Add Asset"/"New Request", never a per-row secondary action) and not green/amber/red (those are reserved by `STATUS_COLORS`/`STATUS_STYLES` for lifecycle/approval status semantics in the same row — reusing them for an unrelated action would visually conflict with the status pill already present in every row).

**Ticket-provider badge** (shown only once a ticket exists, replacing the "Create Ticket" text link — a third semantic pair, distinct from the existing green/amber/red status vocabulary already occupying this row, to avoid ambiguity between "request status" and "ticket provider"):

| Provider | Value |
|----------|-------|
| Jira | `text-blue-400 bg-blue-900/20 border-blue-800` |
| ServiceNow | `text-violet-400 bg-violet-900/20 border-violet-800` |

Both follow the exact `/20`-opacity-background + `-800`-border color formula already established by `STATUS_COLORS`/`STATUS_STYLES` (`72-UI-SPEC.md`'s declared badge system) — blue and violet are chosen specifically because neither collides with the green (`deployable`/`approved`)/amber (`deployed`/`pending`)/red (`broken`/`rejected`)/gray (`archived` etc.) status colors already present in the same row, and violet does not collide with the reserved cyan accent. Padding is the one attribute **not** cloned verbatim: per the Spacing Scale section, this badge uses `px-2 py-1` (4-point-grid vertical padding) rather than the legacy `px-2 py-0.5`.

Accent reserved for: the pre-existing "Add Asset" and "New Request" primary buttons only — unchanged, not expanded by this phase.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Row action (no ticket yet, provider auto-resolved or single provider configured) | `Create Ticket` (text link; `Creating…` + disabled while in flight — clone the existing `actioningId`/disabled-during-action pattern already used by `RequestsPanel.tsx`'s `handleApprove`/`handleReject`) |
| Row action, both Jira + ServiceNow configured | `Create Ticket` opens a small inline dropdown (clone `LifecyclePanel.tsx`'s existing Label-menu pattern verbatim) with two items: `Jira` / `ServiceNow` — selecting one fires ticket creation for that provider immediately, no separate confirm step |
| Neither Jira nor ServiceNow configured for the tenant | The "Create Ticket" action is **hidden entirely** — no button, no disabled state, no explanatory copy. Mirrors `43-UI-SPEC.md`'s identical rule for the same underlying feature: ticketing is opt-in tenant configuration (`TicketingIntegration.tsx`), and a tenant that hasn't configured either provider should not see a dead-end row action repeated on every asset/request row. |
| Ticket already exists (`ticket_ref` truthy — from either the manual action or an automatic D-10 trigger) | The "Create Ticket" text link is replaced by the ticket-reference display: `{ProviderBadge} {ticket_ref}` with an inline `↗` link (`ExternalLinkIcon` at `size={12}`, `target="_blank" rel="noopener noreferrer"`) to the provider's ticket page. No "create another ticket" affordance — one ticket per asset/request in v1, matching `43-UI-SPEC.md`'s identical locked rule. |
| Success toast | `Ticket created.` (exact reuse of `43-UI-SPEC.md`'s established copy, and this codebase's terse past-tense toast convention: `"Asset request approved."`, `"Comment posted."`) |
| Error toast | `Failed to create ticket — please try again.` (exact reuse of `43-UI-SPEC.md`'s established copy) |
| Automatic triggers (`asset.audit_overdue`, stuck-approval) | **No UI moment.** Both fire silently from the new background sweep (RESEARCH.md Pitfall 6). The only visible effect is the same ticket-reference display above appearing the next time the asset/request row is rendered — do not add a toast, banner, or any other signal specifically for an automatically-created ticket. Mirrors `43-UI-SPEC.md`'s identical rule for its own auto-create trigger. |
| Destructive confirmation | Not applicable — no destructive action exists in this phase's UI surface (ticket creation is additive/non-blocking; no delete-ticket action in scope). |
| Webhook event picker (D-14) | No new copy — the 8 new event-type strings render through the existing unmodified checkbox-list markup (`font-mono text-sm`) exactly like the 8 existing entries. Exact strings to add to `availableEvents`, verbatim (must match D-05's dot-namespaced casing precisely, since these are literal `event_type` values matched by webhook subscriptions, not display labels): `asset.checked_out`, `asset.checked_in`, `asset.warranty_expiring`, `license.expiring_soon`, `asset.request_approved`, `asset.request_denied`, `consumable.low_stock`, `asset.audit_overdue`. |

## UI Considerations

Manually resolved against this phase's 3 touched surfaces (E1 asset-row ticket action, E2 request-row ticket action, E3 webhook event-picker array). Given the narrow, almost entirely backend scope, the probe was applied selectively to only the state categories that are actually reachable for each element — categories with no reachable variant (e.g. "long-text" on a fixed 8-entry array) are marked not applicable rather than run through the full matrix.

Applicable state considerations resolved: 15 covered, 2 backstop, 7 not applicable, 0 unresolved.

**Visual hierarchy among the three new elements:** the ticket-provider badge/link (E1/E2, populated state) is the primary visual anchor once a ticket exists — it carries color (blue/violet) and sits where the eye already lands to check row status. The plain-text "Create Ticket" action (E1/E2, empty state) is intentionally low-emphasis (`text-gray-400`, no accent color) so it does not compete with the colored status pill already present in every row. The webhook event-picker additions (E3) introduce no new visual weight at all — they extend an existing `font-mono` checkbox list with zero styling changes.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | E1/E2 (no ticket yet) | ✅ covered | Default/base state — "Create Ticket" text link renders; no special empty-state copy needed, it's the row's normal resting state. |
| loading | E1/E2 (create in flight) | ✅ covered | `Creating…` + disabled, cloning `RequestsPanel.tsx`'s existing `actioningId`-gated disabled pattern verbatim. |
| error | E1/E2 (create fails) | ✅ covered | `showToast('Failed to create ticket — please try again.', 'error')` per Copywriting Contract; row action reverts to its pre-click state (no ticket created, link re-enabled) — no inline red border or persistent error state on the row itself, matching `43-UI-SPEC.md`'s identical "toast only" rule. |
| populated | E1/E2 (ticket exists) | ✅ covered | Ticket-reference display (`{ProviderBadge} {ticket_ref}` + external link) replaces the text link. |
| partial | E1/E2 (neither provider configured) | ✅ covered | Action hidden entirely — see Copywriting Contract row. |
| overflow | E1/E2 (dropdown near table edge) | 🧪 backstop | The cloned Label-menu dropdown is `absolute right-0` — for the rightmost table column this should stay on-screen, but a very narrow viewport could clip it; held-out visual check, not covered by an automated test. |
| zero-one-many | E1/E2 | ⬜ not applicable | Exactly one ticket per asset/request in v1 (locked rule) — no count variance to handle. |
| long-text | E1/E2 (`ticket_ref` value) | 🧪 backstop | Provider-issued ticket keys (e.g. `PROJ-12345`) are short and bounded by the provider's own key format; still, no `truncate`/`title` safeguard is specified — held-out visual check in case a provider ever returns an unusually long reference string. |
| destructive | E1/E2 | ⬜ not applicable | No destructive action exists in this phase's UI surface (see Copywriting Contract). |
| populated | E3 (webhook event picker, 16 total entries after this phase) | ✅ covered | Existing scrollable checkbox list (`space-y-2 max-h-48 overflow-y-auto`) already handles a growing list — unchanged by this phase, confirmed to already scroll past its current 8 entries. |
| overflow | E3 | ✅ covered | Same `max-h-48 overflow-y-auto` container — already handles 16 > 8 entries without layout changes. |
| long-text | E3 | ⬜ not applicable | Event-type strings are fixed, short, system-authored identifiers (max `asset.warranty_expiring`, well within the existing `font-mono text-sm` line). |
| empty / loading / error | E3 | ⬜ not applicable | E3 is a static constant array, not a fetched/data-dependent list — these categories don't apply. |
| zero-one-many | E3 | ⬜ not applicable | Always exactly 16 entries post-phase — a fixed constant, not a data-driven count. |

## Component Notes for Executor

- **Provider value must be a strict enum, never free text** (mirrors `43-UI-SPEC.md`'s identical note, and RESEARCH.md's V5 Input Validation guidance): the dropdown's selection is `'jira' | 'servicenow'`, sent as that literal string to the new manual-create-ticket endpoint — never a free-text provider field anywhere in this UI.
- **Provider availability derivation:** reuse the same `GET /api/ticketing/config` response `43-UI-SPEC.md` already established for deriving `hasJira`/`hasServiceNow` — no new backend endpoint needed just to decide whether to show/hide/pick.
- **Three-state render logic for the row action**, in priority order (identical structure to `43-UI-SPEC.md`'s locked rule, applied per-row instead of per-modal):
  1. `ticket_ref` truthy on the asset/request → render the ticket-reference display only (action link fully hidden).
  2. Neither provider configured → hide the action entirely.
  3. Otherwise → render `Create Ticket` directly if exactly one provider is configured; render the cloned Label-menu dropdown (Jira / ServiceNow) if both are configured.
- **Clone, don't reinvent, the dropdown:** `LifecyclePanel.tsx` already has a working absolute-positioned menu (`labelMenuAssetId` state + outside-click-close `ref` pattern) for the `Label` action a few lines above where `Create Ticket` will sit — reuse that exact state-management shape (a sibling `ticketMenuAssetId`/`ticketMenuRequestId` state) rather than introducing a new dropdown/menu component or a UI library dependency.
- **Toast timing:** identical to `43-UI-SPEC.md` — success/error is communicated via toast only; the row itself shows no other error affordance (no red border, no inline error text), since ticket creation failure does not block or roll back anything else on the row.
- **`ticket_ref` field is additive** on both the `Asset` and `ItamAssetRequest` types (currently absent from both in `types.ts` — confirmed; only the unrelated `RemediationTask` type has `ticket_ref` today at `types.ts:1939`). Add it as an optional field on each, matching the existing `warrantyAlertSentAt`-style additive-marker pattern RESEARCH.md documents for the backend side.
