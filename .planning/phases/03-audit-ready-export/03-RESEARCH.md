# Phase 03: Audit-Ready Export — Research

**Researched:** 2026-06-17
**Domain:** Compliance report generation — PDF (reportlab), Excel (openpyxl), tenant isolation, evidence source labelling
**Confidence:** HIGH

---

## Summary

The project already contains a mature compliance reporting stack. The key files — `compliance_reporting_pdf.py`, `compliance_reporting_excel.py`, `compliance_reporting_data.py`, `compliance_reporting_service.py`, and `compliance_report_endpoints.py` — all exist and are wired into the router registry. PDF is generated by `reportlab 4.5.1`; Excel by `openpyxl 3.1.5`. Both libraries are installed in the venv and declared in `requirements.txt`.

The core reporting pipeline has three gaps relative to the AUDIT-01 through AUDIT-04 requirements:

1. **AUDIT-01 / AUDIT-02: Missing auditor-required header fields.** The PDF title line currently shows only `{FRAMEWORK_NAME} COMPLIANCE REPORT` and a generated-at timestamp. It does not include the tenant name or an explicit export date field as a metadata row. The XLSX header row shows the framework name and generation timestamp but also omits tenant name.

2. **AUDIT-03: Evidence source labelling is absent.** The `_flatten_evidence` helper in `compliance_reporting_data.py` collects `name`, `url`, `description`, `uploadedAt`, and `status` from each evidence item but does not extract the `source` (`"manual"` or `None`) or `systemGenerated` (`True`/`False`) fields that Phase 2 introduced on `compliance_evidence_endpoints.py`. As a result, both PDF and XLSX render a single combined evidence list with no label distinguishing agent-collected from user-uploaded evidence.

3. **AUDIT-04: Tenant isolation is not enforced inside `_build_report_data`.** The function accepts only `framework_id` and queries the database without passing a `tenant_id` parameter. The `compliance_frameworks` collection is declared as a global-reference exemption in `database.py` (`TenantIsolatedDatabase.__getattr__`), meaning its `find_one` bypasses the automatic `tenantId` injection. The `asset_compliance` and `compliance_artifacts` queries do go through `TenantIsolatedCollection`, so they are protected by the context-variable system — but only if `set_tenant_id` has been called on the request context before `_build_report_data` runs. The endpoint in `compliance_report_endpoints.py` does call `get_current_user` (which sets the context variable inside `authentication_service.py`) before dispatching, so those two collections are safe. However, the `compliance_frameworks` query is unprotected and will return any framework regardless of tenant — meaning a user can request a report for a framework that belongs to a different tenant's namespace if framework IDs are guessable. Additionally, the download endpoint does enforce tenant ownership via `db.compliance_reports` metadata, but the download-by-filename route in the legacy `compliance_reports_endpoints.py` has **no tenant check** (it only verifies file existence).

**Primary recommendation:** The plan should add three targeted edits: (a) add tenant-name lookup + header fields to the PDF and XLSX generators, (b) extend `_flatten_evidence` to extract and bucket evidence by source, and (c) add a `tenant_id` parameter to `_build_report_data` with an explicit tenantId filter on the `compliance_frameworks` lookup and a guard on the download route in `compliance_reports_endpoints.py`.

| Check | Current State | Gap |
|-------|---------------|-----|
| `asset_compliance` query | Protected by `TenantIsolatedCollection` (context variable) | None — as long as `set_tenant_id` was called before `_build_report_data` |
| `compliance_artifacts` query | Protected by `TenantIsolatedCollection` | None |

| `compliance_reports` download check | Protected — `compliance_report_endpoints.py` download route checks `db.compliance_reports.find_one({"filename": filename, "tenantId": caller_tenant})` | None |
| Legacy download route | **Unprotected** — `compliance_reports_endpoints.py` download route does NOT check tenant | Add tenant check or remove duplicate router |

**Key finding on `compliance_frameworks`:** The collection is declared as a global exemption because frameworks are platform-seeded and shared across tenants (ISO 27001 controls are the same for every tenant). Cross-tenant leakage risk is therefore **low for framework metadata** (control names and descriptions are public standard definitions). The risk is higher for `asset_compliance` and `compliance_artifacts` records, which are already protected. The planner should nonetheless add a validation step: when a `framework_id` is submitted, verify the framework exists, then proceed. The tenant-id should be stamped into `_persist_report_meta` (already done) so the download check remains authoritative.

**High-risk item:** The `compliance_reports_endpoints.py` legacy download route at line 86-110 has no tenant check. A user who guesses a filename from another tenant can download it. This must be fixed in Phase 3.

### Pattern 2: Evidence Source Bucketing in `_flatten_evidence`

**What:** Split evidence into automated and manual buckets using `systemGenerated` and `source` fields from Phase 2.

**When to use:** Replace `_flatten_evidence` signature/return value to include two counts and prefixed names.

```python
# Source: codebase reading of admin_evidence_service.py and compliance_evidence_endpoints.py
def _flatten_evidence(evidence_list: list) -> dict:
    auto_names, manual_names = [], []
    urls, descs, dates = [], [], []
    seen_ids: set = set()
    for e in evidence_list:
        eid = e.get("id") or e.get("url") or e.get("name", "")
        if eid in seen_ids:
            continue
        seen_ids.add(eid)
        is_auto = e.get("systemGenerated") is True or e.get("source") is None
        name = e.get("name") or e.get("filename") or ""
        label = "[Auto]" if is_auto else "[Manual]"
        if name:
            (auto_names if is_auto else manual_names).append(f"{label} {name}")
        # ... url, desc, date extraction unchanged ...
    all_names = auto_names + manual_names
    return {
        "names": all_names,
        "auto_count": len(auto_names),
        "manual_count": len(manual_names),
        "count": len(seen_ids),
        "urls": urls, "descriptions": descs, "uploaded_ats": dates,
    }
```

### Pattern 3: Framework Scoping for Tenant Isolation

**What:** `compliance_frameworks` is a global collection (platform-seeded, shared). The risk is not cross-contamination of framework definitions (those are identical across tenants) but rather that a user can generate a report for a framework that has no data in their tenant. The `asset_compliance` and `compliance_artifacts` queries are already tenant-filtered via `TenantIsolatedCollection`. So the practical fix is:

1. Pass `tenant_id` into `_build_report_data`.
2. Do NOT add a `tenantId` filter to the `compliance_frameworks` lookup (framework definitions are intentionally global).
3. After fetching `asset_compliance` records, if zero records are returned and `tenant_id` is set, return empty results (already the case — `asset_counts` will be empty and the report will render with no-data rows).

This means isolation is enforced at the data layer without restricting which framework IDs a user can reference — which is correct, since framework IDs are public knowledge (ISO 27001, SOC 2, etc.).

### Anti-Patterns to Avoid

- **Adding tenantId to the compliance_frameworks query:** Will break the system because platform-seeded frameworks do not have `tenantId` set.
- **Generating PDFs/XLSX synchronously on large tenants:** `_build_report_data` can fetch up to 10,000 `asset_compliance` records. For tenants with many assets, this can exceed a 30-second request timeout. The current approach is acceptable for the scope of this phase (no background task queue is in scope); the planner should add a note to consider async task offloading in a future phase.
- **Writing to `static/reports/` without the directory guarantee:** The `_ensure_reports_dir()` call in the endpoints is correct; both generators also use `os.makedirs(reports_dir, exist_ok=True)` in the service constructor.

## Common Pitfalls

### Pitfall 1: `_flatten_evidence` signature change breaks callers

**What goes wrong:** `_flatten_evidence` is called from `_build_report_data`, which then uses the return dict to build `control_rows`. If the return dict gains new keys (`auto_count`, `manual_count`) but the control_rows builder does not reference them, the keys are silently lost.

**Why it happens:** Python dict construction from returned values; unused keys are dropped when building the control_rows list.

**How to avoid:** Update `_build_report_data` to add `"Auto Evidence"` and `"Manual Evidence"` keys to each `control_rows` entry using the new `auto_count` and `manual_count` from `_flatten_evidence`.

**Warning signs:** PDF and XLSX render `auto_count = 0` or column headers appear but all values are `0`.

### Pitfall 2: `tenants` collection uses the global exemption — no auto-filter

**What goes wrong:** `db.tenants` is in the exemption list of `TenantIsolatedDatabase`, so querying it does not auto-inject `tenantId`. However, this is correct: tenants are looked up by ID to get the display name — no isolation needed here.

**Why it happens:** Confusion between "isolation of data from other tenants" and "looking up tenant metadata by the caller's own ID".

**How to avoid:** The lookup `db.tenants.find_one({"id": tenant_id})` is safe and intentional.

### Pitfall 3: Legacy duplicate endpoint (compliance_reports_endpoints.py) missing tenant check on download

**What goes wrong:** `compliance_reports_endpoints.py` exposes `/api/compliance/reports/download/{filename}` with no tenant ownership check — it only verifies the file exists on disk. A user who guesses a filename can download any tenant's report.

**Why it happens:** This file appears to be an older implementation predating the `compliance_reports` metadata collection.

**How to avoid:** Add the same tenant check to the legacy route, or remove the legacy route from router_registry.py and rely solely on `compliance_report_endpoints.py`. The simpler fix is to add the check to the legacy file.

**Warning signs:** In test, a user from tenant-A can download a file stamped with tenant-B's name if they know the filename pattern (`compliance_report_{framework_id}_{timestamp}.pdf`).

### Pitfall 4: `_generate_all_excel` / `_generate_all_csv` iterate ALL frameworks

**What goes wrong:** The "all frameworks" export in `compliance_reporting_excel.py::_generate_all_excel` and `compliance_reporting_service.py::_generate_all_csv` queries all frameworks via `db.compliance_frameworks.find({})`. This returns platform-global framework definitions. However, if `tenant_id` is not passed, the subsequent `_build_report_data` calls will still pull asset_compliance rows filtered by tenant (via context var) — so the data content is tenant-safe. The risk is that the report cover sheet lists frameworks that have zero data for the tenant, which looks misleading to an auditor.

**How to avoid:** Pass `tenant_id` to `_generate_all_excel` and `_generate_all_csv`; skip frameworks with zero control rows for that tenant.

### Pitfall 5: File-size explosion with large evidence blobs

**What goes wrong:** Automated evidence records include a `content` field with up to 4000 characters of PowerShell output. The `_flatten_evidence` function captures `description` but not `content`. If `content` were added to the export columns, a single cell could contain 4 KB of text, making the XLSX unreadable and the PDF table overflow.

**How to avoid:** Keep the existing pattern — only export `description`, `name`, `url`, `uploadedAt`, and `status`. Do not add `content` to report columns.

2. **"All frameworks" export scope for AUDIT-04**
   - What we know: The "all frameworks" routes exist and iterate every framework.
   - What's unclear: Whether AUDIT-04 applies to "all frameworks" export (which is not mentioned in the AUDIT requirements, only single-framework export is mentioned).
   - Recommendation: Apply tenant isolation to "all frameworks" exports defensively — skip frameworks with zero data for the tenant rather than showing empty sheets.

### Known Threat Patterns for this Stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Path traversal via filename | Tampering | Existing `Path.resolve()` guard in `compliance_report_endpoints.py`; must be replicated in legacy route |

| Framework ID enumeration | Information Disclosure | Low risk — frameworks are global reference data; asset_compliance data is tenant-filtered |
| Large file DoS (malformed report) | Denial of Service | Reports are generated server-side by trusted code; no user-controlled content enters the generator |
