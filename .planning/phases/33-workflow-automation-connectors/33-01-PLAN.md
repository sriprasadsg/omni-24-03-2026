<objective>
Add a real, verifiable machine-to-machine authentication path so the n8n node (WF-01) and the Zapier app (WF-02) can authenticate to this platform's webhook CRUD. Today `tenant_endpoints.py::generate_api_key` stores only a display prefix and nothing in the codebase verifies an inbound API key — this plan closes that write-only gap.

Purpose: Both connectors authenticate via a static `X-API-Key` header, not an interactive JWT login. Without a hash-at-rest + verification path, neither connector can call `/api/webhooks` at all — this is the load-bearing Wave-1 prerequisite for the whole phase.
Output: `backend/api_key_auth.py` (new `get_current_user_or_api_key` dependency), a `keyHash` field written by `generate_api_key`, the four webhook routes wired to accept the API-key path, and `backend/tests/test_api_key_auth.py`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| external automation client → /api/webhooks | An n8n/Zapier client presents an X-API-Key header; untrusted credential crosses into tenant-scoped data |
| stored API key at rest → tenants.apiKeys[] | The persisted representation of a credential; must not be reversible to the live key |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-33-KEY | Information Disclosure | generate_api_key storage / apiKeys[] | high | mitigate | Store only `keyHash` = SHA-256(plaintext); the live key is returned once and never persisted recoverably (Task 1). Verification is an indexed equality lookup on keyHash, never a plaintext compare. |
| T-33-ROLE | Elevation of Privilege | get_current_user_or_api_key role assignment | high | mitigate | API-key requests carry the narrow `api-integration` role only; asserted NOT in auth_roles.SUPER_ROLES, so every `_WEBHOOK_SUPER_ROLES` branch resolves to the tenant-scoped query (Pitfall 2, Tasks 1-2). |
| T-33-TENANT | Information Disclosure | non-JWT tenant context vs TenantIsolatedCollection | high | mitigate | get_current_user_or_api_key calls set_tenant_id(tenant["id"]) before returning, per Phase 29's mandatory non-JWT precedent — prevents cross-tenant read/write via TenantIsolatedCollection (Task 1). |
| T-33-SSRF | Tampering | webhook URL validation | medium | accept | `_is_safe_webhook_url`'s private/link-local/loopback blocklist already applies to every POST /api/webhooks regardless of auth method; this plan does not weaken or bypass it. |
| T-33-BRUTE | Spoofing | X-API-Key auth-failure path | low | accept | Keys are `secrets.token_urlsafe(32)` = 256 bits of entropy; no realistic brute-force surface. Optional slowapi rate-limiting on the failure path is a documented follow-up, not required at ASVS L1. |
</threat_model>
