<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry → this repo (supply chain) | New dependencies pulled during install (all OK-verdict per the Package Legitimacy Audit) |
| Zapier app → /api/webhooks (client) | The app holds a tenant API key (bundle.authData) and calls the platform API as an external client |
| platform → Zapier catch-hook (inbound POST) | Zapier receives event POSTs and must be able to verify authenticity |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-33-SC | Tampering | npm install of zapier-platform-core / -schema / -cli | medium | mitigate | All three packages are verdict OK / Approved in 33-RESEARCH.md's Package Legitimacy Audit (publisher zapier, 55k–101k weekly downloads); versions pinned to the audited 19.0.0 line via package.json + lockfile. No SUS package in this plan, so no blocking checkpoint is required (contrast 33-03). |
| T-33-KEYSTORE | Information Disclosure | apiKey stored in Zapier connection (bundle.authData) | medium | mitigate | apiKey uses Zapier's password input type (masked, stored encrypted by Zapier); README surfaces revocation via the platform's existing revoke_api_key. |
| T-33-SIGN-VERIFY | Spoofing | inbound POST authenticity at the Zapier catch-hook | medium | mitigate | README documents verifying the `X-Webhook-Signature: sha256=...` header (produced by 33-02) against the per-webhook secret. |
| T-33-DUP | Tampering (availability) | duplicate subscriptions on Zap re-enable | low | mitigate | Zapier's lifecycle calls performUnsubscribe (keyed on subscribeData.id) before re-subscribe; implementing it correctly prevents duplicate db.webhooks entries (Pitfall 3). |
