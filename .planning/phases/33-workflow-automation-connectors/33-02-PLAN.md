<objective>
Fix the pre-existing bug where `webhook_service.py::_send_single_webhook` never signs its outbound payloads even though every webhook is created with an auto-generated `secret` (`whsec_...`) that is stored but never used. Clone the proven HMAC-SHA256 signing pattern from the sibling `ticket_webhook_service.py` so both connectors (and any generic receiver) can verify that a POST genuinely came from this platform.

Purpose: n8n's Webhook node and Zapier's catch-hook both expect an HMAC signature header to confirm authenticity of inbound POSTs. Without it the connectors have no way to reject forged events (Spoofing/Tampering). This is a small, contained Wave-1 backend prerequisite that closes the connectors' security story.
Output: signed outbound deliveries from the generic webhook path, plus `backend/tests/test_webhook_signing.py` proving the signature matches the exact bytes sent.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-33-SIGN | Spoofing / Tampering | _send_single_webhook outbound delivery | high | mitigate | HMAC-SHA256 sign every delivery with the hook's existing per-webhook `secret`, emitting `X-Webhook-Signature: sha256=...` (cloning ticket_webhook_service.py). A forged POST to the receiver cannot reproduce the signature without the secret (Task 2). |
| T-33-BYTES | Tampering | signature-vs-body mismatch (httpx json= auto-serialization) | high | mitigate | Sign the exact bytes sent: `body = json.dumps(payload)` signed AND passed to `content=body`; never sign one string while httpx re-serializes another via `json=` (Tasks 1-2 both assert this). |
| T-33-SECRET | Information Disclosure | per-webhook secret at rest (whsec_...) | low | accept | Secret already exists per-webhook in db.webhooks; this plan only starts using it for signing — it does not relocate, log, or expose it. No new exposure surface. |
</threat_model>
