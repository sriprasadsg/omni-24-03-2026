# Phase 74 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase spans **three surfaces**, two of which are native Windows UI, not React/Tailwind:

| # | Surface | Stack | Files |
|---|---------|-------|-------|
| 1 | Admin console (view/control canvas + dashboard) | React + Tailwind, existing enterprise design system | `components/RemoteDesktop.tsx`, `components/RemoteAccessDashboard.tsx` |
| 2 | Endpoint consent dialog | **Native** — PowerShell WinForms spawned via `CreateProcessAsUserW` (Rust) / `win32process.CreateProcessAsUser` (Python) | new `consent_ui.rs` / `consent_ui.py`, per `74-RESEARCH.md` Pattern 1/2 |
| 3 | Endpoint stop-control banner | **Native** — same session-injection mechanism, always-on-top WinForms window | same new modules, persistent variant |

Surfaces 2 and 3 are explicitly declared **not part of the Tailwind/shadcn design system** — no CSS variables, no Tailwind classes apply. Their contract below specifies plain hex colors, point sizes (native Win32 UI uses points/DPI-aware pixels via WinForms, not CSS px), and exact copy so the executor can hardcode them into the PowerShell/WinForms script without design ambiguity.

**shadcn gate decision:** `components.json` does not exist in this repo. Per the shadcn gate, the reasonable call for this phase is **do not initialize shadcn now** — the project already carries a single, actively-maintained, non-shadcn Tailwind design system (`design-system/enterprise-omniagent/MASTER.md`, applied project-wide the day before this phase started) with its own CSS-variable color scale (`--primary-*`) and component conventions (`.card`, `.btn-primary`, `.input`). Introducing shadcn for one phase's two small additions (a mode toggle, a disconnect button) would fragment that system rather than extend it. Executor and checker should validate this phase's new React elements against the tokens below, not against shadcn primitives.

**Known pre-existing inconsistency, not in scope to fix:** `RemoteAccessDashboard.tsx` is written entirely in inline `style={}` objects with hardcoded hex values (`#6366f1` indigo/violet, `#10b981`, `#0a0a1f`-era colors), predating the `0e963705f` "Trust & Authority" palette migration and never swept by it (that commit's grep matched literal gradient strings, not this file's standalone indigo accent). `RemoteDesktop.tsx`, by contrast, already uses Tailwind utility classes (`bg-slate-950`, `border-slate-800`, `text-slate-200`, `text-green-400`, `text-red-400`, `text-yellow-500`) which visually match the design system's dark-surface conventions closely enough to extend directly. **Rule for this phase's new code:** every new element this phase adds (mode toggle, disconnect button, control-mode canvas states) MUST use Tailwind utility classes with hex/token values from the table below — never a new inline `style={}` object, and never indigo/violet (`#6366f1`-family) for new accents, since violet is an explicit anti-pattern in the current design system (`MASTER.md` "Anti-Patterns: AI purple/pink gradients"). Do not fix the surrounding file's existing inline styles — out of scope.

## Typography — Surface 1

This phase's new elements are constrained to exactly **2 font weights** — 400 (regular) and 700 (bold) — regardless of how many weights the project's font loader makes available elsewhere. 4 declared sizes, each mapped to one of the two weights:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label (badges, status text, uppercase eyebrow) | 12px | 700 | 1.4 |
| Heading (panel titles, e.g. "Remote Desktop — {hostname}") | 16px | 700 | 1.2 |
| Display (page title, "Remote Access") | 28px | 700 | 1.2 |

Plus Jakarta Sans is loaded project-wide with weights 400/600/700/800 available (`design-system/enterprise-omniagent/MASTER.md`), but that project-wide availability does not exempt this phase from the 2-weight cap — **this phase's new UI elements use only 400 and 700**. 600 and 800 are out of scope for any element this phase introduces, even though the font family itself supports them; do not reach for 600 (e.g. for a "semibold" label) or 800 (e.g. for extra emphasis on the display size) anywhere in the new mode-toggle, disconnect button, or canvas-state elements.

## Interaction Contract — Surface 1 (View vs. Control distinction)

This is the core new interaction surface this phase adds. Four canvas states, each visually and behaviorally distinct:

| State | Trigger | Canvas visual | Cursor | Badge |
|-------|---------|---------------|--------|-------|
| **View-only** | Admin has `view:remote_access` only, or explicitly chose "View Only" mode | Default border (`border-slate-700`, unchanged from today) | `cursor-default` | Small slate badge, "View Only" (no color, no icon) top-right of canvas |
| **Control requested — awaiting consent** | Admin has `control:remote_access`, chose "Request Control", session started, consent dialog shown on endpoint but not yet answered | Canvas dimmed to 60% opacity via a semi-transparent overlay (`bg-slate-950/40` over the frame), spinner centered | `cursor-wait` | Amber pulsing badge (`bg-amber-500/20 text-amber-400`, `animate-pulse`), "Waiting for approval…" |
| **Control active** | Endpoint user clicked Accept; agent has started the `SendInput` relay task | Canvas border changes to `border-emerald-500` (2px ring, `ring-2 ring-emerald-500/50`) to make the elevated-privilege state unmissable at a glance | `cursor-crosshair` (signals "this canvas now captures your mouse/keyboard") | Solid emerald badge with pulsing dot, "LIVE CONTROL" |
| **Control ended/declined** | Endpoint user declined, or D-12 WS-drop-ends-session fired, or admin/platform-admin disconnected | Canvas reverts to View-only visual; a one-line banner replaces the badge | none (reverts to default) | Red-text inline banner (not a persistent badge — this is a transient, dismissible notice), see Copywriting Contract |

Mouse/keyboard capture (`onMouseDown/Move/Up/onWheel/onKeyDown/Up`) is only attached to the canvas element while state = **Control active**. In all other states the canvas has zero input handlers, exactly as it does today — this prevents accidental input leakage during the awaiting-consent window, which is itself a security property (D-01 says the RBAC permission alone must not grant control; the UI must not even attempt to send input frames before consent is confirmed).

**Mode selection entry point:** `RemoteAccessDashboard.tsx`'s existing Terminal/Desktop segmented toggle pattern (rounded pill, `background: rgba(255,255,255,.06)`) is reused for a second, nested toggle that only appears when Desktop mode is active AND the current user has `control:remote_access`: **View | Control**. If the user only has `view:remote_access`, this toggle is not rendered at all (not shown-disabled — omitted, since a disabled-but-visible control-mode option would leak the existence of a permission tier the user doesn't have, which is unnecessary UI noise for a security-gated feature).

**Admin-side disconnect (D-10):** A "Disconnect" button (destructive red, `text-red-400 border border-red-500/40 hover:bg-red-500/10`) appears in `RemoteDesktop.tsx`'s header row (next to the existing FPS counter) whenever `isConnected` is true, regardless of view/control mode. See Copywriting Contract for the two-step confirm interaction.

## Design System — Surfaces 2 & 3 (Native Windows UI)

**These are NOT web components.** No Tailwind, no CSS variables, no shadcn. They are PowerShell WinForms windows spawned into the interactive user's session via `CreateProcessAsUserW`/`CreateProcessAsUser`, per `74-RESEARCH.md` Pattern 1/2. The values below are given as literal hex colors and point sizes for direct use in the WinForms script (`.BackColor`, `.Font = New-Object System.Drawing.Font(...)`), not as design tokens to be looked up from a shared system — there is no shared system reachable from a Session-0 service process.

To keep a consistent brand feel with the web admin console despite being a wholly different rendering stack, both native windows reuse the **same hex values** as Surface 1's dominant/accent/destructive colors (`#0b1220` dark surface, `#0369A1` accent blue, `#DC2626` destructive red), so a user who has seen the web dashboard recognizes the native dialog as "the same product," not a bare unstyled `MessageBox`.

| Property | Value |
|----------|-------|
| Font family | Segoe UI (Windows system default — do not bundle a custom font into a Session-0-spawned script; adds failure surface for zero visual benefit at this size) |
| Font sizes | Title: 12pt bold · Body: 10pt regular · Button label: 10pt bold |
| Background | `#0b1220` (dark surface, matches web canvas background) |
| Foreground text | `#F8FAFC` (near-white, matches web `slate-100`) |
| Accept / primary button | Fill `#0369A1`, text `#FFFFFF` |
| Decline / stop button | Fill `#DC2626`, text `#FFFFFF` |
| Window chrome | No minimize/maximize box; `TopMost = $true`; no taskbar icon requirement either way (leave default) |

### Surface 2 — Consent Dialog (D-01, D-03)

**Layout:** Fixed 440×240px window, centered on the primary screen (`Screen.PrimaryScreen.Bounds` midpoint — reuse the same `System.Windows.Forms.Screen` pattern the existing screenshot capture script already uses per `remote_access.rs:200-206`).

**Content, top to bottom:**
1. Small icon or text glyph indicating a remote-access request (a simple monitor/shield character is sufficient — do not require a bundled icon asset for a Wave-0 script).
2. Title line (12pt bold): `"Remote Support Request"`
3. Body line (10pt regular), **filled with the requesting admin's identity and tenant per D-03** — never generic:
   `"{admin_name} ({admin_email}) from {tenant_name} is requesting to remotely control this computer."`
4. A second, smaller clarifying line (10pt regular, slightly muted `#94A3B8`):
   `"They will be able to see your screen and control your mouse and keyboard until you stop it or the session ends."`
5. Two buttons, right-aligned, in this order: **Decline** (secondary/outline, left) then **Accept** (primary filled `#0369A1`, right — rightmost position is the affirmative action by Windows dialog convention).

**Timeout behavior (Claude's Discretion, not locked by CONTEXT.md — default applied):** If neither button is clicked within **60 seconds**, the dialog auto-closes and reports Decline. This prevents an unattended machine from leaving a control request hanging indefinitely, and matches Zoho Assist's own request-timeout convention. Flag as a `checkpoint:human-verify` default the planner may adjust.

**No-interactive-session case (D-02):** This dialog is never shown at all when `WTSGetActiveConsoleSessionId() == 0xFFFFFFFF` — the request is refused before session-injection is attempted. See Copywriting Contract for the refusal string surfaced to the admin instead.

### Surface 3 — Persistent Stop-Control Indicator (D-09)

**Layout:** A slim always-on-top bar, 360×48px, anchored top-center of the primary screen (matches Zoho Assist's floating control-bar convention cited in CONTEXT.md's Specific Ideas). Not draggable — fixed position, so it can't be accidentally moved off-screen and lost.

**Content, left to right:**
1. Small pulsing dot or icon (`#DC2626` on `#0b1220`) — persistent visual "something privileged is happening" signal, always visible, never fades.
2. Text (10pt regular, `#F8FAFC`): `"{admin_name} is controlling this computer"`
3. A single button, right-aligned, filled `#DC2626`, white text, label: `"Stop Control"`.

**Behavior:** Clicking "Stop Control" is immediate — **no confirmation step**, no second click, no dialog. This is a deliberate departure from the admin-side disconnect's two-step confirm (see Copywriting Contract): an emergency stop that requires confirmation defeats its own purpose (D-09's own rationale: "consent that can't be revoked mid-session isn't real consent" — friction here directly undermines that guarantee). The bar remains visible for the entire duration of an active control session and disappears immediately once control ends (by any of: this button, admin disconnect D-10, platform-admin force-kill D-11, or WS-drop D-12).

**Does not appear during view-only sessions** — this bar is scoped exclusively to `control:remote_access` sessions where `SendInput` is actually active; a passive screenshot-stream viewer session gets no on-screen indicator today and this phase does not change that (out of scope — D-09 only covers control sessions).

| Element | Copy |
