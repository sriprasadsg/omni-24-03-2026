makes the elevated-privilege state unmissable, full mouse and keyboard capture that only exists
while consent holds, and three destructive affordances whose confirmation weight matches their
blast radius.

force-end affordances.

<planner_assumptions>
Two rows in `74-UI-SPEC.md`'s UI Considerations table were left `unresolved`. Both are decided
here rather than dropped:

1. **Two admins requesting control of the same agent at once.** Resolved backend-side in Plan 02:
   a second control request against an agent with a pending or active control session is refused
   with HTTP 409 and a `reason` of `already_controlled`. This plan renders that as its own message
   naming the holding admin — never a silent queue and never a silent override.
2. **Endpoint accepts consent but the input relay then fails to start.** Treated identically to a
   session end (D-12's copy), not given a fifth distinct error string. The dashboard cannot
   distinguish "accepted then broke" from "connection dropped" without agent-side telemetry this
   phase does not build, and inventing a message the system cannot actually justify would be worse
   than reusing an accurate one.
</planner_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DOM events → input frames | Real user input is serialized into frames that end up as `SendInput` calls on someone's desktop |
| browser → API | Disconnect and capability calls cross into the tenant-scoped backend |
| server capability probe → rendered affordance | A boolean decides whether a privileged control is drawn |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-74-03 | Elevation of Privilege | View and Control toggle | high | mitigate | The toggle is an affordance gate only. Real enforcement is `verify_permission` on `start_remote_session` and `require_permission` on the disconnect route (Plans 01 and 02), so a user who edits client state to reveal the toggle still receives 403. The client is never the boundary |
| T-74-25 | Elevation of Privilege | canvas input handler binding | critical | mitigate | Handlers are bound conditionally on the control-active state rather than bound always with an early return, so during the awaiting-consent window there is no code path that can emit an input frame at all |
| T-74-26 | Information Disclosure | absent versus disabled toggle | low | mitigate | The toggle is omitted rather than disabled for users without the permission, so the UI does not enumerate a permission tier to someone who lacks it, including to anyone reading over their shoulder |
| T-74-27 | Spoofing | consent assertion from the browser | high | mitigate | No client wrapper for the consent route is added, and an acceptance criterion greps to prove none exists. Only the tunnel-authenticated agent can assert a consent decision (Plan 02) |
| T-74-09b | Elevation of Privilege | Force End Session | medium | mitigate | Rendered only for the super-role set and behind a full confirmation modal; the backend re-checks the role independently and audits every force-kill, so hiding or showing the button changes nothing about who can actually use it |
| T-74-28 | Tampering | key event capture | low | accept | `preventDefault` while control is active intercepts browser shortcuts within the canvas so keys reach the endpoint. The scope is the focused canvas during an actively-consented session, and the browser retains its own escape hatches outside it |
| T-74-SC | Tampering | dependency manifests | low | accept | No package added. Icons come from `lucide-react`, already a dependency; no component registry of any kind is used, per the UI-SPEC's Registry Safety section |
</threat_model>
