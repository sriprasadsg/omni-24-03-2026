<assumption_delta_decision>
**Noun now primary:** the remote-access permission set becomes plural — `view:remote_access`
gains a sibling, `control:remote_access`.

**Decision: `add-alongside`** (not `promote`). The usual correct move would be to promote a
tiered `remote_access` permission family to primary and demote the existing flag to one variant
of it. That is explicitly forbidden here: D-06 locks a binary permission model and rejects any
intermediate tier, so building a tier family would implement a decision the user declined.

**Accepted debt:** if a third tier is ever wanted, the promotion to a permission family happens
then, and it will touch the RBAC check, the frontend affordance gate, and both agents' input
dispatchers — the cost D-06's own reversibility rationale already names. Recorded, not hidden.

**Corollary decided here:** neither permission implies the other. No implication/hierarchy code
is written. Both `admin` and `Tenant Admin` are granted both permissions explicitly, so a
control session (which necessarily also streams the screen) needs no implicit grant to work.
</assumption_delta_decision>

  <name>Task 1: Lock the remote-input and control-state wire contract</name>
  <decision>Select the JSON frame contract that the browser, the backend relay, the Rust agent, and the Python agent will all speak for interactive control. RESEARCH.md Open Question 2 left this open; the recommended option is pre-filled and needs a yes or no, not a redesign.</decision>
  <context>
This is a one-way door. The contract is consumed by two agent binaries that ship to endpoints via
the installer — `agent-install/omni-agent-rs` and the legacy `agent/` Python tree (D-13). Once
agents speaking this contract are installed in the field, changing a field name or a coordinate
space is not a refactor: an old agent and a new browser talk past each other, and the undo is a
coordinated redeployment across the whole installed base. The backend relay is frame-agnostic (it
moves bytes) and the browser ships with the backend, so the agents are the only version-skew
surface — but they are the one that matters.

Option A's concrete shape, browser to agent over `/api/tunnel/{session_id}/user`:
an `input` type with a `kind` of `mousemove`, `mousedown`, `mouseup`, `wheel`, `keydown`, or
`keyup`; `x` and `y` as floats from 0 to 1; `button` as an integer 0 to 4; `deltaX` and `deltaY`
as integers; `vk` as an integer 0 to 254 with an `extended` boolean and a nullable `unicode`
code unit.
Agent to browser, new: a `control_state` type with a `state` of `awaiting_consent`, `active`, or
`ended`, plus nullable `reason` and `message`.
Agent to browser, existing `error` frame extended: a `reason` discriminant added alongside the
existing `message`, so the dashboard can tell `no_interactive_desktop` from
`unsupported_platform` from `already_controlled` — RESEARCH.md Pitfall 4 is that all three
currently render identically.
  </context>
  <options>
    <option id="option-a">
      <name>One input envelope, normalized absolute coordinates, browser-side keymap (recommended)</name>
      <pros>Coordinates from 0 to 1 map directly onto `SendInput`'s own `MOUSEEVENTF_ABSOLUTE` 0-to-65535 space, so neither agent queries screen bounds and the fixed 800x600 canvas never has to match the real remote resolution. The DOM-code-to-virtual-key table lives once in the browser instead of being duplicated in Rust and again in Python. A single `type` with a nested `kind` keeps the existing flat discriminated-union convention intact.</pros>
      <cons>Every consumer unpacks two levels (`type` then `kind`) instead of switching once.</cons>
    </option>
    <option id="option-b">
      <name>Six distinct top-level frame types, agent-side keymap, pixel coordinates</name>
      <pros>Slightly cheaper to hand-write and read per message; one flat switch per consumer.</pros>
      <cons>Duplicates the keymap across two agent languages, introduces a canvas-versus-remote resolution mismatch surface, and widens the `type` switch in the browser, both agents, and every future consumer.</cons>
    </option>
  </options>
  <resume-signal>Reply with `option-a` or `option-b`, or describe a variant to adopt instead.</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → API (`POST /api/remote/session/start`) | An authenticated but possibly under-privileged tenant user asks to open a control session |
| browser → WS relay (`/api/tunnel/{id}/user`) | Attacker-controlled JSON input frames enter the system here |
| WS relay → agent (`/api/tunnel/{id}/agent`) | Frames cross into a process running as SYSTEM on a real endpoint |
| agent → Win32 (`SendInput`) | The final boundary — anything past it is real keyboard and mouse activity on someone's desktop |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-74-01 | Elevation of Privilege | `start_remote_session` control branch | critical | mitigate | `verify_permission(user, "control:remote_access")` inside the handler before any session or instruction is written; a `view:remote_access`-only principal gets 403 (Task 2), asserted by `TestControlSessionPermission` (Task 3) |
| T-74-04 | Tampering | `parse_input_frame` → `control_input_replay` | high | mitigate | Boundary validation in `parse_input_frame`: enumerated `kind`, `x`/`y` constrained to 0.0..=1.0, `vk` to 0..=254; out-of-range returns `Err` and the frame is dropped, never clamped into a valid-looking event. Unit-tested platform-independently |
| T-74-11 | Elevation of Privilege | Rust agent input read task | critical | mitigate | The input read task is only spawned when the instruction carried control mode; a view-mode session has no read path at all, so a `view:remote_access` session cannot be upgraded by sending frames at it |
| T-74-12 | Spoofing | `/api/tunnel/{id}/user` | high | mitigate | Unchanged existing controls: `verify_token_async` on the JWT plus the IDOR guard comparing `session.tenantId` to the caller's tenant (`tunnel_endpoints.py` lines 93-119). This plan adds no new auth path — reusing `/user` rather than opening a new endpoint is itself the mitigation |
| T-74-06 | Denial of Service | relay queues, `SendInput` call rate | medium | mitigate | The existing `asyncio.Queue(maxsize=512)` bound on `u2a`/`a2u` already back-pressures a frame flood; the agent replays synchronously off a single task so it cannot outpace its own read loop. Per-second rate limiting is deferred to Plan 03 alongside the consent gate |
| T-74-13 | Information Disclosure | `types.ts` `Permission` union | low | accept | Remote-access permissions are deliberately NOT added to the frontend `Permission` union in this plan; the client learns its control capability from an authoritative server probe (Plan 02) instead of a client-side mirror that `App.tsx` intersects with tenant `enabledFeatures` |
| T-74-SC | Tampering | dependency manifests | low | accept | No package is added in either ecosystem. The only manifest change is enabling the `winuser` feature on the already-vetted `winapi` 0.3 crate, so the Package Legitimacy Gate has nothing to audit (`74-RESEARCH.md` § Package Legitimacy Audit) |
