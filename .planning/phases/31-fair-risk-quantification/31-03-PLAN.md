  <action>
    This is a human verification checkpoint — no code is written. Present the how-to-verify steps below to the user, wait for the resume-signal, and record the outcome (approved, or a defect list) in the SUMMARY. Do not auto-approve.

  <what-built>
    The full FAIR (Factor Analysis of Information Risk) quantitative layer: a tenant-scoped POST /api/risks/{id}/fair-simulation endpoint running a synchronous numpy Monte Carlo (31-01), and a "Quantify with FAIR" trigger + RiskFairModal + FAIR summary column in the Risk Register (31-02). All backend behaviors pass automated tests and the frontend builds clean; this checkpoint confirms the visual/interaction flow works in the running app.
  </what-built>
  <how-to-verify>
    1. Start the backend and frontend the same way the project runs them (e.g. the standard dev-server commands used in prior phases), and log in as a normal tenant user.
    2. Open the Enterprise Risk Register. Confirm the table now has a "FAIR" column and that risks without a simulation show "Not quantified".
    3. On any risk row, click the new "Quantify with FAIR" action. Confirm the FAIR modal opens.
    4. Enter Loss Event Frequency min/likely/max (e.g. 0.1 / 0.5 / 2) and Loss Magnitude min/likely/max (e.g. 10000 / 50000 / 250000), then run the simulation.
    5. Confirm a dollarized loss-exceedance summary renders (mean and p10/p50/p90, plus the exceedance-curve view) and looks sensible (p10 < p50 < p90, values within the input magnitude range).
    6. Close the modal and confirm the risk's FAIR column now shows the "$p10-$p90 (90% CI)" summary without a full page reload.
    7. Negative check: reopen the modal and enter an inverted range (e.g. LEF min 10, likely 5, max 1) and run — confirm you get a clean validation error, not a crash or a raw 500.
  </how-to-verify>
  <resume-signal>Type "approved" if the flow works as described, or describe any defects (each becomes a gap-closure task).</resume-signal>
