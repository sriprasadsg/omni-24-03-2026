<objective>
Deliver the thinnest complete vertical slice of this phase's financial record: one asset gets a purchase record written through a new RBAC-gated, tenant-scoped route, and its current book value is read back straight-line-depreciated — end-to-end through every layer this phase touches except the background scheduler.

Purpose: prove the whole architecture (Pydantic contract extension, pure-service split, RBAC reuse, tenant-isolated atomic update, structured no-policy responses, real router registration, test harness) on one write→read path before Plans 59-02/03/04 expand it to warranty status, alert-window config, and the background alert sweep. Records ITAM-FIN-01 and ITAM-FIN-03 in one slice because a book value is meaningless without a purchase record to depreciate, and a purchase record with no read consumer is a horizontal layer, not a vertical slice.

Output: `backend/itam_finance_service.py` and `backend/itam_finance_endpoints.py` (both new), depreciation and purchase field extensions in `backend/itam_models.py`, a registration line in `backend/router_registry.py`, and the phase's test scaffold (`backend/tests/itam_finance_test_support.py` + `backend/tests/test_itam_finance.py`).

**Planning decisions recorded here (referenced by later plans):**
- **PD-02:** a Model carries a usable depreciation policy only when BOTH `usefulLifeYears` and `salvageValueCents` are present (RESEARCH Pitfall 4). A Model with only one of them yields the structured no-policy response rather than an assumed salvage of zero — a partial policy is ambiguous, and every Model created in Phases 56-58 has neither field.
- **PD-04:** warranty expiry is **derived**, never persisted. The asset document stores `purchaseDate` + `warrantyMonths` (the requirement's own "purchase date + warranty period" wording); `warrantyExpiresAt` exists only as a computed response field, added by Plan 59-03. Persisting it would drift the moment either input changes.
</objective>

Layer 2 — `backend/itam_finance_service.py` (new, pure). Module docstring: this module holds the ITAM finance computations for Phase 59 and deliberately imports neither FastAPI nor any database symbol, so every function is unit-testable without an app or a DB, and so the background sweep Plan 59-04 adds here can never resolve its own database handle (it will receive one as a parameter). Define `REASON_NO_PURCHASE_RECORD = "no_purchase_record"` and `REASON_NO_DEPRECIATION_POLICY = "no_depreciation_policy_assigned"`.

Define `compute_book_value(purchase_date: str, purchase_cost_cents: int, useful_life_years: int, salvage_value_cents: int, now: datetime) -> Dict[str, Any]` exactly as RESEARCH Pattern 4 specifies: parse `purchase_date` with `datetime.fromisoformat(purchase_date.replace("Z", "+00:00"))` and attach `timezone.utc` when the parsed value is naive; compute `years_elapsed` as an anniversary-based whole-year count — `now.year - purchase_dt.year`, minus one when `(now.month, now.day)` has not yet reached `(purchase_dt.month, purchase_dt.day)` — clamped to at least 0 and at most `useful_life_years` (whole-year proration is the resolved Claude's-discretion choice from CONTEXT.md; day- and month-level proration is deliberately out of scope). Compute `annual_depreciation_cents = (purchase_cost_cents - salvage_value_cents) // useful_life_years` using integer floor division (D-01 — all arithmetic stays in integer cents, no float ever enters this function). Compute `book_value_cents = purchase_cost_cents - (years_elapsed * annual_depreciation_cents)` and then raise it to `salvage_value_cents` when it falls below (D-04 — the floor is the salvage value, so the result is never negative and never below salvage). Return `{"bookValueCents": ..., "yearsElapsed": ..., "annualDepreciationCents": ...}`. Raise `ValueError` when `useful_life_years` is not a positive integer or when `purchase_date` is unparseable — the caller is responsible for turning that into a structured response, and this function must never guess a default policy.
