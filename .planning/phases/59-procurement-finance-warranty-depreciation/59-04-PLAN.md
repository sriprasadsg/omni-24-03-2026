<objective>
Close ITAM-FIN-02: a background sweep finds assets whose warranty is inside the tenant's alert window or already past expiry, delivers an alert through both the in-app notification feed and the tenant's configured notification/webhook rules, and marks each asset so it is never alerted twice for the same warranty.

Purpose: this is the highest-risk work in the v4.0 milestone. STATE.md flagged the background-scheduler tenant-isolation bug class as this milestone's most severe recurring risk, this phase's CONTEXT.md named it again by name, and RESEARCH found that a literal reading of D-03's own wording would introduce a second, silent failure on top of it — `notification_service.send_notification` reads `db._db` unconditionally, so calling it with the raw handle D-03 requires would raise `AttributeError` on the first matching asset, be swallowed by the sweep's outer handler, and leave the feature looking installed while delivering nothing. Every design choice below exists to make one of those two failures impossible rather than merely unlikely.

Output: `_tenant_admin_emails`, `_RawDbForNotificationRules`, `run_warranty_alert_pass` and `start_warranty_alert_scheduler` in `backend/itam_finance_service.py`; a registration block in `backend/app_startup.py`; and `backend/tests/test_itam_finance_sweep.py`.

**Planning decision recorded here (PD-03):** the rule-routed delivery call receives a tiny local adapter object exposing `_db`, not `database.TenantIsolatedDatabase` plus a `set_tenant_id`/`reset_tenant_id` pair as RESEARCH Pattern 3's optional path sketched. `send_notification` reads only `db._db.notification_rules` and `db._db.notification_channels`, and every one of those queries already carries an explicit `{"tenantId": tenant_id}` filter — the ContextVar is never consulted on that path. Mutating a process-wide ContextVar inside a long-lived background task would therefore add real leak risk for zero benefit, and the adapter additionally keeps `itam_finance_service` free of any database import, which is what makes the "this module cannot resolve its own handle" guarantee structural rather than a matter of discipline.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application startup → sweep | The database handle chosen here determines whether every subsequent read and write in the sweep is tenant-scoped correctly or not; there is no request context to fall back on. |
| asset documents (all tenants) → sweep loop | One loop body processes documents belonging to every tenant on the platform in sequence, with no ambient isolation. |

| sweep → `assets` collection | A background writer mutates tenant-owned documents with no authenticated user behind it. |
