## Spacing Scale

Declared values (multiples of 4), expressed as the Tailwind steps the executor must use:

| Token | Value | Tailwind | Usage in this phase |
|-------|-------|----------|---------------------|
| xs | 4px | `1` | Icon-to-text gap inside chips, marker padding-y |
| sm | 8px | `2` | Gap between chips and labels, legend gaps, grid row gap in the role panel |
| md | 16px | `4` | Card inner padding on the in-place panel rows, gap between buttons, group padding |
| lg | 24px | `6` | Role panel padding, space between panel sections |
| xl | 32px | `8` | In-place no-access card padding, full-page card padding |
| 2xl | 48px | `12` | Icon circle diameter (no-access icon), vertical breathing room above the in-place card |
| 3xl | 64px | `16` | Not used |

Exceptions:
- 12px (`p-3`, `px-3`) is kept for compact chips, table cells and permission group cards because `RoleEditorModal` and `SettingsRolesTab` already use it. 12 is a multiple of 4.
- Touch/click targets: icon-only buttons in the roles table stay `p-1.5` visually but must expose a 32px minimum hit area (`min-w-8 min-h-8`, `inline-flex items-center justify-center`).
- Existing half-step utilities in untouched code (`py-1.5`, `mb-0.5`) are not copied into new elements.

## Screens and States

### 1. Fail-closed sidebar (ACC-06)

- No new chrome. `Sidebar.tsx` line 181 fail-open fallback is replaced by deny: when `useUser()` is absent, `currentUser` is null, or the permission set has not been delivered, `hasPermission` returns `false` for everything.
- Unknown-permissions state (before `/login` or `/me` data arrives): nav area renders 6 skeleton rows (`h-8` = 32px, `rounded-xl`, `bg-gray-200 dark:bg-gray-700`, `animate-pulse`; collapsed sidebar shows 6 `h-8 w-8` circles). No real item and no group header renders until permissions are known.
- Groups with zero visible items render no header (existing behaviour, keep).
- Super Admin and platform roles keep their existing bypass via `isSuperAdminRoleName` / `isPlatformRoleName`; the bypass applies only to a resolved user, never to a missing one.

### 2. In-place no-access panel (D-05, D-06)

Where: replaces the output of `renderView()` inside `<main>`. Sidebar and Header stay. Nothing of the blocked screen mounts (no component render, no fetch).

Layout: `main` content centers a single card: wrapper `flex justify-center pt-12` (48px top), card `w-full max-w-lg` (512px), `bg-white dark:bg-gray-800 border border-gray-200 dark:border-gray-700 rounded-lg shadow-md p-8` (32px), content left-aligned in a column with `gap-4` (16px) except the icon row.

Anatomy, top to bottom:
1. Icon circle 48px (`h-12 w-12 rounded-full bg-gray-100 dark:bg-gray-700`) holding `ShieldLockIcon` 24px in `text-gray-500 dark:text-gray-400`. `aria-hidden`.
2. Heading (18/600, `h2`, `tabIndex={-1}`, receives focus on render so screen readers announce it): `You don't have access to {Screen label}`.
3. Reason paragraph (14/400, `text-gray-600 dark:text-gray-400`), one of three variants (see Copywriting):
   - `role`: role lacks the permission.
   - `switched_off`: role has the permission but the tenant feature switch is off (spec C6).
   - `unmapped`: the view has no manifest permission (fail closed, 76 IN-04).
4. Required-permission row, `role` variant only: label `Required permission` (12/400 muted) then the permission in a chip (`font-mono text-xs px-2 py-1 rounded bg-gray-100 dark:bg-gray-700 text-gray-800 dark:text-gray-200`).
5. "Access changed" notice, only when the panel appears because a permission refresh (focus or 403) removed access to the open screen: `InfoIcon` 16px + 14/400 text in a `rounded-lg border border-blue-200 bg-blue-50 text-blue-800 dark:border-blue-800 dark:bg-blue-900/50 dark:text-blue-300 p-3` box (same blue info style as the built-in role banner). Not shown on first load or deep-link.
6. Action row (`flex gap-2`): primary button `Go to {landing label}` (`px-4 py-2 text-sm font-semibold text-white bg-primary-600 hover:bg-primary-700 rounded-lg focus:ring-2 focus:ring-primary-500`). One button only; no secondary action.

Behaviour:
- `Go to {landing}` navigates through `handleSetCurrentView` to the D-06 landing: `dashboard` if the role holds `view:dashboard` (and the screen is on), else the first allowed sidebar item in menu order (ITAM roles land in the ITAM console). The button label uses the manifest label of that view. The same function supplies the post-login view.
- The URL hash is replaced (not pushed) to the landing hash on Go to, so Back does not loop into the panel.
- The panel is derived state, not a route: it re-evaluates on every permission refresh; if access is restored (admin re-grants the permission) the real screen mounts without a click.
- If no landing exists, the in-place panel is never shown; the full-page screen (section 3) takes over.
- While permission state is unknown, show `SkeletonDashboard` instead of the panel, so an allowed user never sees a flash of "no access".
- A failed background refresh (network error) keeps the last known permission set; the gate does not flip to denied on a transient failure.
- Unsaved edits on a screen that becomes blocked are discarded (fail closed). No confirm prompt.

### 3. Full-page zero-access screen (D-07)

Where: replaces the whole authenticated shell (no Sidebar, no Header). Floating widgets (`ChatFab`, `CharacterTourBot`, `InteractiveVoiceBot`, call overlay) and their background fetches do not render or run in this state. Theme follows the stored light/dark preference (`dark` class on the root).

Layout: `min-h-screen flex items-center justify-center bg-[#f8fafc] dark:bg-[#0b1220] p-4`; card `w-full max-w-md` (448px), `bg-white dark:bg-gray-800 border border-gray-200 dark:border-gray-700 rounded-lg shadow-md p-8`, column with `gap-6` (24px).

Anatomy, top to bottom:
1. Brand tile (same as sidebar logo: `bg-gradient-to-tr from-primary-500 to-primary-700 p-2 rounded-lg`, `BotIcon` 24px white) with `branding.companyName` or `Omni-Agent` at 18/600 beside it.
2. Title (24/600, `h1`, `tabIndex={-1}`, focused on mount): `Your role has no screens yet`.
3. Body (14/400): `Ask your administrator to give your role access to at least one screen, then select Retry.`
4. Identity block, `dl` in a `rounded-lg bg-gray-50 dark:bg-gray-700/50 border border-gray-200 dark:border-gray-600 p-4` box, three rows, label 12/400 muted left, value 14/600 right, `truncate` with `title` for long values:
   - `Signed in as` : email
   - `Role` : role display name (`roleLabel`)
   - `Tenant` : tenant name (fall back to tenant id)
5. Status line (below identity, `min-h-[20px]`, `aria-live="polite"`), empty until Retry is used.
6. Action row (`flex gap-2`, stacks to column under 400px): `Retry` (primary, accent, `RefreshCwIcon` 16px left) and `Sign out` (secondary: `border border-gray-300 dark:border-gray-600 bg-white dark:bg-gray-700 text-gray-700 dark:text-gray-200 hover:bg-gray-50 dark:hover:bg-gray-600`, `LogOutIcon` 16px left).

Retry states:
- Idle: `Retry`.
- Pending: button `disabled`, label `Checking...`, icon `animate-spin` (respect `prefers-reduced-motion`: no spin, label alone). Triggers `refreshPermissions` once; ignore repeated clicks.
- Success with screens: the landing view loads automatically; no toast.
- Still nothing: status line (`text-gray-600 dark:text-gray-400`, 14/400) `Still no screens for your role. Last checked {time}.`
- Failure (network/server): status line `text-red-600 dark:text-red-400` with `role="alert"`: `Couldn't check your permissions. Check your connection and try again.`

Sign out: never disabled, never gated by Retry state; calls the existing `logoutSession` flow (same as `handleLogout`). It must work even if Retry is hanging.

### 4. Hidden widgets, tabs and panels (D-08)

- A widget, tab, panel or action button backed by a catalogue the role cannot read is not rendered. No placeholder, no lock icon, no "request access" tile, no empty card, no skeleton.
- The corresponding fetch is skipped (extend the `ifOn` pattern in `loadAllData` to permission checks). A restricted role therefore produces no 403 toast, no error toast and no "Backend connection lost" banner. The red top banner stays reserved for real connectivity loss (network error), never for a 403.
- Layout reflow: remaining widgets fill the existing grid; do not leave a hole or a reserved column. A tab bar with exactly one allowed tab renders that tab's content without the tab bar; with zero allowed tabs the whole screen falls to the in-place panel (section 2).
- If the active tab becomes disallowed after a refresh, activate the first allowed tab, keeping the URL hash on the screen.
- Loading skeletons appear only for allowed widgets.
- **All parts hidden (user decision during UI-SPEC, 2026-10-18):** an allowed screen whose every widget, tab and panel is hidden keeps its title and shows one 14/400 muted line, `Nothing on this screen is available to your role yet.`, plus the in-place panel's `Go to {landing label}` button when the D-06 landing is a different screen. This is a whole-screen guard against a blank page, not a per-widget placeholder (D-08 stands).
- Unexpected 403 from a fetch the client believed allowed: silent. It triggers `refreshPermissions` (ACC-08); the result drives the gate. No toast.

### 5. Role list and custom-role editor (D-01..D-04)

Role list (`SettingsRolesTab.tsx`), table keeps current structure and gains:
- A `Type` chip next to the role name: `Built-in` (`ShieldLockIcon` 12px, neutral outline chip) or `Custom` (neutral filled-light chip: `bg-gray-100 text-gray-700 dark:bg-gray-700 dark:text-gray-200`). Text always visible.
- A `What it can see` button in the Actions cell (see section 6), placed before Edit/Delete: `EyeIcon` 14px + label on `sm` and up, icon-only below `sm` with `aria-label`.
- Edit and Delete icon buttons get `aria-label`: `Edit role {name}` and `Delete role {name}`. Built-in rows: Edit is `aria-disabled` with title `Built-in roles cannot be edited.`; the lock glyph replaces Delete (existing). Custom rows: both enabled when the viewer holds `manage:rbac`; the whole tab is already gated by `canManageRBAC`.
- Empty custom roles are not an empty state (13 built-ins always list). When the tenant has no custom roles, a one-line helper under the table heading (12/400 muted): `No custom roles yet. Built-in roles cannot be edited; create a custom role to tailor access.`
- Row pending states: while a delete is in flight the row is `opacity-60 pointer-events-none` and the trash button shows a 14px spinner; saving a role keeps the row unchanged until the server confirms, then updates in place.

Role editor (`RoleEditorModal`, `Modal size="2xl"`, same form structure), changes only:
- Name field is editable on create only; on edit it is `disabled` with helper text (12/400 muted) `A role's name can't be changed. To rename, create a new role and reassign its users.` (D-13).
- Title unchanged: `Create New Role` / `Edit Role: {name}`. Submit labels unchanged: `Create Role` / `Save Changes`. Pending: button `disabled`, label `Saving...`; Cancel remains enabled; inputs `disabled`.
- Ceiling banner for every non-Super-Admin editor, top of form, blue info style (same as the built-in banner): `You can only grant permissions you hold yourself.` Super Admin sees no banner.
- The permission list is the editor's own effective set with the `manage:X => view:X, request:X` closure applied (server-delivered, replaces the `enabledFeatures` filter). Permissions the editor does not hold are not listed. `PLATFORM_ONLY_PERMISSIONS` and `manage:tenants` are never listed, for anyone.
- Existing permissions on a role that the current editor cannot touch (granted earlier by someone with a higher set): row renders checked and `disabled` with `LockIcon` 12px and `title`/`aria-describedby` text `Your role doesn't include this permission, so you can't change it.`
- Implied permissions: ticking `manage:X` auto-checks the matching `view:X` and `request:X` rows (where those permissions exist), renders them checked and `disabled`, and appends muted helper text `Included with Manage` (12/400) after the label (`aria-describedby` wired to the checkbox). Unticking `manage:X` releases them back to whatever the user had set manually before. Never silently submit implied permissions the user cannot see as checked.
- Label for any permission without a `featureMap` entry: the raw permission string in `font-mono` 12px (no blank labels).
- Name validation (inline under the field, `text-xs text-red-500`, `role="alert"`):
  - Duplicate in the tenant: `A role with this name already exists.` (existing).
  - Collides with a built-in after normalization: `That name matches the built-in role "{built-in name}". Choose a different name.`
- Server rejection (ceiling violation, race, network): keep the modal open, preserve every input, show a `rounded-lg border border-red-200 bg-red-50 text-red-700 dark:border-red-900/50 dark:bg-red-900/20 dark:text-red-300 p-3 text-sm` block with `AlertTriangleIcon` above the footer, `role="alert"`: `Couldn't save the role: {server message}. Your changes are still here, fix the issue and try again.` Fallback when the server gives no message: `Couldn't save the role. Check your connection and try again.`
- Success: close the modal, `showToast('Role "{name}" saved.', 'success')`, list updates in place.
- Built-in roles open nowhere in the editor (Edit stays disabled); inspecting a built-in role is done through the "What it can see" panel.

Delete flow:
1. Trash click opens `ConfirmationModal` with `isDestructive`. Title `Delete role`. Message `Delete the custom role "{name}"? This can't be undone.` Confirm text `Delete role`. Cancel text `Keep role`.
2. Server refuses because users still hold the role (409 with holders): open a `Modal size="md"` titled `Can't delete "{name}" yet`. Body 14/400: `1 user still holds this role.` or `{N} users still hold this role.`, then `Reassign them to another role, then delete it.` When SAML/LDAP group mappings name the role (D-15), a second sub-list follows the holders with the sub-heading `Sign-in mappings` (12/600): per mapping, the directory group name 14/600 over `SAML` or `LDAP` 12/400 muted, same scroll and 50-row rules. Then a scrollable list (`max-h-48 overflow-y-auto`, 192px, `divide-y`, `role="list"`): per holder, name 14/600 (`truncate`) over email 12/400 muted (`truncate`); a holder with no name shows the email as the bold line only. More than 50 holders: show 50 and a final row `and {N-50} more`. Footer: `Close` (secondary) and `Go to User Management` (primary, switches the Settings tab to `users` and closes the dialog). Focus lands on the dialog heading.
3. Success: row removed, `showToast('Role "{name}" deleted.', 'success')`.
4. Other failure: `showToast('Couldn't delete the role: {server message}. Try again.', 'error')` and the row returns to idle.

### 6. "What it can see" panel (D-09, D-10, ACC-07)

Trigger and placement: a `What it can see` button per role row toggles an inline panel rendered as an extra table row (`<tr><td colSpan>`) directly under that role. Button has `aria-expanded` and `aria-controls={panelId}`; chevron (`ChevronRightIcon` 14px, rotates 90deg when open; no rotation transition under `prefers-reduced-motion`). One panel open at a time; opening another closes the first. Opening does not steal focus.

Panel container: `bg-gray-50 dark:bg-gray-900/40 border-t border-gray-200 dark:border-gray-700 p-6` (24px), `role="region"`, `aria-label="What {role name} can see"`, `aria-busy` while loading. Content stacks with `gap-4`.

Header block:
- Summary (18/600): `{Role name} can see {A} of {T} screens`. `A` counts screens marked View or Manage (switched-off ones excluded); `T` is total manifest nav screens.
- Basis line (12/400 muted): `Based on this role's permissions, narrowed by the screens switched on for {tenant name}.` When a Super Admin views a platform role: `Platform role. Tenant screen switches do not narrow it.` and no Switched off section is rendered. When a Super Admin has no tenant selected (D-17): built-in roles show unnarrowed with `No tenant selected. Tenant screen switches do not narrow it.` and no Switched off section; custom roles are not listed until a tenant is selected.
- Legend row (`flex flex-wrap gap-2`): the three markers (View, Manage, Switched off) with a short gloss each in 12/400: `View: can open the screen`, `Manage: can also change data`, `Switched off: granted, but off for this tenant`.
- `Expand all` / `Collapse all` text button (12/600, `text-gray-600 hover:text-gray-900 dark:text-gray-300`, not accent), right-aligned.

Group sections: one per `CATALOGUE_GROUPS` entry in manifest order (8 groups: Dashboards & Insights, Observability, Infrastructure & Assets, Security (SecOps), DevSecOps & Engineering, Governance & Compliance, Automation & Intelligence, Management & Settings). Groups with zero allowed and zero switched-off screens still render collapsed with count `0 of {y}` so the admin sees the gap.
- Group header = full-width button (`aria-expanded`), 12/600 uppercase `tracking-wider`, left: title; right: `{x} of {y}` (12/400) plus, when applicable, an amber count `+{n} switched off` and `ChevronDownIcon` 14px (rotates 180deg open). Default state: all groups collapsed.
- Group body (expanded): grid of allowed screens `grid grid-cols-1 sm:grid-cols-2 xl:grid-cols-3 gap-x-4 gap-y-2`; each cell `flex items-center justify-between gap-2 rounded-md border border-gray-200 dark:border-gray-700 bg-white dark:bg-gray-800 px-3 py-2`: label 14/400 (`truncate`, `title` with full label) and its View or Manage marker at the right. Items in manifest order. Screens the role does not grant are not listed (they only reduce `x`).
- Inside the same group, after the allowed grid, when granted-but-off screens exist: a divider (`border-t border-amber-200 dark:border-amber-900/30 pt-2 mt-2`), sub-heading 12/600 amber text `Switched off for this tenant`, then the same grid with the Switched off marker; labels in these cells use `text-gray-500 dark:text-gray-400`. This is the "listed separately" requirement: it never mixes with the allowed list.
- A screen is Manage when the role (post-closure) holds the manage permission paired with the screen's manifest permission, else View. The marker comes from the server payload, never recomputed client-side (SC3).

Panel states:
| State | Contract |
|-------|----------|
| Loading | Header skeleton (one 24px bar, 60% width) and 3 collapsed-group skeleton bars (`h-10 rounded-lg bg-gray-200 dark:bg-gray-700 animate-pulse`); `aria-busy="true"`. |
| Populated | As above. |
| Role sees nothing | Replace the group list with `This role can't see any screens yet.` plus, for custom roles, a second line `Edit the role to grant permissions.` (button-free). |
| Error | `AlertTriangleIcon` + `Couldn't load what this role can see.` (`text-red-600 dark:text-red-400`, `role="alert"`) and a `Try again` text button (12/600). |
| Cache | Data is cached per role while the panel stays mounted; it refetches after a role save/delete, a permission refresh that changed the set, or a tenant switch. |
| Authorization | The button is shown to anyone who can list roles (`manage:users` or `manage:rbac`) for their own tenant's built-in and custom roles. Platform roles appear in the list only for Super Admin. |

Responsive: panel is full width of the table card; the table already scrolls horizontally (`overflow-x-auto`); the panel row uses `min-w-0` and wraps legend chips. At under 640px the grid is one column and the group-count text wraps below the title.

### 7. Permission refresh on focus and 403 (ACC-08) — visual contract

- Silent. No spinner, toast or banner when a refresh runs or when it changes nothing.
- A changed set updates the sidebar in place (items appear or disappear; the accordion group containing the active item stays open).
- If the open screen is no longer allowed after a refresh, swap to section 2 with the "Access changed" notice; if nothing is allowed, swap to section 3 (no notice there).
- No notification is shown when access is only added.

## Accessibility and Interaction Notes

- Focus: the in-place heading and the full-page title take focus on mount (`tabIndex={-1}`) so assistive tech announces the state change; visible focus ring on all new controls (`focus:outline-none focus:ring-2 focus:ring-primary-500`; add `focus:ring-offset-2` on light surfaces).
- Contrast: markers and muted text must meet 4.5:1 for 12px text on their surface in both themes; the amber marker pair and the neutral outline marker above are chosen for that. Meaning never relies on color alone (icon plus text on every marker).
- Keyboard: all expanders are real `<button>`s with `aria-expanded`; Esc closes the editor, the confirmation and the refusal dialog (inherited from `Modal`); Tab stays trapped inside open dialogs (inherited).
- Motion: spin, rotate and pulse animations are disabled under `prefers-reduced-motion` (the global rule at `index.css` line 310 covers CSS animation; do not add inline `style` transitions that bypass it).
- Icon-only buttons carry `aria-label`; decorative icons carry `aria-hidden`.
- Live regions: the Retry status line and the role-panel loading state use `aria-live="polite"`; errors use `role="alert"`.
- No emojis anywhere in UI copy.
