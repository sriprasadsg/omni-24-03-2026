## 4. Interaction Flow

### Step-by-step user journey

**Step 0 — Trigger**
User clicks "Bulk Upload Evidence" in the FrameworkDetail header.
Modal opens. All state is reset to empty. Focus moves to the modal's first interactive element (zip file drop zone / click target).

**Step 1 — Select zip file**
User clicks the zip drop zone (or drops a file onto it).
Hidden `<input type="file" accept=".zip">` fires. `zipFile` state is set.
The drop zone transitions from empty state to file-selected state: shows filename + file size + a clear button (×).
No validation happens client-side at this point (validation is server-side only).

**Step 2 — Select manifest JSON**
User clicks the manifest file picker.
Hidden `<input type="file" accept=".json">` fires. File is read with `file.text()`.
`JSON.parse()` is attempted.
- If parse fails: `manifestParseError` is set; error shown inline below the picker. `manifest` stays empty.
- If parse succeeds and result is an array: `manifest` is set; `manifestFileName` is set. Preview section renders immediately.
- If parse succeeds but result is not an array: treated as parse error.

**Step 3 — Preview**
Preview section renders when `manifest.length > 0`.
Shows a scrollable list (max-height ~200px, `overflow-y-auto`) with one row per manifest entry: `{filename} → {control_id}`.
User can review mappings before submitting. No inline editing in this phase — if the manifest is wrong, user closes, edits the JSON file, and re-selects.

**Step 4 — Submit**
"Upload Batch" button is enabled only when `zipFile !== null && manifest.length > 0 && !uploading`.
On click: `uploading = true`, all error/success state cleared.
`uploadBulkEvidence(zipFile, manifest)` is called (FormData multipart POST).

**Step 5a — Validation failure (HTTP 422)**
API returns `{ detail: { errors: [...] } }`.
`validationErrors` state is populated.
`uploading = false`.
Error section renders (see Section 6).
Modal stays open. User can fix the zip/manifest and re-submit.

**Step 5b — Fatal error (HTTP 400, 413, 500, network)**
`fatalError` state is set to the appropriate copy from the Copywriting Contract.
`uploading = false`.
Fatal error banner renders (see Section 6).

**Step 5c — Success (HTTP 200)**
`successResult` is set with `{ committed, batch_id }`.
`uploading = false`.
`onUploaded()` callback fires — FrameworkDetail refreshes evidence.
Success summary renders (see Section 7).
Submit button is hidden. "Close" button label replaces "Cancel".

## 5. Manifest Format

The manifest is a JSON file the auditor prepares before uploading. It is a flat array; each object maps one filename (exactly as it appears in the zip) to one control ID.

### Schema

```json
[
  { "filename": "access-policy.pdf", "control_id": "CC6.1" },
  { "filename": "training-certs.xlsx", "control_id": "CC9.1" },
  { "filename": "vendor-nda.docx", "control_id": "CC2.2" }
]
```

### Rules (communicated in the UI format hint)

- `filename`: the filename as it appears at the root of the zip (no directory path). Example: `"report.pdf"`, not `"docs/report.pdf"`.
- `control_id`: the exact control ID string (e.g., `"CC6.1"`, `"A.8.1"`).
- One file can map to multiple controls by repeating the entry with different `control_id` values.
- Array must be non-empty.
- Maximum 50 entries.

### Frontend validation (client-side, pre-submit)

The frontend performs only structural parsing (is it a non-empty array? does each entry have `filename` and `control_id` keys?). It does not validate control ID values exist in the framework — that is backend responsibility.

If client-side structural check fails, `manifestParseError` is set and "Upload Batch" remains disabled.

## 8. Accessibility

### ARIA Labels

| Element | aria attribute | Value |
|---------|---------------|-------|
| Modal overlay | `role="dialog"` | — |
| Modal overlay | `aria-modal="true"` | — |
| Modal overlay | `aria-labelledby` | ID of the `<h3>` heading |

| Manifest file picker trigger | `aria-label` | `"Select manifest JSON file"` |
| Submit button | `aria-label` | `"Upload Batch"` (inherits button text) |
| Submit button (uploading) | `aria-busy="true"` | — |
| Error section | `role="alert"` | Announces errors to screen readers immediately |
| Success section | `role="status"` | Announces success to screen readers |
| Per-file error list | `aria-label` | `"Validation errors"` |

### Keyboard Navigation

- Modal opens: focus moves to the modal container `<div>` (via `autoFocus` or `useEffect` focus call on the first interactive element).
- Tab order: Close (X) → Zip drop zone → Manifest picker → Preview list (inert, no tab stops) → Submit button → Cancel button.
- `Escape` key: closes the modal (calls `onClose()`). Only active before a successful upload; after success `Escape` calls `onClose()` as well (same as clicking "Close").
- Drop zone `onKeyDown`: `Enter` or `Space` triggers the hidden file input click.
- Manifest picker `onKeyDown`: same.

### Screen Reader Announcements

- When `validationErrors` is set, the error container has `role="alert"`. No `aria-live` needed — role="alert" implies live="assertive".
- When `successResult` is set, the success container has `role="status"` (live="polite").
- Spinner during upload: `aria-label="Uploading"` on the `<svg>` spinner element.

### Focus Management

- On modal open: focus the close (X) button or the zip drop zone (first interactive element after the heading).
- On modal close: return focus to the "Bulk Upload Evidence" trigger button in `FrameworkDetail`. Use a `useRef` to store the trigger element and call `.focus()` in `onClose`.
- After validation errors render: do not move focus automatically (the `role="alert"` handles announcement). User can tab to the error list if needed.
- After success renders: focus the "Close" button automatically (modal's final state has only one action).

## 9. API Contract Summary

### Endpoint

`POST /api/compliance/evidence/bulk`

Authentication: JWT bearer token via `authFetch` (same as all other compliance endpoints).

### Request

`multipart/form-data` — **no explicit `Content-Type` header set by the client**; browser sets boundary automatically (project decision T-02-07 in STATE.md).

| Field | Type | Description |
|-------|------|-------------|
| `zip_file` | `File` (binary) | The zip archive containing evidence files |
| `manifest` | `string` | JSON-serialized array of `ManifestEntry` objects |

### Success Response (HTTP 200)

```json
{
  "success": true,
  "committed": 3,
  "batch_id": "a3f8c2d1e0b94f7...",
  "evidence": [
    {
      "id": "cev-bulk-{hex}",
      "name": "access-policy.pdf",
      "url": "/static/evidence/{uuid}.pdf",
      "type": "application/pdf",
      "uploadedAt": "2026-06-22T10:00:00+00:00",
      "controlId": "CC6.1",
      "source": "manual",
      "bulk_batch_id": "a3f8c2d1e0b94f7..."
    }
  ]
}
```

Frontend uses: `committed` (success count display) and `batch_id` (batch ID display). The `evidence` array is not rendered in the modal but is available for future use.

### Validation Failure Response (HTTP 422)

```json
{
  "detail": {
    "errors": [
      { "filename": "access-policy.pdf", "error": "File content does not match extension" },
      { "filename": "training-certs.xlsx", "error": "File exceeds 25 MB limit" }
    ]
  }
}
```

Frontend extracts: `err.detail.errors` as `BulkError[]`.

### Fatal Error Responses

| HTTP Status | `detail` | Frontend copy |
|------------|---------|--------------|
| 400 | `"Uploaded file is not a valid zip"` | "The selected file is not a valid zip archive. Select a .zip file and try again." |
| 400 | `"Manifest exceeds 50 entries"` | "Manifest exceeds 50 entries. Split the batch and upload separately." |
| 413 | `"Zip file exceeds 200 MB limit"` | "Zip file exceeds the 200 MB limit. Reduce the batch size and try again." |
| 500 | any | "Upload failed. Please try again. If the problem persists, contact support." |

Frontend catches all non-200 non-422 responses and maps them to `fatalError` state using the above copy. If `detail` string matches a known pattern, use the specific copy. Otherwise fall back to the generic 500 copy.

### Frontend API Function (to add in `services/apiService.ts`)

```typescript
export interface ManifestEntry {
  filename: string;
  control_id: string;
}

export interface BulkUploadResult {
  success: boolean;
  committed: number;
  batch_id: string;
  evidence: any[];
}

export const uploadBulkEvidence = async (
  zipFile: File,
  manifest: ManifestEntry[]
): Promise<BulkUploadResult> => {
  const formData = new FormData();
  formData.append('zip_file', zipFile);
  formData.append('manifest', JSON.stringify(manifest));
  // No Content-Type header — browser sets multipart boundary automatically (T-02-07)
  const res = await authFetch(`${API_BASE}/compliance/evidence/bulk`, {
    method: 'POST',
    body: formData,
  });
  if (!res.ok) {
    const body = await res.json().catch(() => ({}));
    const err = new Error('Bulk upload failed') as any;
    err.status = res.status;
    err.detail = body.detail;
    throw err;
  }
  return res.json();
};
```
