## Defect Analysis for Plan 13-02

### Defect 1: asyncio Event-Loop Ordering Bug

**Root cause:** Python 3.12 `asyncio.run()` creates a new event loop, runs the coroutine, then **removes** the current event loop from the thread. `asyncio.get_event_loop()` called subsequently returns a fresh loop in Python 3.10+, but by Python 3.12 this is deprecated and raises `RuntimeError: There is no current event loop in thread 'MainThread'` when no policy-backed loop exists.

**Evidence:** Live test run confirms exactly 5 failures with `RuntimeError` when `test_scheduled_reports.py` runs first:
```
FAILED tests/test_compliance_narrative_service.py::TestGenerateExecutiveSummary::test_returns_str_on_success
FAILED tests/test_compliance_narrative_service.py::TestWordBudget::test_trims_to_150_words
FAILED tests/test_compliance_narrative_service.py::TestFallbackOnError::test_returns_fallback_on_error_prefix
FAILED tests/test_compliance_narrative_service.py::TestFallbackOnBlocked::test_returns_fallback_on_blocked_prefix
FAILED tests/test_compliance_narrative_service.py::TestFrameworkNarrative::test_framework_narrative_within_200_words
```

**Lines to change:** 38, 63, 85, 110, 165 in `test_compliance_narrative_service.py` — each reads `asyncio.get_event_loop().run_until_complete(run())`.

**Fix:** Replace with `asyncio.run(run())`. This creates a new event loop per call — identical outcome, but each call is isolated from prior event-loop state. No assertion logic, mock setup, or test class structure changes needed.

**Note on review concern [MEDIUM]:** The 13-REVIEWS.md originally flagged `asyncio.run()` vs `get_event_loop()` as a potential "loop is closed" edge case and suggested standardising to `get_event_loop()`. The live test run proves the opposite: `get_event_loop()` is what breaks in Python 3.12 cross-test scenarios. Plan 13-02 correctly overrides this suggestion and uses `asyncio.run()`. The 3 sync tests (TestSanitise, TestNarrativeOutput, TestBuildPdfIntegration) are unaffected — they have no event loop calls.

**Docstring update needed:** Line 4 currently reads `Pattern: asyncio.get_event_loop().run_until_complete() + AsyncMock (NO pytest-asyncio).` — update to reflect `asyncio.run()`. Line 5 refers to the RED phase — update to reflect that all tests now pass GREEN with `asyncio.run()`.

### Defect 2: 500-Line CLAUDE.md Violation

**Root cause:** `scheduled_reports_service.py` is 539 lines. The overage (39 lines) comes from Phase 13-01 additions (try/except import guard: +4 lines, framework_id gate: +1 line, `_render_narratives` calls: +2 lines, skip set expansion: +1 line) plus earlier organic growth. No `_process_due_schedule` helper exists — the `start_report_scheduler` for-loop body (lines ~511-536) is inline.

**Fix:** Extract the for-loop body inside `start_report_scheduler` into a new `async def _process_due_schedule(schedule: Dict[str, Any], db) -> None` defined just before `start_report_scheduler`. Replace the loop body with a single `await _process_due_schedule(schedule, db)` call. This removes ~23 lines from `start_report_scheduler` and adds ~28 lines for the helper function, but the indentation reduction in the loop saves enough to bring the total to ≤ 500 lines.

**Behaviour preservation:** All existing functionality must remain identical — the extracted body includes the inner try/except Exception that catches per-schedule failures and writes delivery logs without propagating to the scheduler outer loop.

## Common Pitfalls

### Pitfall 1: Editing Async Tests Without Running in Both Orderings

**What goes wrong:** The event-loop bug only manifests when `test_scheduled_reports.py` runs before `test_compliance_narrative_service.py`. Running in narrative-first order always passes (even with the broken pattern), which can create a false sense that the fix is unnecessary or complete.

**How to avoid:** Always verify in both orderings after Task 1:
- `pytest tests/test_scheduled_reports.py tests/test_compliance_narrative_service.py`
- `pytest tests/test_compliance_narrative_service.py tests/test_scheduled_reports.py`

### Pitfall 2: Breaking Phase 13 Integration Points During Line-Count Reduction

**What goes wrong:** The for-loop body in `start_report_scheduler` contains the inner try/except that catches per-schedule failures. If the extraction accidentally moves the try/except to the outer scope, a single failed schedule would abort the entire scheduler loop rather than continuing to process remaining due schedules.

**How to avoid:** The extracted `_process_due_schedule` must include the inner try/except. The outer `try/except Exception` in `start_report_scheduler` (around the full while-loop body) must remain untouched.

### Pitfall 3: Changing the try/except ImportError Guard

**What goes wrong:** The try/except ImportError guard at lines 20-24 of `scheduled_reports_service.py` defines fallback no-op functions for `enrich_report_data` and `_render_narratives`. If this guard is accidentally removed during the line-count reduction edit, a broken `compliance_narrative_service` import would take down all scheduled reports.

**How to avoid:** Plan 13-02 Task 2 reads the full file first. The guard is in the imports block (lines 20-24) — well above the `start_report_scheduler` function at line 498. The extraction only touches the for-loop body inside `start_report_scheduler`.

### Pitfall 4: Counting Affected Lines Incorrectly

**What goes wrong:** The 13-01-SUMMARY.md says 508 lines but `wc -l` currently shows 539. The extraction needs to reduce to ≤ 500. The savings come from removing the indented try/except block from inside the for-loop and replacing it with a single-line call — the helper definition adds lines but at the function (not loop) level.

**Expected arithmetic:** Current 539 lines. The for-loop body (approximately lines 512-536 = ~25 lines) is replaced by 1 line (`await _process_due_schedule(schedule, db)`). The helper function adds approximately 28 lines (docstring + try/except body). Net change: 1 - 25 + 28 = +4 lines from 539 = 543? That exceeds 500. Re-check: the actual indentation level reduction (4 levels to 1 level) and re-examining what the helper body actually requires in lines is critical. Read the actual file before editing to count correctly.

**How to avoid:** Read the full `scheduled_reports_service.py` first, count the exact for-loop body lines (from `for schedule in due_schedules:` to the end of the inner `except` block), verify that the helper extraction arithmetic lands at ≤ 500.

### Pitfall 5: asyncio.run() Inside an Already-Running Loop

**What goes wrong:** `asyncio.run()` raises `RuntimeError: This event loop is already running` if called inside a coroutine or when an event loop is already active (e.g., in Jupyter or some async test frameworks). For standard pytest (non-asyncio mode), there is no running event loop in the test collection/execution thread, so `asyncio.run()` is safe.

**How to avoid:** The project uses standard pytest without `asyncio_mode` (confirmed by the `PytestConfigWarning: Unknown config option: asyncio_mode` warning in the test output). `asyncio.run()` is correct for this environment.
