# Phase 84 — UI Design Contract

> Visual and interaction contract for Staged Patch Rollouts: (1) a new **Rollouts** tab on the Patching screen (rollout list, ring detail, halt block, Resume and Cancel, `Rollout rings` settings, the Start rollout dialog); (2) a **rollout approval card** inside `Needs your decision` on the Autonomous Ops screen (Install line and Reboot line, one Approve and Deny each); (3) Activity-row copy for canary installs and reverts; (4) the **Maintenance windows** rework in Settings (time zone, windows past midnight); (5) a read-only **Maintenance windows** list in Change Management; (6) a ring chip on Agent Groups; (7) the `Draft a rollout` link on the Phase 83 vulnerability suggestion. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Locked inputs: 84-CONTEXT.md D-01..D-18. Nothing here re-opens them. Details the context left open are recorded as researcher defaults in "Assumptions Recorded" (IDs R1..R16); the planner treats them as decided unless the user overrules.
> Extends, does not replace, `81-UI-SPEC.md`, `83-UI-SPEC.md` and `87-UI-SPEC.md`: tokens, the four-size and two-weight type scale, the spacing scale, chip anatomy and tones, `.card`, `Modal` conventions, `EmptyStateCard`, the decision-card anatomy (83 section 2a), the stop and shadow rules and the 900 px table budget are inherited as written. Only deltas are declared here.
> New infrastructure: none. No new library, token, colour or chip tone. Files read for this contract: `components/PatchManagementDashboard.tsx`, `OsPatchesTab.tsx`, `MaintenanceWindowConfig.tsx`, `ChangeManagementDashboard.tsx`, `AgentGroupsDashboard.tsx`, `AutonomousOpsActivity.tsx`, `AutonomousOpsDecisions.tsx`, `Modal.tsx`, `icons.tsx`, `shared/catalogue-access.json`, `shared/autonomous-ops-banned-terms.json`.

## Spacing Scale

Inherited unchanged from 81-UI-SPEC (4, 8, 16, 24, 32, 48; 64 unused). Phase 84 usage:

| Token | Tailwind | Usage in this phase |
|-------|----------|---------------------|
| xs 4px | `1` | Icon-to-text gap in chips and buttons, gap between a title and its meta line |
| sm 8px | `2` | Gap between chips, between Approve and Deny, between stacked helper lines, between checkbox rows |
| md 16px | `4` | Line padding (`px-6 py-4`), ring block padding, gap between ring blocks, form row gap |
| lg 24px | `6` | Card padding (`p-6`), gap between rollout cards, dialog gaps |
| xl 32px | `8` | Empty-state card padding (unchanged) |
| 2xl 48px | `12` | Empty-state icon circle (unchanged) |

Exceptions (all multiples of 4):
- `Start rollout`, `Approve`, `Deny`, `Resume rollout`, `Cancel rollout`, `Save rings`, `Save window` and every dialog confirm are `min-h-10` (40px, `px-4`), the same consequential-control rule as Stop and Approve.
- Checkbox and patch-picker rows are `min-h-10` (40px) so the whole row is the hit area; the checkbox box itself is `h-4 w-4` (16px).
- Ring remove, move up and move down buttons: `h-8 w-8` (32px hit area) with a 16px icon.
- Number inputs (soak hours, failure share, minimum hosts) `w-24` (96px); time inputs `w-32` (128px); name inputs `w-full max-w-sm`.
- Host table column minimums: Host 200, State 150, Result 300, Changed 150 = 800px, inside the 900px budget (87 amendment), so the table fits 1280px with the sidebar open; below `lg` rows become stacked cards with `dl` rows.
- Ring blocks in the ring strip: `min-w-[200px] flex-1`, four rings fit one row at 1280px with the sidebar open (4 x 200 + 3 x 16 = 848px of 874px content width).
- No half-steps in new elements.

## Color

Inherited from 81, 82 and 83: dominant `--bg-main`, secondary `.card` surface, accent `primary-600`, destructive `red-600`, amber warning, blue info, neutral text. 60/30/10 unchanged: the tab, cards and dialogs are `.card` or `Modal` surfaces on the page canvas; accent stays small.

No tone is added. Phase 84 meanings map onto the existing chips (chip anatomy and classes from 81: icon 12px `aria-hidden` plus visible text):

| Meaning | Chip | Tone and icon |
|---------|------|---------------|
| Waiting for a person (approval), waiting for the window, a signal not in yet | `Waiting for approval`, `Waiting for window`, `Waiting` | AMBER, `ClockIcon` (the Pending anatomy) |
| In progress (installing, restarting, soaking, checking health) | `Installing`, `Restarting`, `Soaking`, `Checking health` | BLUE, `RefreshCwIcon` (the Suggested anatomy used for "in progress"; see R6) |
| Passed, installed, healthy, completed | `Passed`, `Installed`, `Healthy`, `Completed` | GREEN, `CheckCircleIcon` |
| Halted, install or check failed, no data | `Halted`, `Failed`, `No data` | RED, `XCircleIcon` (`AlertOctagonIcon` on the rollout-level `Halted` chip) |
| Put back | `Reverted` | NEUTRAL, `RefreshCcwIcon` |
| Ended by a person, not started yet | `Cancelled`, `Not started` | NEUTRAL (Undone anatomy), `XCircleIcon` for Cancelled, `ClockIcon` for Not started |
| Could not be put back, left out, offline the whole ring | `Not reverted`, `Left out`, `Not reached` | OUTLINE, `ShieldLockIcon` for Not reverted, `InfoIcon` for Left out, `ClockIcon` for Not reached |
| Shadow mode | `Simulation` | dashed chip, `FlaskConicalIcon` (81) |

Accent reserved for (the 81 list items 1 to 4, the 82 item 5 and the 83 items 6 to 9 stand; Phase 84 adds exactly four):
10. `Approve` on a rollout approval line (the 83 item 6 rule applied to the new card).
11. `Start rollout`: the Rollouts tab header button and the Start dialog's confirm. The one affirmative action of the tab.
12. The confirm of `Resume this rollout?` (`Resume rollout`), the same pattern as `Resume automatic actions`.
13. `Save rings` and `Save window` when the form has unsaved changes.

Accent is NOT used for: `Deny`, `Cancel rollout`, `Draft a rollout`, `Review in Needs your decision`, `Show hosts`, `Show health check`, `Add ring`, `Add window`, `Discard changes`, any chip, any countdown, or section headings.

Destructive red (button) is used in this phase for exactly two confirms, both of which cannot be taken back: `Cancel rollout` (ends the rollout for good) and `Delete window` (removes a window). Red also marks the `Halted`, `Failed` and `No data` chips, inline error text and error blocks. Nothing else in the phase is red. Blockers that stop a start (no window, no canary host) are amber `role="status"` blocks, not red: they are a to-do, not a failure.

Meaning never relies on colour alone: every chip carries an icon and visible text; a disabled button carries a visible reason line referenced by `aria-describedby`; the ring strip states the state in words.

## Screens and States

### 1. Placement and routing

| Surface | Where | Permission |
|---------|-------|------------|
| Rollouts tab, ring settings, Start rollout | Patching screen (`patchManagement`), a **new tab `Rollouts`** (order below) | view: `view:patching`; start, rings, Resume, Cancel: the server flags `canStart`, `canManageRings`, `canResume`, `canCancel` (backed by the `manage:patches` write permission) |
| Rollout approval card | Autonomous Ops screen, inside the existing `Needs your decision` section | the server flags `canApprove`, `canDeny` (approve-tier permission with MFA, 81 D-05 and D-07) |
| Maintenance windows (time zone, overnight) | Settings, `Maintenance` tab (existing `MaintenanceWindowConfig`) | existing `canManageSettings` gate |
| Windows list, read-only | Change Management screen | the screen's existing view permission |
| Ring chip | Agent Groups screen | the screen's existing permission |

Tab order on Patching becomes `Patches & Deployment`, `Software Updates`, `OS Patches`, `Rollouts`, `Agent Approvals` (Rollouts sits beside OS Patches because that is where pending updates are listed). Label `Rollouts`, no emoji (the older tab labels keep theirs; new copy does not add any). The tab badge counts rollouts waiting for a person (`Waiting for approval` or halted needing Resume or Cancel), amber classes like the existing `approvals` badge, hidden at zero.

No new sidebar entry. Route group `/api/patch-rollouts` (planner's name) is registered in `shared/catalogue-access.json` under the existing `patchManagement` view (`routes` and `write`), and in a `catalogue_mounts_*.py` slice, or drift tests fail.

Platform organization (81 D-04, 84-CONTEXT carried forward): the Rollouts tab renders a single `EmptyStateCard` (no buttons): heading `Rollouts aren't available for the platform organization`, body `Patches are never rolled out to the platform's own server. Open a customer organization to start a rollout.` (R1)

**Visual anchor (focal point).** On the Rollouts tab the anchor is the first rollout card that needs a person (halted, or waiting for approval), else the first running rollout, else the `Start rollout` header button. The window strip sits above the list but is one quiet line; the `Rollout rings` card is collapsed and below the list so it never outranks a rollout. A halt block (red) is the loudest element and is always inside its rollout card, never a page banner. On Autonomous Ops the app-wide stop banner and watchdog banner still outrank everything (81).

### 2. Rollouts tab

Top to bottom: tab header row, assurance line, window strip, rollout list, `Rollout rings` card.

**Header row** (`flex flex-wrap items-center justify-between gap-4`): left `h2` 18/600 `Rollouts` with a 14/400 muted line `Install patches in rings: a small canary group first, then larger groups. Each ring waits and is health-checked before the next one starts.`; right, when `canStart`, the accent button `Start rollout` (`min-h-10`, `RocketIcon` 16px left). Without `canStart`: no button and one 12/400 muted line `Ask someone with patching access to start a rollout.`

**Assurance line** (12/400 muted, `InfoIcon` 12px, always visible, one line so the banned-term check sees "where supported" on it): `A rollout halts on failure; reverts where supported. Nothing is installed outside your maintenance window.` This exact sentence also opens the halt block (section 4) and the Start dialog (section 3).

**Window strip** (`.card p-4 flex flex-wrap items-center gap-4`): one row.
- Window open: GREEN chip `Window open` + 14/400 `Closes at {HH:MM} ({time zone}).`
- Window closed: OUTLINE chip `Window closed` + 14/400 `Next window opens {Day D Mon, HH:MM} ({time zone}).`
- No windows (D-03): amber block (`AlertTriangleIcon`, `role="status"`) `Add a maintenance window first.` with link `Open maintenance windows` (14/600 underline; navigates to Settings, Maintenance tab; the link renders as plain text if the viewer cannot open Settings). Start is disabled in this state with the same words in its reason line.
- Right: `Time zone: {IANA name}` in 12/400 mono. No zone set yet: 12/400 muted `No time zone set. Windows use UTC.` (R3)

**Rollout list.** `<section aria-labelledby>` of `.card` rollout cards (section 4), `space-y-6`. Ordering: halted first, then waiting for approval, then running, then waiting for window, then finished (Completed, Cancelled) newest first. Finished rollouts older than 30 days are not listed (the activity ledger keeps the record; R7). Paging: 10 cards, then a secondary `Show more rollouts` button (`min-h-10`, pending `Loading...`).

Data: one fetch on mount of the tab, every 30 s while the tab is visible, on focus, on `Refresh` (the existing refresh icon in the tab header), and immediately after Start, Resume or Cancel. Polling pauses when the tab is hidden or the Rollouts tab is not the active tab. The payload carries `shadow` and `stopped` flags so the tab does not depend on the Autonomous Ops status context (a Patching-only role has no access to it). A background poll shows no skeleton and no spinner and a failed poll keeps the last cards.

Tab states:

| State | Contract |
|-------|----------|
| First load | Three `h-24` skeleton cards in `.card`, `aria-busy="true"` on the section. |
| No rollouts, rings not set up | `EmptyStateCard`: heading `No rollouts yet`, body `Set up your rings, then start a rollout from the patches your computers are waiting for.` CTA (with `canStart`): `Start rollout`. |
| No rollouts, rings set | heading `No rollouts yet`, body `Pick the patches your computers are waiting for and roll them out ring by ring.` CTA `Start rollout`. |
| Populated | Cards as above. |
| Error (first load) | Red block (`AlertTriangleIcon`, `role="alert"`): `Couldn't load rollouts. Check your connection and try again.` with `Try again`. |
| Error (background poll) | Keeps the last cards, shows nothing new. |
| Stopped | Amber block (`PauseCircleIcon`, `role="status"`) above the list: `Rollouts are paused while automatic actions are stopped. Nothing new installs or restarts. A revert that is already under way still runs.` (platform variant: `... stopped for the whole platform. ...`). `Start rollout` is disabled with reason line `Paused while automatic actions are stopped.`; Resume stays enabled (it re-runs a check, it does not install). |
| Shadow mode | Blue block (`FlaskConicalIcon`, `role="status"`): `Shadow mode is on for this organization. A rollout runs as a simulation: it records what it would have done and installs and restarts nothing.` Rollouts started while it is on carry the `Simulation` chip in the header and ring text reads `Would install` and `Would restart`. |
| Live region | One visually hidden `role="status"` announces `{n} rollouts need your attention` only when the count rises after a background poll; never on first load. |

### 3. Start rollout dialog (D-03, D-09..D-13)

`Modal size="2xl"`, `showClose={false}`, `closeOnBackdrop={false}`, Esc closes unless a request is in flight. Title (18/600) `Start a rollout`. Initial focus on the name input. Body `gap-6`, scrolls inside the modal (`max-h-[90vh]` is the Modal's). Footer: `Cancel` (secondary) left, `Start rollout` (accent, pending `Starting...`) right.

Sections, in order:

1. **Name.** Label 14/600 `Rollout name`; input `w-full max-w-sm`, 1 to 60 characters, default `Rollout {D Mon}`; helper 12/400 muted `Shown in the list and when a computer is left out of another rollout.` Validation `Enter a name for this rollout.`

2. **Patches.** Label 14/600 `Patches to install`; helper 12/400 muted `These are the updates your computers are waiting for.` A list (`ul`, `divide-y`, `max-h-72 overflow-y-auto` inside a bordered rounded box) of checkbox rows (`min-h-10`): mono patch id 12/400, title 14/400 `break-words`, OS chip (OUTLINE, `WindowsIcon` or `LinuxIcon`, text `Windows` or `Linux`), and 12/400 muted `{n} computers`. Above the list: a `Search patches` input (`SearchIcon`, `aria-label`) and a counter `{k} selected`. Paging: first 50, then secondary `Show more patches`. Zero patches pending: `EmptyStateCard`-lite text `Nothing is waiting to be installed.` and Start stays disabled with that reason. Only patches that exist on at least one eligible computer are listed; computers of other operating systems are not offered (Windows and Linux only, 83 D-20).

   **Draft state (D-11).** Opened from the vulnerability suggestion link, the dialog starts with the matching patches ticked, the name set to `Patches for {CVE id or "vulnerabilities"} on {host}` and a blue info block (`InfoIcon`) at the top: `Filled in from the vulnerabilities reported by {host}. Nothing starts until you press Start rollout.` The draft exists only in the dialog; the platform stores no rollout until the operator presses Start (R9). If a suggested patch is no longer pending, it is dropped and the block adds `{k} patches are no longer needed and were removed.`

3. **Check before starting** (`role="status"`, `aria-live="polite"`, recomputed from the server preflight whenever the selection changes, debounced 300 ms; shows `Checking...` as 12/400 muted while in flight, and keeps the previous result visible so the layout does not jump). One row per check, each with an icon (CHECK green, AlertTriangle amber), a 14/600 title and a 12/400 muted detail:
   - **Window.** OK: `Next window: {Day D Mon, HH:MM} ({time zone}).` Blocker: `Add a maintenance window first.` with link `Open maintenance windows`.
   - **Rings.** OK: `{n} computers in {r} rings: {ring name} {n}, {ring name} {n}.` Blocker, no canary group: `The canary ring has no computers. Pick a group for it in Rollout rings.` with link `Open rollout rings` (closes the dialog and expands the card).
   - **Canary per operating system (D-12).** One row per OS in the selection. OK: `The canary ring has a Windows computer.` Blocker: `The canary ring has no Linux host; add one to the Canary group.` The group name is the canary ring's first group: `add one to the {group} group`; with several groups `add one to a group in the canary ring`. Link `Open agent groups`.
   - **Left out (D-13).** Info row, shown only when it applies, one line per other rollout, first 3 then `and {k} more`: `3 hosts are in "November security" and were left out.` (`1 host is in "..." and was left out.`) with `Show hosts` disclosure listing at most 10 names in mono, then `Showing 10 of {n}.`
   - **Offline now.** Info row when applicable: `{n} computers are offline now. They get the patches in a later window if they come back online.`
   - **Platform server.** Never listed as a row (it is never offered); the info block below states the rule.

4. **What will happen** (blue info block, `InfoIcon`, 14/400, a short `ul` of four lines): `Installs and restarts run only inside your maintenance window.` / `Only the canary ring installs on its own, and only patches that can be reversed on that computer. That is checked just before each install.` / `Every other install and every restart waits for your approval, one ring at a time.` / `{assurance line}` (`A rollout halts on failure; reverts where supported.`). Then 12/400 muted: `The platform's own server is never patched by a rollout.`

Button state: `Start rollout` is disabled while any blocker shows, while name is invalid, while no patch is ticked, during a stop (reason line `Paused while automatic actions are stopped.`) and while the preflight is loading the first time. The disabled button has `aria-describedby` pointing at a visually visible reason line (the first blocker's text). Failure: red block above the footer (`role="alert"`): `Couldn't start the rollout: {server message}. Try again.` Fallback `Couldn't start the rollout. Check your connection and try again.` A 409 `already_in_rollout` (a race with another rollout) refreshes the preflight and shows the Left out row. Success: dialog closes, toast `Rollout "{name}" started. The canary ring goes first.` (shadow variant: `Rollout "{name}" started as a simulation. Nothing will be installed.`), list refetches, focus moves to the new card (`tabIndex={-1}`).

Entry points to the same dialog: `Start rollout` in the tab header; a secondary `Roll out in rings` button added to the `OS Patches` tab header row beside Refresh, which switches to the Rollouts tab and opens the dialog; `Draft a rollout` from the Phase 83 suggestion (section 9). The existing per-computer `Deploy All` button is unchanged (a single-host manual deploy, not a rollout).

### 4. Rollout card (PTCH-01..05, D-14..D-18)

Shadow variant: `Waiting for approval` never occurs (no cards exist); detail lines read `Would install on {n} computers.` and `Would restart {n} computers.` and the soak line runs on the simulated clock the server supplies.

When a ring waits for approval the strip block adds, under the detail line, the link `Review in Needs your decision` (14/600 underline, `ExternalLinkIcon` 12px), navigating to `autonomousOps` (the Patching screen gets an `onOpenView` prop from `App.tsx`, as 83 did for suggestions). **Ring detail disclosure** (per ring, text button `Show details` / `Hide details`, 14/600, `aria-expanded`, `ChevronRightIcon` that rotates, under the ring block). Destructive actions in this phase, and the confirmation approach for each:
- **Approve** an install or a restart: one click by design (the 83 approval-card rule). Safeguards instead of a dialog: the consequence and the window timing are printed on the line before the click, each line has its own single-use decision, there is no approve-all, the button names its target and rollout in `aria-label`, MFA is required server-side, and the action is recorded in the ledger and audit chain.
- **Cancel rollout**: dialog above (ends the rollout, cannot be restarted).
- **Delete window**: dialog above (red confirm; extra amber block for the last window).
- **Resume rollout**: dialog with a required typed reason (D-16).
- Not destructive: Deny, Start rollout (the preflight and the info block state what will happen; nothing installs until the window and, outside the canary, an approval), Save rings, Save window.
