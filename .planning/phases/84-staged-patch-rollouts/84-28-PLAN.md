<objective>
Close WR-03's second half: a running rollout cannot be cancelled (cancel requires halted), so an operator has no way out of a stuck or unwanted rollout.

Key decision KD-84-G3 (corrected, follows locked D-16): Cancel on a running rollout stops the rollout without reverting anything. It stamps `cancelRequested` {by, at} with a compare-and-set on status running, closes the rollout's open and approved-not-sent rows, and ends instructions no computer has fetched. From then on the controller only settles the work already on the computers (installs and restarts in flight) and decides nothing new; it runs no ring verdict, so no halt and no revert can follow. Once no host is installing or restarting, and at the latest RESULT_DEADLINE (84-27) after the request, it runs the existing cancel completion: status cancelled, rings that did not pass cancelled, claims released, cancelledBy = the requester. Hosts already patched keep their patches (D-16). D-14/D-15 reverts follow only a FAILED ring, and the halted-rollout path (84-16 revert, 84-18 Cancel) is unchanged. An earlier draft of this plan reverted the in-flight ring on Cancel, following an orchestrator gap_scope note that contradicted D-16; that draft is withdrawn. Record the corrected KD-84-G3 in the SUMMARY key-decisions. Reversibility: reversible (server code only, one additive rollout field).

Output: lifecycle and controller change, route summary, Resume refusal while cancelling, server flag and sentences, Cancel dialog text, tests. UI-SPEC DEV-1..DEV-4 are not touched.
</objective>
