# Phase 43 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase adds one action ("Create Ticket") and one read-only display block to an existing, already-styled modal (`components/RemediationTaskModal.tsx`), and reads provider-availability data already exposed by the existing `GET /api/ticketing/config` endpoint. It is not a new page, route, or nav entry. Per 43-RESEARCH.md's phase brief, this contract **reuses the project's existing manual-Tailwind design system verbatim** — every value below is sourced directly from `RemediationTaskModal.tsx`/`RemediationDashboard.tsx` (the exact file being modified and its parent dashboard), `AddCloudAccountModal.tsx` (closest structural analog for a radio-style provider picker), and `utils/toast.ts`/`showToast` (the codebase's one established async-failure notification pattern, used identically by `AddCloudAccountModal.tsx`, `RemediationTaskModal.tsx`, and `RemediationDashboard.tsx` today).

**shadcn gate note:** No `components.json` detected; the project has 500+ hand-built Tailwind components and no Radix/shadcn primitives anywhere in the tree (confirmed via `ls components.json tailwind.config.* postcss.config.*` — only the plain Tailwind/PostCSS configs exist). Per the phase brief's explicit instruction to reuse the existing dashboard's Tailwind design system rather than introduce new tokens, and because this is a single button + inline picker + read-only display block added to one existing modal (not a new page/surface), shadcn initialization was not proposed to the user for this phase — introducing a component-library dependency for one modal addition would contradict the phase's own scope instruction, and would be visually inconsistent with the modal's 25+ surrounding hand-rolled fields. `Tool: none` is a deliberate, scoped decision, not an unanswered gate. This mirrors the identical decision already made and approved for Phase 42 (`42-UI-SPEC.md`), the most recent sibling UI phase in this milestone.

## Spacing Scale

Declared values (must be multiples of 4) — all sourced from `RemediationTaskModal.tsx`/`AddCloudAccountModal.tsx`, no new values introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps (`gap-1`), spinner sizing |
| sm | 8px | Compact element spacing (`gap-2`, `p-2`, `p-2.5`), input padding |
| md | 16px | Field group spacing (`space-y-4`, `mb-4`), modal body padding contribution |
| lg | 24px | Modal body padding (`p-6`) |

Exceptions:
- `gap-2.5`/`p-2.5` (10px) appears on `AddCloudAccountModal.tsx`'s provider radio tiles — this is a pre-existing off-scale value in that file. **Do not propagate it into the new ticket-provider picker.** Use `p-2` (8px) for the Jira/ServiceNow radio tiles instead, consistent with the 8-point scale and with `RemediationTaskModal.tsx`'s own field padding.
- `mt-6` (24px) is used for the modal's final button row in `RemediationTaskModal.tsx` — carry forward unchanged; the new Create Ticket section sits inside the existing `space-y-4` field stack, above that row, not inside it.

## Typography

All sizes/weights below are the exact classes already used by `RemediationTaskModal.tsx` and `RemediationDashboard.tsx` — no new sizes introduced. This phase declares exactly **2 new font weights** for the UI it actually adds (Create Ticket button, provider picker, ticket-display body text).

**New weights this phase declares: 400 regular + 500 medium.** Matches `RemediationTaskModal.tsx`'s exact existing vocabulary (its field labels already use `font-medium`, not `font-semibold`).

**Pre-existing exception (carried over, not a new declaration):** The provider badge inside the ticket-display block (`Jira`/`ServiceNow` pill) reuses `RemediationDashboard.tsx`'s already-established `STATUS_COLORS` status-pill markup verbatim — `px-2 py-0.5 text-xs font-semibold rounded-full` (confirmed at `RemediationDashboard.tsx:192`: `className={\`px-2 py-0.5 text-xs font-semibold rounded-full ${STATUS_COLORS[task.status] ?? ## Copywriting Contract

| Element | Copy |
|---------|------|
| Section label (above the button/picker) | `Ticketing` (small `text-sm font-medium` label, same visual weight as the modal's other field labels — e.g. "Assignee Type", "Due Date") |
| Primary CTA (single provider configured, or picker already resolved) | `Create Ticket` (button; disabled + spinner + `Creating...` while in flight — exact clone of the existing `Save Task`/`Saving...` and `Suggest steps`/`Suggesting...` in-flight pattern already in this file) |
| Provider picker label (both configured) | `Choose a provider` (small helper label above the two radio tiles, shown only when both Jira and ServiceNow are configured for the tenant — D-02) |
| Provider tile labels | `Jira` / `ServiceNow` (plain text inside each radio tile — no emoji; this modal's existing icon vocabulary is `lucide-react`, not emoji, so do not carry `TicketingIntegration.tsx`'s 🔵/🟢 emoji convention into this file, only its color association) |
| No provider configured | Section is **hidden entirely** — no button, no disabled state, no explanatory copy. Ticketing is opt-in tenant configuration (`TicketingIntegration.tsx`); a tenant that hasn't configured either provider should not see a dead-end feature. This mirrors `RemediationTaskModal.tsx`'s own existing precedent for the AI-suggest button being conditionally rendered based on prerequisite state, taken one step further to full hiding since there is no meaningful disabled affordance to offer (there's nothing to configure from inside this modal). |
| Task not yet saved (creating, not editing) | Section is **hidden entirely** — ticket creation requires a persisted `task.id` (the adapter needs a real task to build the ticket payload from). Exact structural precedent: `handleSuggest`'s existing `disabled={!task?.id}` gate on the AI-suggest button, extended to full hiding (not just disabling) since there's no useful picker state to show pre-save. |
| Ticket already created (`ticket_ref` truthy) | Button and picker are both **hidden entirely** — replaced by the read-only ticket-display block below. This is the RESEARCH.md-flagged, now-locked interaction rule: no "create a second ticket" flow in v1. |
| Ticket-display block label | `Ticket` (small `text-sm font-medium` label, same field-label style as the rest of the modal) |
| Ticket-display block content | `{ProviderBadge} {ticket_ref}` on one line, with a second line/inline link: `View in Jira ↗` or `View in ServiceNow ↗` (the `↗` rendered via `ExternalLinkIcon` at `size={12}`, `target="_blank" rel="noopener noreferrer"` on the `<a>`) |
| Success toast | `Ticket created.` (matches the terse past-tense pattern of existing toasts in this codebase: `"Comment posted."`, `"Request approved."`) |
| Error toast | `Failed to create ticket — please try again.` (exact-pattern clone of this file's own existing `"AI suggestion unavailable — please try again"` and `"Failed to save — please try again"` toasts — same em-dash-plus-retry-instruction shape) |
| Destructive confirmation | **Not applicable.** No destructive action exists in this phase's UI surface — ticket creation is additive, non-blocking (D-04), and there is no delete/unlink-ticket action in scope. |

**Auto-create (D-01) has no UI moment**, per CONTEXT.md's own framing — it happens silently on task creation at high/critical priority. The *only* place its result becomes visible is the same ticket-display block described above, which renders identically regardless of whether the ticket was auto-created or manually created. Do not add a toast, banner, or any other UI signal specifically for the auto-create trigger — the task simply appears with its ticket fields already populated the next time the task is viewed.

## Component Notes for Executor

- **Provider value must be a strict enum, never free text** (RESEARCH.md Security Domain, V5 Input Validation): the radio group's `value` prop is typed `'jira' | 'servicenow'` in the frontend state, and the request body sent to `POST /tasks/{id}/create-ticket` carries that same literal string — never render a free-text input for provider selection anywhere in this UI.
- **Provider availability derivation:** the frontend derives `hasJira`/`hasServiceNow` booleans from the existing `GET /api/ticketing/config` response's `jira_url`/`snow_instance` presence (per RESEARCH.md Pattern — these fields are already returned unmasked). No new backend endpoint is needed for this UI to decide which of the three states (hidden / direct-create / picker) to render.
- **Three-state render logic for the Ticketing section**, in priority order:
  1. `task?.ticket_ref` truthy → render the read-only ticket-display block only (button/picker fully hidden).
  2. `!task?.id` (unsaved task), or neither provider configured → hide the entire Ticketing section.
  3. Otherwise → render `Create Ticket` directly if exactly one provider is configured (no picker needed, D-02); render the provider radio tiles + `Create Ticket` confirm button if both are configured.
- **Loading/disabled states:** clone the existing `saving`/`suggesting` boolean-flag + inline spinner pattern verbatim (`<span className="inline-block w-3 h-3 border-2 border-white border-t-transparent rounded-full animate-spin" />` for the filled indigo button, matching `Save Task`'s spinner exactly) — do not introduce a new spinner component.
- **Toast timing:** `showToast(..., 'error')` on any create-ticket failure (network error, non-2xx response, or a best-effort backend response indicating the connector call failed) — the task view itself must not show any other error affordance (no red border, no inline error text) since D-04's contract is "the task action still succeeds," only the ticket-specific toast communicates the failure.
- **Optional (non-blocking) discretionary note:** `RemediationDashboard.tsx`'s task table currently has no per-row ticket indicator. Adding a small `TicketIcon` badge next to the task title when `ticket_ref` is set (no interaction, purely informational, matching the table's existing terse-cell style) would improve at-a-glance visibility without opening the modal, but is **not required** by REM-01/REM-02's success criteria and is left to the planner's/executor's discretion given the phase brief's "keep the design contract scoped accordingly" instruction. If added, reuse the existing table cell padding/typography (`p-4`, `text-xs`) — no new spacing or type tokens.
