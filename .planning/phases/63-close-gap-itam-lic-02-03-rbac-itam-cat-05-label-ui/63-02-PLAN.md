## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser client → ITAM label API | Crossed by three new `authFetch` calls. Authorization is enforced server-side by `_require_itam_admin` on `itam_label_endpoints.py` (already correct since Phase 58); the client adds no authorization logic and must not assume any. |
| backend response headers → browser filesystem | A server-supplied `Content-Disposition` value becomes an anchor `download` attribute — attacker-influenceable data reaching a file-write sink. |
| in-memory blob → object URL | `URL.createObjectURL` allocates a document-lifetime handle that leaks unless explicitly revoked. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-63-08 | Tampering | Filename derived from the `Content-Disposition` header and assigned to the anchor `download` attribute in `triggerLabelDownload` | medium | mitigate | Parse with `exportReport`'s bounded regex and strip quote characters; the backend already sanitises the tag through `itam_label_endpoints._safe_filename_part` before it reaches the header. Never concatenate an asset tag or any other user-controlled field into a filename client-side — Task 1 forbids this explicitly and the fallback name is derived only from the opaque asset id. Browsers additionally strip path separators from `download`. |
| T-63-09 | Elevation of Privilege | The Label action is rendered for any user who can reach the Lifecycle tab | low | accept | UI visibility is not an authorization boundary. The three routes are gated by `_require_itam_admin` server-side, so a non-admin receives 403 and the handler surfaces it as an error toast via `itamThrow`. Adding a client-side role check would duplicate authorization in an untrusted tier for no security gain. Accepted rationale: the authoritative check is server-side and already verified in Phase 58. |
| T-63-10 | Denial of Service | `POST /api/assets/labels/sheet` with a large `assetIds` array | low | accept | This plan always sends exactly one id per D-03, and the backend independently enforces `MAX_LABEL_SHEET_ASSETS` with a descriptive refusal. No client-side cap is added, so there is no second limit to drift out of sync with the server's. |
| T-63-11 | Information Disclosure | Requesting a label for an asset id belonging to another tenant | low | accept | Already mitigated server-side: `itam_label_endpoints._load_asset_for_label` reads through the tenant-isolated database handle, so a cross-tenant id is indistinguishable from a nonexistent one. This plan sends only ids the tenant-scoped `fetchAssets` response already returned. |
| T-63-12 | Denial of Service | Object URL / DOM leak — an unrevoked blob URL or an orphaned anchor per download | low | mitigate | `triggerLabelDownload` calls `window.URL.revokeObjectURL` and removes the anchor after `click()`, matching the teardown order proven by `downloadComplianceReport` and `exportReport`. Centralising this in one helper means the three call sites cannot each get it subtly wrong. |
