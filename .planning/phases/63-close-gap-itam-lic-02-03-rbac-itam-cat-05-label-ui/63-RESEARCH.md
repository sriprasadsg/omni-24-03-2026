## Summary

Both gaps are pure "clone an already-working sibling pattern" fixes with zero new design surface. For the RBAC gap: `itam_consumable_endpoints.py` (7 routes) and `itam_component_endpoints.py` (5 routes across two routers) currently depend on bare `Depends(get_current_user)`; every other ITAM router (license, finance, asset, lifecycle, label) depends on `Depends(_require_itam_admin)`, a function defined once in `itam_asset_endpoints.py` that wraps `get_current_user` and additionally checks `manage:assets` via `verify_permission`. The fix is a mechanical `Depends()` swap plus an import change, in both files, with **zero other code changes required** — `get_current_user` is used for nothing else in either file, so its import can be deleted entirely, and downstream service code already reads `current_user.tenant_id` via `getattr(current_user, "tenant_id", ...)`, which is unaffected by the swap since `_require_itam_admin` returns the identical `TokenData` object `get_current_user` produces. A genuinely useful discovery: the existing test fixtures for both files (`consumable_app`, `component_app`) **already** monkeypatch `itam_asset_endpoints.verify_permission` to return `True` — this patch is currently dead code (nothing in either endpoint file calls `verify_permission` yet), but it means once the swap lands, **every existing passing test keeps passing unmodified**; only new 403-test classes need to be added.

For the label UI gap: `itam_label_endpoints.py`'s 3 routes (`GET /{asset_id}/label/qr`, `GET /{asset_id}/label/barcode`, `POST /labels/sheet`) return `StreamingResponse` with `Content-Disposition: attachment; filename=...` headers and are already RBAC-correct. `apiService.ts` already has a proven blob-download pattern used twice (`exportReport`, `downloadComplianceReport`) — `authFetch` → `.blob()` → `URL.createObjectURL` → synthetic `<a>` click → `revokeObjectURL`. The new frontend functions should clone this pattern exactly rather than inventing a new one. `LifecyclePanel.tsx`'s per-row action cell (lines 175-181) has room for one more trigger; no dropdown/menu component exists anywhere in the codebase (confirmed again this session), so the new "Label" action needs a self-built minimal menu — recommend a local per-row `useState<string | null>` (the open row's asset id) with a small absolute-positioned panel, since three separate always-visible buttons would visually crowd the already-tight `whitespace-nowrap` action cell next to Check In/Check Out/Mark Audited.

**Primary recommendation:** Do the RBAC swap first (10-minute mechanical diff across 2 files + 2 new small test classes), then the label UI wiring (3 new `apiService.ts` functions cloning the existing blob-download pattern + 1 new dropdown block in `LifecyclePanel.tsx`). Both are independent — no shared files, no ordering dependency — but sequencing RBAC first means every subsequent phase test run also exercises the (still-latent) `verify_permission` mock wiring already sitting in the consumable/component test fixtures.

async def _require_itam_admin(current_user: TokenData = Depends(get_current_user)):
    """Dependency to ensure the current user has 'manage:assets' permission."""
    if not await verify_permission(current_user, "manage:assets"):
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="User does not have permission to manage ITAM assets."
        )
    return current_user

### Pattern 2: Blob-download client function (the reusable model for the 3 new label functions)

**What:** `authFetch` → check `res.ok` → `res.blob()` → `URL.createObjectURL` → synthetic `<a>` with `.download` set → click → `revokeObjectURL`.
**When to use:** Any `apiService.ts` function that must trigger a browser file download from a binary/streaming backend response — exactly the label routes' `StreamingResponse` + `Content-Disposition: attachment` shape.
**Example — clone this exactly (already proven twice in the codebase):**
```typescript
// Source: services/apiService.ts lines 3658-3670 (downloadComplianceReport, verified this session)
export const downloadComplianceReport = async (filename: string): Promise<void> => {
    const res = await authFetch(`${API_BASE}/compliance/reports/download/${encodeURIComponent(filename)}`);
    if (!res.ok) throw new Error('Failed to download report');
    const blob = await res.blob();
    const url = window.URL.createObjectURL(blob);
    const a = document.createElement('a');
    a.style.display = 'none';
    a.href = url;
    a.download = filename;
    document.body.appendChild(a);
    a.click();
    window.URL.revokeObjectURL(url);
    document.body.removeChild(a);
};
```
A second precedent (`exportReport`, lines 1191-1225) additionally reads the filename **out of the `Content-Disposition` response header** rather than hardcoding it — this is the more correct shape for the 3 new label functions, since the backend generates the filename dynamically from the asset tag (see Research Finding 7) and the frontend must not invent its own:
```typescript
// Source: services/apiService.ts lines 1205-1214 (exportReport, verified this session) — filename-from-header extraction
const disposition = response.headers.get('Content-Disposition');
let filename = `${type.replace(/\s+/g, '_').toLowerCase()}_report.${format}`;
if (disposition && disposition.indexOf('attachment') !== -1) {
    const filenameRegex = /filename[^;=\n]*=((['"]).*?\2|[^;\n]*)/;
    const matches = filenameRegex.exec(disposition);
    if (matches != null && matches[1]) {
        filename = matches[1].replace(/['"]/g, '');
    }
}
```
Recommend combining both precedents: the `downloadComplianceReport` shape (simpler, single `void`-returning function per label type) with `exportReport`'s header-parsing regex (so the actual backend-generated filename, e.g. `asset-label-<tag>-qr.png`, is respected instead of a hardcoded guess).

### Anti-Patterns to Avoid
- **Do not redefine `_require_itam_admin` locally** in either file — it must be imported from `itam_asset_endpoints`, exactly like every other sibling router does. A locally-redefined copy would drift from the canonical gate over time.
- **Do not leave `get_current_user` imported but unused** in either fixed file — Research Finding 1 confirms it has zero other use in both files after the swap; an unused import is dead code CLAUDE.md's cleanliness bar would flag.
- **Do not build a new global `<DropdownMenu>` component** for this single feature — no such component exists in the codebase yet, and introducing one for a single 3-item, single-row-scoped menu is disproportionate. A local per-row `useState` is the established lightweight pattern this file already uses for `checkoutTarget`/`checkinTarget`/`auditTarget`.
- **Do not invent a client-side filename** for the 3 downloads — the backend already computes and sends one via `Content-Disposition` (see Research Finding 7); parse it out per the `exportReport` precedent.

## Common Pitfalls

### Pitfall 1: Forgetting to fix `asset_components_router` alongside `router` in `itam_component_endpoints.py`
**What goes wrong:** `itam_component_endpoints.py` defines two separate `APIRouter` instances — `router` (component CRUD/attach/detach, 4 routes) and `asset_components_router` (the asset-scoped `GET /{asset_id}/components` sub-resource, 1 route). It is easy to fix only `router`'s 4 routes and miss `asset_components_router`'s 1 route, since it's defined at the top of the file (lines 20-34) before `router`'s own routes.
**Why it happens:** The file's route count (5 total) is split across two router objects that both need the identical `Depends()` swap.
**How to avoid:** Grep `Depends(get_current_user)` in the file after editing — must return zero matches. Confirmed count this session: `list_asset_components_endpoint` (asset_components_router, 1) + `create_component_endpoint`, `list_components_endpoint`, `attach_component_endpoint`, `detach_component_endpoint` (router, 4) = 5 total, matching CONTEXT.md's stated count.
**Warning signs:** `router_registry.py` line 88 registers `asset_components_router` as a **separate** `_load()` call from `router` (line 87) — a strong hint the file genuinely has two independent router objects, not one.

### Pitfall 2: Assuming the existing consumable/component tests need a full rewrite
**What goes wrong:** A planner unfamiliar with the test fixtures might assume every existing test in `test_itam_consumable.py`/`test_itam_component.py` needs updating to inject a `verify_permission` mock, since the routes currently bypass that check entirely.
**Why it happens:** It looks like a routes-level behavior change should cascade into every test using those routes.
**How to avoid:** Both fixture functions (`consumable_app` at `test_itam_consumable.py:140-146`, `component_app` at `test_itam_component.py:142-148`) **already** contain `monkeypatch.setattr(itam_asset_endpoints, "verify_permission", AsyncMock(return_value=True))` — this line is currently dead code since neither endpoint file calls `_require_itam_admin` yet, but it means **all existing tests will keep passing unmodified** once the swap lands. Only new tests (403-for-non-admin) need to be added, following `test_itam_finance.py`'s `TestFinanceRbacAndTenantIsolation` class as the concrete pattern.
**Warning signs:** If the plan proposes editing >2 lines per existing test function in either file, that's a sign this finding was missed.

### Pitfall 3: Hardcoding the downloaded filename instead of reading `Content-Disposition`
**What goes wrong:** A naive frontend implementation invents its own filename (e.g. `qr-code.png`) instead of respecting the backend's actual generated name (e.g. `asset-label-WS-0042-qr.png`), which silently diverges from what Phase 58's backend intends callers to see and loses the asset-tag-specific naming that makes bulk-downloaded files distinguishable.
**Why it happens:** `res.blob()` alone doesn't surface the filename — it has to be pulled from response headers explicitly, an easy step to skip.
**How to avoid:** Follow `exportReport`'s regex-based `Content-Disposition` header parse (services/apiService.ts:1205-1214), not `downloadComplianceReport`'s simpler shape (which works only because its caller already knows the filename ahead of time — not true for the label routes, whose filenames are asset-tag-derived server-side).
**Warning signs:** A frontend function signature for the label downloads that takes a `filename` parameter from the caller, rather than deriving it from the response, is a sign this pitfall wasn't avoided.

### Pitfall 4: LifecyclePanel.tsx has an uncommitted, unrelated in-flight change
**What goes wrong:** `git status`/`git diff` (re-confirmed this session) shows `components/itam/LifecyclePanel.tsx` is currently modified in the working tree — a "Logged-in User" table column was added (new `<th>` at line 156, new `<td>{a.loggedInUser || '—'}</td>` at line 174), shifting the exact line numbers CONTEXT.md's canonical refs cite (it said "lines ~177-181"; with this uncommitted change already applied, the action buttons are now at lines 176-181). If execution stages/reverts working-tree state carelessly, this unrelated change could be lost.
**Why it happens:** An unrelated, uncommitted edit landed in the same file this phase needs to modify, before this phase started.
**How to avoid:** Do not `git checkout`/`git restore`/`git stash drop` this file. Build the "Label" action addition on top of the current working-tree state (which already includes the "Logged-in User" column) rather than an older committed version. Confirm via `git diff` before finishing that the "Logged-in User" column change is still present in the final diff, alongside the new Label action.
**Warning signs:** A diff that removes the `loggedInUser` column, or a `git status` showing the file was reset before this phase's edits were made.
