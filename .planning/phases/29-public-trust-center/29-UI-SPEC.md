# Phase 29 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase has **two distinct visual surfaces** with different constraints. Both are specified below; do not cross-apply tokens between them without checking which surface a task touches.

| Surface | File | Framework | Audience |
|---------|------|-----------|----------|
| A. Public trust page | `backend/static/trust-page.html` | Standalone HTML + hand-written CSS + vanilla JS (no React, no Tailwind, no build step — per `29-RESEARCH.md` Open Question 1, resolved) | External prospects/auditors, unauthenticated |

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge internal padding |
| sm | 8px | Compact element spacing, form field internal padding |
| md | 16px | Default element spacing, card internal padding (mobile) |
| lg | 24px | Section padding, gap between form fields |
| xl | 32px | Card internal padding (desktop), gap between major page sections |
| 2xl | 48px | Major section breaks (public page hero → body) |
| 3xl | 64px | Page-level top/bottom spacing on the public page |

Exceptions:
- Existing precedent in `TrustCenter.tsx` uses half-step Tailwind utilities (`gap-1.5`, `px-1.5`, `py-1.5` = 6px) for icon+label chips and pill badges — this is an accepted, already-shipped exception; do not "fix" it to a full 8pt value when doing incremental edits to the existing file. New code in this phase (both surfaces) should use the 8pt scale above; only touch existing 6px chip spacing if a task explicitly requires editing that specific element.
- Surface A (static HTML) uses `rem` units at a 16px root: 0.25rem/0.5rem/1rem/1.5rem/2rem/3rem/4rem map to the tokens above.

## Typography

### Surface A — Public trust page (`trust-page.html`)

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label / meta | 14px | 400 (regular) | 1.5 |
| Section heading | 20px | 600 (semibold) | 1.2 |
| Display (page hero: company name) | 32px | 600 (semibold) | 1.2 |

Exactly 4 sizes (14/16/20/32), exactly 2 weights (400/600). Do not introduce a 3rd weight (no 500/700) on this page — semibold at 20px/32px is sufficient for hierarchy without a bold weight.

### Surface B — Admin additions (`TrustCenter.tsx`)

Match the file's existing, already-shipped type scale exactly — do not introduce new sizes/weights when adding the profile-edit form, access-request filters, or domain/slug settings field:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 |
| Label | 12px (`text-xs`) | 500 (`font-medium`) | 1.5 |
| Heading (card title) | 16-18px (`font-semibold`, unnumbered Tailwind default) | 600 (semibold) | 1.2 |
| Display (page title) | 24px (`text-2xl`) | 700 (bold, existing `font-bold` on the gradient-text `<h1>`) | 1.2 |

Note: Surface B intentionally keeps the existing file's established weights (400/500/700) since `TrustCenter.tsx` is explicitly incremental, not a redesign (per phase scope) — the "exactly 2 weights" rule from the standard contract is relaxed here to preserve visual continuity with code already shipped in this file. New form fields added in this phase must reuse `text-sm`/`font-medium`/`text-gray-500` classes already used elsewhere in the file, not invent new ones.

## Color

### Surface A — Public trust page

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f8fafc` (light neutral background, matches `secondary-50` in `tailwind.config.js`) | Page background |
| Secondary (30%) | `#ffffff` with `1px solid #e2e8f0` border, `border-radius: 12px`, subtle shadow (`0 1px 3px rgba(0,0,0,0.06), 0 4px 16px rgba(0,0,0,0.08)` — matches existing `--card-shadow` token) | Card surfaces: profile header card, document list cards, access-request form card |
| Accent (10%) | `#00a8cc` (primary-600 — the darker, more legible-on-white step of the existing cyan primary scale; avoid the lighter `#00d2ff` primary-500 on a white background for text/border contrast reasons) | Reserved for: the "Request Access" CTA button, hyperlink color (public document download links), section-heading accent underline/icon, form input focus ring |
| Destructive | `#dc2626` (red-600) | Reserved for: inline form validation error text/border only (this page has no delete/destroy actions) |
| Success (compliance badges) | `#15803d` text on `#dcfce7` background (green-700/green-50 — matches existing `TrustCenter.tsx` framework-badge colors) | Reserved for: compliance framework badges (SOC 2, ISO 27001, etc.) only |

**Explicit decision — light theme only, no dark mode on Surface A:** the internal SPA supports light/dark via a `.dark` class toggle, but the public page is a standalone static file with no theme-toggle mechanism and no JS framework to read the visitor's app-level preference. Building a `prefers-color-scheme` dark variant is optional polish, not required — default to light theme only, matching the "simple, clean, no new machinery" scope resolution in `29-RESEARCH.md` Open Question 1. If a dark variant is added, it must reuse the exact `.dark` CSS variable values from `index.css` (`--bg-main: #080818`, `--text-main: #e2e8f0`, `--surface-raised: rgba(24,24,52,0.95)`) — do not invent new dark-mode colors.

Reuse the existing file's already-shipped color usage exactly (do not introduce new hues):

Accent reserved for (both surfaces, explicit — never "all interactive elements"):

|---------|------|

| Public link field label | "Public Trust Page URL" |
| Public link copy action | "Copy Link" → on click, button label changes to "Copied!" for 2s (existing toast/inline-feedback convention; use `showToast('Public link copied to clipboard', 'success')` per `utils/toast.ts`, already wired via `ToastContainer.tsx`) |
| Custom domain field label | "Custom Domain (optional)" |
| Custom domain field helper text | "Point a CNAME record for this domain at your platform URL, then enter it here. DNS and TLS setup are your responsibility — this only tells the app which domain to recognize." |
| Empty state — no access requests | "No access requests yet — approved and denied requests will also appear here once visitors submit them." (existing `p-8 text-center text-gray-500` empty-state pattern, reused verbatim from the file's current `{requests.length === 0 && ...}` block — do not restyle) |
| Error state — profile save fails | `showToast('Could not save trust profile. Please try again.', 'error')` (existing toast pattern) |
| Error state — approve/deny action fails | `showToast('Could not update request status. Please try again.', 'error')` |
| Destructive confirmation | **Approve/Deny are NOT destructive-delete actions** — they are reversible status transitions on a request record (an admin can re-open review later via the existing `update_request_status` call), and this phase does not change that interaction model per the phase brief's "incremental, not a redesign" instruction. Do not add a confirmation dialog to Approve/Deny; that would be new scope beyond "verify and only spec what's missing." **Accessibility (checker Dimension 2 finding):** these icon-only buttons must carry `aria-label="Approve request"` / `aria-label="Deny request"` respectively — add this attribute when touching these buttons for the toast-wiring change below, even though the buttons themselves are pre-existing and not otherwise being rebuilt.
| Success feedback — approve/deny action succeeds | `showToast('Request approved.', 'success')` / `showToast('Request denied.', 'success')` — currently the file updates state silently with no toast; adding this toast call is the one small UX addition in scope, using the already-established `utils/toast.ts` bus |

## Cross-Surface Consistency Notes

- Both surfaces must use the same font stack (`Outfit` → `Inter` → system fallback) so a visitor who later logs into the authenticated app doesn't perceive a jarring brand shift.
- Both surfaces must use the same accent color family (cyan/blue primary scale) even though Surface A uses the darker `primary-600` (#00a8cc) for contrast-on-white reasons while Surface B keeps its existing `blue-600`/`cyan-500` gradient — these are close enough on the same hue family to read as one brand, and this divergence is intentional (documented above), not an oversight.
- Both surfaces must reuse the identical green/red semantic meaning: green = compliant/approved, red = denied/error. Do not introduce a different semantic color mapping on Surface A than what `TrustCenter.tsx` already established on Surface B.
- Compliance-data honesty (per `29-RESEARCH.md` Pitfall 4): if any future iteration adds a live compliance score or scan-result number to Surface A, it must carry the same SIMULATED-badge convention established in Phase 25 — out of scope for this phase's static framework-name-list display, but noted here so the executor doesn't silently add a number without provenance labeling.
