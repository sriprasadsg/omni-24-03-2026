# Phase 87 — UI Design Contract

> Visual and interaction contract for four surfaces: the Super Admin **Partners** screen, the **Partner portal** (partner admin, partner viewer), the public **Accept invite** page, and **sign-in routing and navigation** for partner users. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Locked inputs: 87-CONTEXT.md D-01..D-20. Nothing here re-opens them. In particular D-01: partner staff see seats and usage only, so no alert, asset, finding, user or other customer data appears on any partner-facing screen, tooltip, CSV column or error message. Visual details the context left open are recorded as researcher defaults (section "Assumptions Recorded", R1..R14) and the questions that need the user are listed under "Open Questions".
> Extends, does not replace, the Phase 81, 82 and 83 UI-SPECs (most recent: `83-UI-SPEC.md`): tokens, the four-size and two-weight type scale, the spacing scale, chip anatomy and tones, banner anatomy, `.card`, `Modal` conventions and the state vocabulary are inherited as written. Only deltas are declared here.
> New infrastructure: none. No new library, no new token, no new colour, no new chip tone.

## Spacing Scale

Inherited unchanged from 81-UI-SPEC (4, 8, 16, 24, 32, 48; 64 unused).

| Token | Tailwind | Usage in this phase |
|-------|----------|---------------------|
| xs 4px | `1` | Icon-to-text gap in chips and buttons, gap between a stat label and its value |
| sm 8px | `2` | Gap between chips, between footer buttons, between stacked helper lines |
| md 16px | `4` | Form row gap, table cell vertical padding (`py-4`), gap between blocks inside a card or modal |
| lg 24px | `6` | Card padding (`.card p-6`), table cell horizontal padding (`px-6`), gap between page sections |
| xl 32px | `8` | Empty-state card padding, Accept-invite card padding |
| 2xl 48px | `12` | Empty-state icon circle, Accept-invite top margin on narrow screens |

Exceptions (all multiples of 4):
- Every consequential control (`Appoint partner`, `Create customer`, `Save seats`, `Save screens`, `Send invite`, `Move customer`, `Suspend partner`, `Reinstate partner`, `Set password`, `Export CSV`) is `min-h-10` (40px, `px-4`).
- Row action text buttons in tables (`Change seats`, `Choose screens`, `Move customer`, `Edit partner`, `Show customers`, `Suspend partner`, `Resend invite`) are `min-h-8` (32px hit area, `px-2`), declared as in 83 for the 32px remove button.
- Inherited exception, 40px controls (`min-h-10`): not on the 4/8/16/24/32/48 scale as a layout step, but it is the control height Phases 81 and 83 already declared for every consequential control (83-UI-SPEC, "Approve, Deny, Confirm isolation, Undo, Save settings and every dialog confirm are `min-h-10`"). Phase 87 keeps one control height across the product rather than introducing a second; it is a size of a control, not a spacing step between elements.
- Inherited exception, 12px input padding (`px-3`): the existing `TenantLicensePanel.tsx` input class is `px-3 py-2`, used by every tenant form today. A 12px horizontal inset is a multiple of 4 but sits between the 8 and 16 steps. Phase 87 reuses that class unchanged (only `min-h-10` is added) so the new forms look identical to the forms beside them; moving to `px-2` or `px-4` would make them differ from every other input in the product. Not for use on any element other than text, number, date, email, password and select inputs.
- Stat tile: `p-6`, label and value stacked with `gap-1`.
- Pool bar: `h-2` (8px) track, full tile width.
- Accept-invite card: `max-w-md` (448px), centred.
- No half-steps in new elements.

Inherited from 81, 82 and 83: dominant `--bg-main`, secondary `.card` surface, accent `primary-600` (`rgb(14 116 144)` in the light theme), destructive `red-600`, amber warning, blue info, neutral text. 60/30/10: the page canvas is the dominant surface, tiles, tables and modals are `.card` surfaces, accent stays small.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bg-main` | Page canvas |
| Secondary (30%) | `.card` surface (`--glass-bg`) | Stat tiles, tables, modals, the Accept-invite card |
| Accent (10%) | `primary-600` (hover `primary-700`) | See reserved list |
| Destructive | `red-600` | `Suspend partner` confirm, inline errors, `Expired` chip |

Meaning maps onto the existing chip tones; no tone is added:

| Meaning | Chip | Tone |
|---------|------|------|
| Partner active | `Active` | GREEN (`CheckCircleIcon`) |
| Partner suspended | `Suspended` | AMBER (`PauseCircleIcon`) |
| Pool expired | `Expired` | RED (`AlertTriangleIcon`) |
| Pool expires within 30 days | `Expires in {n} days` | AMBER (`ClockIcon`) |
| Pool has no expiry | text `No expiry`, no chip | none |
| Staff member signed in at least once | `Active` | GREEN |
| Staff invited, link still valid | `Invited` | NEUTRAL (`MailIcon`) |
| Staff invited, link expired | `Invite expired` | AMBER (`ClockIcon`) |
| Customer licence expired | `Expired` chip beside the date | RED |
| Customer seats all in use | text only, no chip | none |

GREEN and RED chip class strings are the inherited ones (`bg-green-50 text-green-800 border-green-200 dark:bg-green-400/10 dark:text-green-200 dark:border-green-400/25` and the red equivalent); the executor copies them from the Phase 81 chip definitions.

Accent reserved for (inherited items 1 to 5 from 81 and 82 stand; Phase 87 adds exactly six):
6. The page-level create button: `Appoint partner` (Super Admin) and `Create customer` (partner admin). One per screen.
7. The submit button of a modal that creates or saves (`Appoint partner`, `Save partner`, `Create customer`, `Save seats`, `Save screens`, `Send invite`, `Move customer`, `Reinstate partner`, `Set password`).
8. The "handed out" fill of the pool bar and of the per-customer used-seats bar.
9. The focus ring (global `:focus-visible`).
10. The active sidebar entry (`Partners` or `Partner portal`), as every other entry.
11. The `Accept invite` page's `Set password` button and its `Go to sign in` button.

Accent is NOT used for: `Export CSV`, `Resend invite`, `Cancel`, `Discard`, row action buttons, table links, stat numbers, chips, section headings.

Destructive red is used for `Suspend partner` (it signs every partner user out, so the confirm is the one red button), inline field and request errors, and the `Expired` chip. Nothing in this phase deletes data: there is no delete-partner or delete-customer control on these screens (deleting an organization stays on Tenant Management).

Meaning never relies on colour alone: every chip carries a 12px `aria-hidden` icon and visible text; the pool bar always has the figures beside it in words; an expired licence carries the word `Expired`.

## Screens and States

### 0. Placement, roles and the sign-in contract

**Primary visual anchor:** for a partner user, the single `Partner portal` sidebar entry in its active state (accent, nothing else in the sidebar competes with it); at sign-in refusal, the red error block above the form.

| Viewer | Sidebar | Lands on | Can open |
|--------|---------|----------|----------|
| Super Admin (holds `manage:partners`) | existing groups; new entry `Partners` in the management group directly under `Tenants` | unchanged (their current landing) | `Partners`; never `Partner portal` (the owner passes every view check, so the entry is hidden by a role gate, not by permission: R1) |
| Partner admin (`partner_admin`) | exactly one entry, `Partner portal`, no group heading | `Partner portal` | `Partner portal`, plus profile and security self-service reachable from the header menu |
| Partner viewer (`partner_viewer`) | exactly one entry, `Partner portal` | `Partner portal` | same page, read-only |
| Anyone else | unchanged; no `Partners`, no `Partner portal` | unchanged | unchanged |

Partner users see nothing else: no dashboard, no notification bell data, no search results, no tenant switcher, no theme-affecting customisation entry that calls a non-partner route. The header keeps the organization name (the partner's name), the theme toggle and a user menu with `Sign out`, and the self-service security entry only if it is reachable with partner permissions (Open Question 6). A deep link to any other view renders the existing "no access" state (Phase 77), never a blank page.

**Suspended partner at sign-in (PART-01).** On a correct email and password for a user of a suspended partner, the sign-in form shows the existing red error block (same anatomy as the other sign-in errors in `LoginPage.tsx`) with: `This partner account is suspended. Contact your platform administrator to restore access.` Nothing else is revealed (no partner name, no reason, no date). The refusal is shown only after valid credentials, so it cannot be used to discover which emails belong to partners (planner: server-side requirement, record as a test). A wrong password shows the ordinary failure.

**Suspended while signed in.** The next API call answers 403 `partner suspended`. The app clears the session and navigates to `/login?error=partner_suspended`; `LoginPage` maps that param to the same message as above (the pattern already used for `?error=sso_failed`). No toast, no half-rendered portal. Unsaved form content in an open modal is lost; this is stated nowhere because the refusal is immediate.

**Signed-in partner user, no partner permission at all.** Cannot occur by design; if the user object has a partner role but the portal call fails with 403 for any other reason, show the portal error state (section 2, Error).

### 1. Super Admin `Partners` screen (PART-01, PART-03, PART-07; D-07, D-11, D-14, D-18)

Route/view id `partners`, group `mgmt`, permission `manage:partners` (Super Admin only). `<main>` with `container mx-auto p-6`, `space-y-6` between sections.

**Primary visual anchor:** the Partners table, specifically each row's pool bar (the accent fill is the only accent-coloured mass on the screen besides the `Appoint partner` button, so the eye lands on which partners are nearly out of seats). The 30px page title names the screen; it is not the anchor.

**Header.** Left: `h1` 30/600 `Partners`; under it a 14/400 muted line `Appoint partners, give each a pool of agent seats and set which screens they may sell.` Right: `Appoint partner` (accent, `PlusIcon` 16px left, `min-h-10`). Below the header, a `{n} partners` 12/400 muted count and, when there are more than 10 partners, a search input (`SearchIcon`, `aria-label="Search partners"`, filters by name client-side, placeholder `Search partners`).

**Partners table** (`.card overflow-hidden`; `<table>` inside `overflow-x-auto`; column minimums sum to 1,008px, scrolling horizontally below `xl` is accepted for a back-office table, and below `lg` rows collapse to stacked cards, one per partner, with each field as a labelled `dl` row, the Phase 81 stacked-card pattern).

| Column | Content | Width |
|--------|---------|-------|
| Partner | Name 14/600 `break-words`; under it 12/400 muted `{n} customers` (`1 customer`) | `min-w-[240px]` |
| Pool | `{handedOut} of {size} handed out` 14/400 tabular-nums, `h-2` bar under it (accent fill = handed out, `bg-gray-200 dark:bg-white/10` track), then 12/400 muted `{free} free` | `min-w-[200px]` |
| Expires | Date `Mon D, YYYY` 14/400 with the expiry chip beside it when within 30 days or past; `No expiry` muted otherwise | `min-w-[160px]` |
| Screens | `{n} screens` 14/400 (`All screens` when the ceiling is unrestricted; `1 screen`) | `min-w-[120px]` |
| Status | `Active` or `Suspended` chip | `min-w-[120px]` |
| Actions | `Edit partner`, `Show customers` (disclosure toggle; reads `Hide customers` when open), `Suspend partner` or `Reinstate partner` as 32px text buttons, left to right, `flex flex-wrap gap-2` | `min-w-[200px]` |

Ordering: name ascending. No pagination below 50 partners; at 50 or more, 25 per page with a `Show more partners` secondary button (`min-h-10`, pending `Loading...`).

**Customers disclosure (per partner).** The `Show customers` button (`aria-expanded`, `aria-controls`, `ChevronRightIcon` that rotates; the label becomes `Hide customers` when open) expands a full-width row under the partner: a compact inner table of that partner's customers with columns `Customer`, `Seats used`, `Seats assigned`, `Agents online`, `Licence expires`, and a row action `Move customer` (`aria-label="Move {customer}"`). A header strip above it carries `Add an existing organization` (secondary, `PlusIcon`) which opens the move dialog in its "add" mode. This is the Super Admin's view of seats and usage only; it carries the same D-01 fields as the portal, no more.

Table states:

| State | Contract |
|-------|----------|
| Loading | Header renders; the table body shows 4 skeleton rows (`h-4` bars), `aria-busy="true"` on the table region. |
| Empty (no partners) | `EmptyStateCard`: `BuildingIcon`, heading `No partners yet`, body `Appoint a partner to give a dealer or reseller its own pool of seats. Its staff then create and manage their own customers.`, primary action `Appoint partner`. |
| Empty search | Inline row `No partners match "{query}".` with a `Clear search` text button. |
| Error | Red block above the table (`AlertTriangleIcon`, `role="alert"`): `Couldn't load partners. Check your connection and try again.` with a `Try again` secondary button; no stale table. |
| Partner with no customers | Disclosure shows 12/400 muted `This partner has no customers yet.` |
| Populated | As above. |

**Appoint / Edit partner modal** (`Modal size="lg"`, `closeOnBackdrop={false}`, Esc closes unless a request is in flight; footer `Cancel` left, submit right). One form, two titles: `Appoint a partner` (submit `Appoint partner`, pending `Appointing...`) and `Edit {partner name}` (submit `Save partner`, pending `Saving...`). Body `space-y-6`.

Fields, in order:
1. `Partner name` (text, required, 1 to 100 characters, autofocus on appoint). Helper: `The name staff and customers recognise.` Edit mode: editable.
2. `Seat pool` (number, `inputMode="numeric"`, required, whole number 1 to 1,000,000). Helper: `How many agent seats this partner can hand out in total.` In edit mode a second helper line: `{handedOut} seats are handed out, so the pool can't go below {handedOut}.` The field's `min` is `handedOut`. Inline error below `handedOut`: `The pool can't be smaller than the {handedOut} seats already handed out. Ask the partner to take seats back first.` (D-07; the server's 409 text is shown verbatim as well, since it carries the authoritative count).
3. `Pool expires on` (date, optional). Helper: `Leave empty for no expiry. After this date the partner can't create customers or hand out seats. Customers keep their seats: agents already enrolled keep working and new agents wait for approval.` (D-08).
4. `Screens this partner may sell` (screen ceiling): a checklist of the platform's screens grouped as `ManageTenantModal.tsx` groups them (same group names and labels from `shared/tenant-feature-switches.json`), with `Select all screens` and `Clear all screens` text buttons, and a count `{n} of {total} selected`. Helper: `A partner can only switch these screens on for its customers. Screens a customer already has stay on if you remove them here.` (D-19). A parent/child screen follows the same parent rule as the customer feature picker. The Dashboard entry is shown checked and disabled with `Always included`.
5. Appoint mode only, group `First partner administrator`: `Name` (text, required) and `Email address` (email, required). Helper: `We email this person a link to set a password. The link works for 7 days. They then invite their own colleagues.` (D-17).

Validation (inline, 12/400 `text-red-600 dark:text-red-400`, `role="alert"`, on blur and on submit; submit disabled while any field is invalid or, in edit mode, nothing has changed): `Enter a partner name.`; `Enter a pool between 1 and 1,000,000 seats.`; `Enter a valid email address.`; `Enter a name for the administrator.`

Request errors (red block above the footer, `AlertTriangleIcon`, `role="alert"`): `Couldn't appoint this partner: {server message}. Try again.` / `Couldn't save this partner: {server message}. Try again.`; fallback `Couldn't appoint this partner. Check your connection and try again.` Known server messages the UI must display verbatim: the pool-below-handed-out refusal (with the count), `That name isn't available.` and the email-already-used refusal (generic, never says which organization holds it).

Success (appoint): modal closes, toast `Partner appointed. An invite was sent to {email}.`; if the server answers `emailSent: false`, the modal stays open on a result view instead: green check, `{name} was appointed.`, amber block `The invite email couldn't be sent. Email is not configured on this platform. Set a password for {email} in User Management, then share it with them directly.` and a `Done` button. Edit success: toast `Partner saved.`; if the pool, expiry or ceiling changed, the table refetches.

**Suspend and Reinstate dialogs** (`Modal size="md"`, `showClose={false}`, `closeOnBackdrop={false}`).
- `Suspend {name}?` Body (14/400): `Everyone at this partner is signed out now and can't sign in until you reinstate it. Its customers are not affected: they keep their seats and keep running.` Amber block (`AlertTriangleIcon`, `role="status"`): `This is recorded in the audit log with your name.` Confirm: red `Suspend partner` (pending `Suspending...`), `Cancel`. Success toast `{name} is suspended.`
- `Reinstate {name}?` Body: `Its staff can sign in again. Seats, customers and the pool are unchanged.` Confirm: accent `Reinstate partner` (pending `Reinstating...`). Success toast `{name} is reinstated.`
- Failure for both: red block `Couldn't suspend this partner: {server message}. Try again.` / `Couldn't reinstate this partner: {server message}. Try again.` with fallbacks.

**Move customer modal** (`Modal size="lg"`, same conventions). Two modes.
- Move: opened from a customer's `Move customer` button. Title `Move {customer name}`. Read-only summary block (`rounded-lg bg-gray-50 dark:bg-white/[0.04] border border-gray-200 dark:border-white/10 p-4`): `Currently with {partner name}`, `{assigned} seats assigned, {used} in use`. Field `Move to` (`<select>`): every other active partner (each option `{name} ({free} free)`) and last the option `No partner (direct customer)`. Under the select, once a partner is chosen, a 14/400 line: `{customer} keeps its {assigned} seats. They are taken from {target}'s pool ({free} free) and returned to {current}'s pool.` If the target cannot fit them: red inline `role="alert"` `{target} has {free} seats free and {customer} needs {assigned}. Increase {target}'s pool first.` and submit disabled (D-18; the server's 409 with the free count is shown verbatim if the race is lost). For `No partner (direct customer)`: `{customer} becomes a direct customer and keeps its {assigned} seats as its own licence. The seats return to {current}'s pool.`
- Add (`Add an existing organization`, opened from a partner's disclosure strip): Title `Add an organization to {partner name}`. Field `Organization` (`<select>` listing direct customers only, option `{name} ({assigned} seats)`, with a text filter above it when there are more than 20). The same summary and fit check run against the partner being added to. Empty list: 12/400 muted `Every organization already has a partner.`
- Both modes: amber block `This is recorded in the audit log with your name. Screens the customer already has stay on, even if this partner may not sell them.` (D-19). Submit accent `Move customer` (pending `Moving...`); success toast `{customer} moved to {target}.` or `{customer} is now a direct customer.`; failure red block `Couldn't move this customer: {server message}. Try again.`

Focus: a modal's initial focus is the first field; after success the opener (button) regains focus via `Modal`'s restore; after a table refetch the focus stays on the row's `Show customers` or `Edit partner` button when it still exists.

### 2. Partner portal (PART-02, PART-05, PART-06, PART-08; D-01, D-04, D-09, D-10, D-16, D-17)

Route/view id `partnerPortal`, permission `view:partner_portal`, writes `manage:partner_customers`. `container mx-auto p-6`, `space-y-6`. **Primary visual anchor:** the Seat pool summary, led by the `Free` tile and the pool bar directly under the tiles (the partner's first question is how many seats it can still hand out); the Customers table is the second read.

The page shows only the viewer's own partner. No tenant switcher, no organization selector, no link to any customer: a customer name is plain text, never a link (there is nothing to open: D-01).

**Header.** Left: `h1` 30/600 `Partner portal`; under it 14/400 muted the partner's name. Right (`flex flex-wrap gap-2`): `Export CSV` (secondary, `DownloadIcon` 16px, `min-h-10`) for admin and viewer; `Create customer` (accent, `PlusIcon`) for the admin only. Both are `disabled` while the first load is in flight. `Create customer` is also `disabled` (with the reason line from the expiry banner, referenced by `aria-describedby`) when the pool is expired or has no free seats.

**Viewer variant.** Identical page with every control removed, not disabled: no `Create customer`, no row actions, no `Team` section, no `Invite colleague`. `Export CSV` stays (it is a read). One 12/400 muted line under the header: `You have read-only access. Ask a partner administrator to make changes.` The viewer never sees a control it cannot use.

**Pool expired banner** (when `expiresAt` is past; amber block, `AlertTriangleIcon`, `role="status"`, above the summary): `Your seat pool expired on {Mon D, YYYY}. Your customers keep working with the seats they have.` When expiry is within 30 days: info block (blue, `InfoIcon`): `Your seat pool expires on {Mon D, YYYY}.` Both are static text, not dismissible.

**Seat pool summary** (`<section aria-labelledby="pool-title">`, `h2` 18/600 `Seat pool`). A `.card p-6` with four stat tiles in a `grid gap-6 sm:grid-cols-2 xl:grid-cols-4` and, below them, the bar.

| Tile | Label 12/600 | Value (Display 30/600, tabular-nums) | Helper 12/400 muted |
|------|--------------|---------------------------------------|---------------------|
| 1 | `Pool size` | `{size}` | none |
| 2 | `Handed out` | `{handedOut}` | `{pct}% of the pool` |

## Accessibility and Interaction Notes

- Focus: global `:focus-visible` ring only. `Modal` handles focus trap, restore and Esc as built. After a table refetch the focus stays where it was; it is never left on a removed node.
- Live regions: errors are `role="alert"`; banners and success summaries are `role="status"`; toasts are polite; counts and polls are silent.
- Tables: real `<table>` with `<th scope="col">`; stacked cards below `lg` use a `<dl>` per customer, and each card has an accessible name (the customer or partner name).
- Disclosures (`Show customers`, `Choose screens` in Create customer): real `<button>` with `aria-expanded` and `aria-controls`.
- Buttons name their target where the page has many of them: `aria-label="Change seats for {customer}"`, `"Choose screens for {customer}"`, `"Move {customer}"`, `"Edit {partner}"`, `"Suspend {partner}"`, `"Resend invite to {email}"`.
- A disabled `Create customer` is explained by visible text referenced with `aria-describedby` (the expiry banner or `You have no free seats. Ask the platform administrator for a larger pool.`).
- Forms: every field has a visible `<label>`; helper and error text are linked with `aria-describedby`; required fields carry `aria-required`; the pool, seats and password fields use `inputMode` and `autoComplete` appropriately (`new-password`, `email`, `off` for names).
- Pool bar: `role="img"` with an `aria-label` that repeats the figures; the numbers beside it are the authority.
- Motion: only `animate-spin` and `animate-pulse`; chevron rotation honours the global reduced-motion rule.
- Touch targets: primary and modal controls `min-h-10`; table row text buttons 32px (declared).
- Dates and times: `<time dateTime>`; `Mon D, YYYY` in the user's locale; full ISO in `title` where the date is abbreviated.
- Text fit: no `truncate` on any data (names, emails). Emails use `break-all`, names `break-words`.
- Security of rendered strings: every server string is rendered as React text; no `dangerouslySetInnerHTML`; a customer name is never a link; the invite token never appears in the DOM, a toast, a log line or the address bar after load.
- D-01 review rule for the executor and UI auditor: on the portal, the CSV and every partner-facing message, the only customer facts present are name, seats assigned, seats used, agents online, agents total and licence expiry.
- Idempotency: every create, save, move, suspend and invite button is disabled while its request is pending, so one click sends one request; the server's atomic pool claim is the second line of defence.

## Open Questions (for the user; each has a recommended default so planning is not blocked)

1. **Customer admin's sign-in link when email is not set up.** SMTP is unconfigured on this VM, so every invite will return `emailSent: false`. Recommended default: show the result view in the modal telling the partner to ask the platform administrator, and let the Super Admin set a password in User Management. Alternative: let the Super Admin copy a one-time link from the Partners screen. (Not done: copying a link to a partner would let it set the customer admin's password, a D-01 breach.)
2. **Does the Accept-invite page need a status call?** The existing confirm endpoint cannot tell expired from used. Recommended default: add a small public status lookup that returns `valid`, `expired`, `used` or `invalid` plus the organization name and the invitee's email. If it is not wanted, the page shows one combined state (`This invite link isn't valid or has expired`) after a failed submit. This is a Planner dependency (below).
3. **Can a partner untick a screen that is outside its ceiling (D-19)?** Recommended default: no, shown locked on. Alternative: allow unticking (then it cannot be put back).
4. **Should the CSV include the pool figures?** Recommended default: no, per-customer rows only. Alternative: a leading summary block or a totals row.
5. **Does the partner admin see a Team list including itself and other admins?** Recommended default: yes, admins only, no viewer access.
6. **Self-service for partner users.** Partner roles hold no `view:profile`, so the header menu offers `Sign out` and, only if reachable with partner permissions, the existing two-step verification settings. Recommended default: `Sign out` plus MFA settings.
7. **Remove, disable or change the role of partner staff.** Not covered by D-17. Recommended default: out of scope for this phase (the Super Admin can disable a user in User Management).

## Open Items for the Planner (not blocking the contract)

Server shapes the contract assumes (names are the planner's; the UI treats every flag as authoritative):
1. **Partner portal overview** returns `{ pool: { size, handedOut, free, expiresAt, expired }, customers: [{ id, name, seatsAssigned, seatsUsed, agentsOnline, agentsTotal, licenseExpiresAt }], role }` (the role lets the page choose admin or viewer), and `ceiling` for the screen picker. The customer `id` is for row keys and requests only; it is never rendered. Counts exclude Pending and Rejected agents as `get_tenants` does.
2. **Invite status**: `GET` public route taking the token and returning `{ state: valid | expired | used | invalid, organizationName?, email?, roleKind? }` (Open Question 2). Rate-limited, no data other than those fields, token never echoed.
3. **Partners list** for the Super Admin: `id`, `name`, `poolSize`, `allocated`, `free`, `expiresAt`, `screenCeiling` (or `unrestricted`), `status`, `customerCount`; and per-partner customers with the D-01 fields. Pool shrink, move and ceiling errors return the numbers the copy needs (`handedOut`, `free`, `needed`).
4. **Sign-in refusal**: `403` with a stable code for a suspended partner on login and on any later request; the existing 15-minute token and refresh paths are covered by the research's chokepoint. The login refusal must be given only after valid credentials.
5. **Navigation**: add `partners` and `partnerPortal` to the catalogue manifest and to the sidebar with a role gate for the portal entry; partner users' `landingView` is `partnerPortal`.
6. **Feature switch vocabulary**: the picker reads the same `tenant-feature-switches.json` groups used by `ManageTenantModal.tsx`; the server returns the partner's ceiling in that vocabulary.
7. **Public route**: `/accept-invite` must be reachable without a session and must not be redirected to `/login` by the app shell (precedent: the `/sso-callback` handling in `App.tsx` around line 711).
