<module_budget>
## 500-line cap (CLAUDE.md)

`backend/sso_service.py` is **331 lines today**. This plan adds SAMLConfig, SAMLAuthenticator (metadata + AuthNRequest + ACS validation + SLO), SAMLUserProvisioner, and SAMLGroupMapper — comfortably 200+ lines. Appending them to sso_service.py breaks the project's 500-line cap.

**Decision: extract up front, not reactively.** All new SAML code lands in a new `backend/saml_service.py`. sso_service.py keeps only:
- its existing OIDC/OAuth2 surface (KNOWN_OIDC_PROVIDERS, build_oidc_auth_url, token exchange), and
- thin `get_saml_sp_metadata()` / `process_saml_response()` wrappers that delegate into saml_service.py so existing importers (`sso_endpoints.py`) keep working.

The line-count gate in Task 1's verify block enforces both files stay at or under 500 lines. If `saml_service.py` itself approaches the cap, split the group/attribute mapping out into `backend/saml_mapping.py` rather than letting either file run over.
</module_budget>

<frontend_scope>
## Frontend wiring (ROADMAP "UI hint: yes")

Audited — the SSO frontend is **partially** present:
- `components/LoginPage.tsx` (382 lines) has an SSO path, but only to `/api/sso/google/login`; `App.tsx` completes it via `/api/sso/exchange`. There is no SAML "Sign in with SSO" entry point.
- There is **no admin UI** for SSO/SAML configuration anywhere in `components/` (no SSO settings tab alongside `SettingsUsersTab` / `SettingsRolesTab` / `SettingsApiKeysTab`).

**Deferred, with rationale.** This plan is intentionally backend-only:
1. The SAML admin config surface (7 endpoints in Task 2) needs a settings tab with certificate upload, IdP metadata paste, and attribute-mapping table — a substantial UI with its own design surface that would not fit this plan's context budget alongside the SAML SP itself.
2. SAML configuration is a one-time operator task; until a tenant is configured, a login-page SAML button has nothing to point at. The env-var + admin-API path in `user_setup` is a complete operator workflow without UI.
3. The ITAM console frontend (`services/apiService.ts` + console shell) is owned end-to-end by Phase 70's four plans; adding an SSO settings tab here would collide with that ownership.

Consequence to record in the SUMMARY: ITAM-USR-04 ships operator-configurable (env vars + admin API) but not operator-*discoverable* (no settings screen), and end users cannot yet initiate SAML login from `LoginPage.tsx`. Both are UI follow-ups, not backend gaps.
</frontend_scope>
