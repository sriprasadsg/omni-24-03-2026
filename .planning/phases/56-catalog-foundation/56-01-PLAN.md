<assumption_delta_record>
## Assumption-Delta Architecture Checkpoint — recorded decision

**Pluralization signal:** manual (non-agent) asset creation is a second asset-creation path
alongside the existing agent-heartbeat-upsert path.

- **Noun now primary:** `assets` — generalized to mean "any tracked asset, agent-discovered
  or hand-catalogued".
- **Decision:** `promote` (generalize the existing noun), **not** add-alongside. No parallel
  `itam_assets` / `manual_assets` / `physical_assets` collection is created in this phase or
  any later ITAM phase.
- **Rationale:** every existing cross-cutting feature — global search, dashboards,
  `POST /api/assets/bulk-update`, `PATCH /api/assets/{id}/criticality` (the autonomous
  remediation confidence gate), vulnerability findings, compliance evidence linkage, agent
  linking — already assumes one `assets` collection is the CMDB. A parallel collection would
  silently exclude manual assets from all of them and turn "every asset with an open CVE and
  an expiring warranty" into an application-level join.
- **Mechanism:** additive optional fields plus an `assetSource: "agent" | "manual"`
  discriminator; the required-field `Asset` model in `backend/models.py` is left untouched and
  a leaner sibling contract lives in `backend/itam_models.py`.

**Naming reconciliation (recorded so later phases do not re-litigate):**
- The lifecycle field is `lifecycleStatus`, never `status`. `assets.status` already carries
  agent-liveness meaning (seeded `"active"` by the heartbeat upsert, projected by
  `global_search_endpoints.py`, listed in `_BULK_UPDATE_ALLOWLIST`).
- Milestone `ARCHITECTURE.md` sketches this field as `statusLabel` in two code examples;
  `PITFALLS.md`, `REQUIREMENTS.md`, and the ROADMAP goal all say `lifecycleStatus`.
  **`lifecycleStatus` wins** — treat every `statusLabel` mention in the research as a synonym.
- Router file names follow `ARCHITECTURE.md`'s `itam_*` convention
  (`itam_catalog_endpoints.py`, `itam_asset_endpoints.py`), not `STACK.md`'s
  `asset_catalog_endpoints.py` sketch, so phases 57-61 (`itam_checkout_endpoints.py`,
  `itam_license_endpoints.py`, …) stay consistent.

  <decision>
    Three sub-decisions that phases 57-61 build directly on and that cannot be changed later
    without a data migration across every asset document:
    (a) the generated asset-tag format, (b) the exact lifecycleStatus vocabulary and whether
    the six values are stored verbatim, and (c) how pre-existing agent-discovered assets
    acquire a lifecycleStatus.
  </decision>
  <context>
    The field *names* `assetSource` and `lifecycleStatus` are already locked by the milestone
    research (corroborated independently by all four research files) and are NOT being
    re-opened. What is still open is the value shape.

    Undo cost if wrong: asset tags are printed onto physical labels in Phase 58 and scanned
    thereafter — a format change after labels are printed cannot be undone by a code change.
    Phase 57 gates check-out on `lifecycleStatus == "deployable"`, Phase 59 keys warranty
    reporting off lifecycle state, and Phase 61 renders the vocabulary as a UI filter, so a
    vocabulary change becomes a lockstep edit across four phases plus a document rewrite.
  </context>
  <options>
    <option id="option-a">
      <name>IT-0001 zero-padded counter, six-value verbatim vocabulary, read-time default (RECOMMENDED)</name>
      <pros>
        Tag `IT-{seq:04d}` is short enough for a physical label and 1D barcode, sorts
        lexicographically for the first 9999 assets, and matches the pattern
        `PITFALLS.md` prescribes. Vocabulary is exactly the six ROADMAP values
        (deployable/deployed/archived/retired/disposed/broken) stored verbatim lowercase.
        Pre-existing agent assets get no write at all — a missing key reads as `deployable`
        via a read-time default, so this phase performs zero migration and zero mass-update
        against the live assets collection.
      </pros>
      <cons>
        Rolls over to five digits past 9999 (`IT-10000`), so tag width is not fixed forever.
        A read-time default means `lifecycleStatus` is genuinely absent on most documents, so
        any future query that filters on it must handle the missing-key case explicitly.
      </cons>
    </option>
    <option id="option-b">
      <name>Tenant-prefixed tag, same vocabulary, one-time backfill of every existing asset</name>
      <pros>
        Tags are globally distinguishable across tenants; every asset document physically
        carries a lifecycleStatus so later queries need no missing-key handling.
      </pros>
      <cons>
        A tenant-prefixed tag leaks the tenant identifier onto a printed physical label. The
        backfill is an unbounded cross-tenant mass-update against the live assets collection
        on the same code path the heartbeat writes to — the highest-risk operation in the
        phase, for a convenience the read-time default already delivers.
      </cons>
    </option>
    <option id="option-c">
      <name>Opaque UUID tag, extended vocabulary with a maintenance state</name>
      <pros>
        No counter, no sequence gaps, no atomicity concern at all. A `maintenance` state
        matches how some ITAM tools model in-repair equipment.
      </pros>
      <cons>
        An opaque UUID is unusable as a human-readable label a technician reads aloud or types
        — this is the single thing an asset tag exists to be. Extending the vocabulary beyond
        the six ROADMAP values contradicts success criterion 4 and REQUIREMENTS ITAM-LIFE-01.
      </cons>
    </option>
  </options>
