  <behavior>
    - A text `equals` filter matches case-insensitively and an exact-cased value still matches.
    - A text `contains` filter matches a substring case-insensitively, and a value containing regex metacharacters is matched literally.
    - A numeric `gt` filter on 1000 excludes a row whose value is exactly 1000; `lt` on 1000 likewise excludes exactly 1000.
    - A numeric `between` filter with min 100 and max 200 includes rows at exactly 100 and exactly 200.
    - A `between` filter with min equal to max returns the rows equal to that value, not an empty set.
    - A date `before`/`after` filter is strict; a date `between` includes both endpoint dates, and start equal to end returns that day's rows.
    - Zero filter conditions returns every in-scope asset row.
    - An unknown operator, an unknown field name, or a field not present in the catalogue raises a validation error before any database call.
    - Results are sorted by asset tag ascending by default, so two identical runs page identically.
    - A licence/component/consumable value belonging to another tenant never appears on a row, even when the join key collides.
  </behavior>
  <action>
Create `backend/itam_reporting_filters.py` — the module RESEARCH.md and PATTERNS.md both flag as the one subsystem with no codebase analog. Keep it under the project's 500-line file cap; it holds three things.

1. `FIELD_CATALOG` — an ordered, closed allowlist of selectable/filterable fields. Each entry carries `key` (the wire name, e.g. `asset.assetTag`), `label` (the display header used as the row-dict key), `entity` (one of `asset`, `finance`, `license`, `component`, `consumable`), `type` (one of `text`, `date`, `number`, `enum`), and `source` (how the value is obtained). Populate it from fields that already exist on the models — from `Asset`: assetTag, name, serialNumber, type, lifecycleStatus, manufacturerId, modelId, categoryId, supplierId, locationId, poNumber, purchaseDate, purchaseCostCents, warrantyMonths, notes, createdAt, updatedAt; from finance (computed, not stored): bookValueCents, warrantyStatus, warrantyExpiresAt, daysToExpiry; from joined licences: license name, seatCount, expiryDate; from joined components: component name, type, serialNumber; from joined consumables: consumable name, checked-out quantity. The catalogue deliberately excludes `productKey`, the raw `customFields` mapping, `tenantId` and `_id`; a request naming any key absent from the catalogue is rejected. Expose `def list_report_fields()` returning the catalogue without internal `source` details.
2. `FilterCondition` — a Pydantic model with `field: str`, `operator: Literal["equals","contains","before","after","between","gt","lt"]`, `value`, and `value2` (used only by `between`), `model_config` with `extra="forbid"`. A validator rejects a `field` outside `FIELD_CATALOG` and rejects an operator that does not belong to that field's `type` (text takes equals/contains; date takes before/after/between; number takes gt/lt/between; enum takes equals). `CustomReportDefinition` — `name: str` (1..120 chars), `columns: List[str]` with at least one entry, `filters: List[FilterCondition]` defaulting to empty, `extra="forbid"`.
3. `def _filters_to_mongo_query(conditions) -> dict` — a pure function mapping each closed operator to a hand-written Mongo fragment: `equals` on text becomes a case-insensitive anchored regex built from `re.escape` of the value; `contains` becomes a case-insensitive regex built from `re.escape`; `gt`/`lt` become the strict comparison operators; `between` becomes the inclusive pair; `before`/`after` become strict comparisons against the ISO string. Multiple conditions AND together at the top level. Conditions that target a computed finance field or a joined entity are returned separately (not translated into the Mongo query) so the caller can apply them in Python after the join, using identical comparison semantics — implement one shared comparison helper so the Mongo path and the Python path cannot diverge. Never accept, forward or interpolate a client-supplied operator string.

Then `async def run_custom_report(db, definition, tenant_id, limit=None)`: query `db.assets` through the tenant-isolated handle with the translated query, sort by `assetTag` ascending as the stable default, then perform the joins in Python — collect the matched asset ids and issue one batched tenant-scoped `find` per joined collection (`license_assignments` filtered to `targetType` `asset` then `licenses` by the resulting licence ids; `components` by `assetIds`; `itam_consumables` whose checkout records name the asset with `assignedToType` equal to `asset`; `asset_models` for the depreciation policy) and merge in application code. Do not use an aggregation join: `TenantIsolatedCollection.aggregate` tenant-scopes only the top-level match, so a joined sub-pipeline can read another tenant's documents (RESEARCH Pitfall 4). Compute finance values with `itam_finance_service.compute_book_value` and `compute_warranty_status` — never a second depreciation or warranty implementation. Apply the deferred (computed/joined) conditions in Python, project the requested `columns` into a display-header row dict rendering an absent value as an em dash, apply the `MAX_REPORT_ROWS` ceiling with the `truncated` flag, and return the same `{key,title,columns,rows,rowCount,truncated}` dict shape pre-built reports return.

In `backend/itam_reporting_service.py`, extend `build_report_rows` so `kind` also accepts the string `custom`, delegating to `itam_reporting_filters.run_custom_report` with the supplied `definition`. Leave the renderer registry, the row-ceiling handling and the metadata store untouched.

Create `backend/tests/test_itam_reporting_builder.py` using `backend/tests/itam_reporting_test_support.py`, with one test per behavior above. Name the cross-tenant case so `-k tenant_isolation` selects it: seed two tenants whose assets share a `modelId` and whose licences share an id-shaped key, then assert the report for tenant A contains no tenant-B value.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/itam/reports/custom* | Client-authored report definitions (field names, operators, values) cross into query construction here. |
| API → MongoDB (assets + four joined collections) | An asset-rooted query fans out into licence, component, consumable and model lookups across a multi-tenant database. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-72-01 | Tampering | `_filters_to_mongo_query` input | high | mitigate | `FilterCondition` restricts `operator` to a Pydantic `Literal` set and `field` to `FIELD_CATALOG`; each operator maps to a hand-written fragment and every user string used in a regex passes through `re.escape`. No client-supplied query fragment is forwarded. |
| T-72-02 | Information Disclosure | Cross-collection joins in `run_custom_report` | high | mitigate | Python-side joins over separate tenant-isolated `find` calls; no aggregation join is used, so no sub-pipeline can bypass the tenant match (RESEARCH Pitfall 4). Proven by the `tenant_isolation` test seeding colliding keys across two tenants. |
| T-72-07 | Information Disclosure | Field catalogue exposing secret-bearing fields | high | mitigate | `FIELD_CATALOG` is a closed allowlist that omits `productKey`, raw `customFields`, `tenantId` and `_id`; a field outside it fails validation, asserted by a test. |
| T-72-05 | Elevation of Privilege | Custom report CRUD routes | high | mitigate | `Depends(_require_itam_admin)` on every route, exercised by the `-k permission` test. |
| T-72-09 | Repudiation | Shared tenant-wide definitions (D-04) | low | accept | Definitions record `createdBy` and `createdAt`; edits are not supported (save creates a new definition), so there is no silent-overwrite path to attribute. |
| T-72-SC | Tampering | npm/pip installs | low | accept | No package is installed by this plan. |
</threat_model>
