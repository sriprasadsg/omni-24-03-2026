<objective>
Build the agent-side SSH `authorized_keys` rotation mechanics as one focused new module: target the exact fingerprint, refuse the lockout case, snapshot the file, generate an Ed25519 replacement, write atomically, prove the post-write state, and be able to undo all of it from the path alone.

Purpose: this is the destructive half of `rotate_key` — the part that touches a live SSH authentication file on a production host. Every locked safety decision (D-04 fingerprint-exact, D-05 sole-entry refusal, D-06 reversible, D-07 grounded re-verify, D-09 no key material in the result) is enforced here, in one module, under hermetic tests. The dispatch arms that expose it to the backend land in plan 64-04; nothing in this plan is reachable from an instruction yet, which is deliberate — the mechanics are proven before they are wired.

Output: `src/capabilities/ssh_key_rotation.rs`, two new `RemediationError` variants, and the `mod.rs` declaration.

## Decisions this plan records (not deferred, not implicit)

**RESEARCH Open Question 2 / Assumptions Log A4 — rollback mechanism: RESOLVED.**
Backup *granularity* is a whole-file snapshot taken before the edit (RESEARCH.md's recommendation — it avoids re-deriving exact line placement and ordering on rollback). Backup *mechanism* is a dedicated `rotate_key_rollback` arm, NOT a reuse of `restore_file`. `restore_file` requires an explicit `backup_path` parameter, and `_render_step_params` resolves whole-string templates only — it cannot compose `"{{finding.details.affected_path}}"` plus a suffix, and the backup path does not exist on the finding document (the agent creates it at execution time, long after ingest). Plan 64-01 already shipped `rotate_key.yaml` with `rollback: [{action: rotate_key_rollback, params: {authorized_keys_path: ...}}]` on exactly this reasoning. So A4 resolves to "restore_file is not reusable" — for the templating constraint, not the granularity one. This module therefore derives both the backup path and the rotated-key path deterministically from `authorized_keys_path` alone.

**D-08 boundary (recorded, not silently inherited):** the new private key is written to the host and nothing else happens to it. No delivery, no upload, no notification. Out-of-band delivery is explicitly out of scope per D-08, which is *why* the sole-entry refusal (D-05) exists: nobody can log in with a key they have not received yet.

**Non-idempotent by design (new scope boundary surfaced by this plan):** a rotation refuses when a previously rotated private key file is still present in the target directory. Overwriting it would destroy a private key the operator may still be delivering out-of-band (D-08), and a fingerprint-suffixed filename would break the deterministic path derivation the rollback step depends on. Fail-closed is the correct trade; the operator's own out-of-band workflow ends by moving the key off-host, which clears the guard.

`pub fn validate_target(authorized_keys_path: &str) -> Result<(), RemediationError>` refuses in this order: empty string is `InvalidPath`; a path rejected by `ssh_key_checks::is_authorized_keys_path` is `InvalidPath` (this is the single guard between an untrusted instruction parameter and a privileged file write — it already enforces absolute, traversal-free, exact-filename); a path that does not exist or is not a regular file is `FileNotFound`.

`pub fn select_target(text: &str, fingerprint: &str) -> Result<TargetedEntry, RemediationError>` runs `ssh_key_checks::parse_authorized_keys` over the text, then: refuses with `InvalidTarget` when `fingerprint` is empty; counts the parsed entries as `total_entries`; refuses with `LockoutRefused` when `total_entries` is less than 2, naming the count in the message (D-05 — rotating the only entry removes the sole access path, and D-08 puts out-of-band delivery of the replacement private key out of scope, so there is no path back in); then finds the single entry whose `fingerprint` field is exactly equal to the argument (full-string equality, never a prefix, substring, or case-insensitive comparison) and refuses with `KeyNotFound` when there is none. Ordering matters: the lockout check runs before the match lookup so a single-entry file refuses identically whether or not the fingerprint matches.

`pub fn write_atomic(path: &Path, contents: &str) -> Result<(), RemediationError>` reads the existing file's metadata permissions, writes `contents` to a sibling temp file in the same directory named from the target's file name plus a `.omni-tmp-` prefixless suffix carrying the current process id, applies the captured permissions to the temp file under a `#[cfg(unix)]` block using `PermissionsExt::set_mode` (mirroring `fim_baseline.rs`), then renames the temp file over the target. Any failure removes the temp file before returning `OperationFailed`. When the target has no pre-existing metadata, default the mode to owner-read/write only.

`pub fn snapshot_backup(authorized_keys_path: &str) -> Result<String, RemediationError>` copies the whole file to `backup_path_for(...)`, sets owner-only permissions on the copy under `#[cfg(unix)]`, and returns the backup path. It overwrites an existing snapshot on purpose: the snapshot means "the state immediately before this rotation", which is exactly what a step rollback must restore.

`pub fn rollback_rotation(authorized_keys_path: &str) -> Result<(), RemediationError>` validates the target path, returns `FileNotFound` when no snapshot exists at the derived backup path, restores the snapshot's contents over the live file via `write_atomic`, then best-effort removes the snapshot file and both rotated-key files (the private key at `rotated_key_path_for(...)` and its sibling with a `.pub` extension) so a subsequent rotation is unblocked. | Boundary | Description |
|----------|-------------|
| backend instruction params -> agent filesystem | A backend-rendered `fingerprint` and `authorized_keys_path` become a write to a live SSH authentication file on a production host. |
