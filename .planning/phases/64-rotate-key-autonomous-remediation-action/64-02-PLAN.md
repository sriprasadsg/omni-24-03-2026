## Scope boundaries (explicit, not silent)

- **Scan scope (resolves RESEARCH Open Question 1):** enumerate `/root/.ssh/authorized_keys`, one level of `/home/*/.ssh/authorized_keys`, and on macOS one level of `/Users/*/.ssh/authorized_keys`. A non-default `AuthorizedKeysFile` directive in `sshd_config` is NOT parsed in v1 — the codebase has no sshd_config directive parser today and adding one is a separate concern. This limitation is recorded in the module doc comment, not left implicit.
- **Weak-type detection only (resolves RESEARCH Open Question 3).** No known-compromised-fingerprint blocklist ships in v1; the finding schema already carries a fingerprint, so a blocklist feed is purely additive later.
- **Linux/macOS only.** Windows `administrators_authorized_keys` needs ACL manipulation, not file-mode changes, and has no precedent in this codebase (RESEARCH Pitfall 3).

Define `pub const MIN_RSA_BITS: u32 = 2048;`, `pub const MAX_AUTHORIZED_KEYS_FILES: usize = 64;`, `pub const AUTHORIZED_KEYS_READ_CAP: usize = 256 * 1024;`.

Define `pub struct AuthorizedKeyEntry` with public fields `line_index: usize`, `options_prefix: String`, `algorithm: String`, `fingerprint: String`, `comment: String`, `weak_reason: Option<String>`.

Define `pub fn weak_reason_for(key_data: &<the crate's parsed public key data type>) -> Option<String>`: return `Some` with a short human reason for an RSA key whose modulus bit length is below `MIN_RSA_BITS` (include the actual bit count in the reason) and for any DSA key (reason names DSA's fixed inadequate key size — no bit-length test, per D-02 and RESEARCH A2); return `None` for every other algorithm including Ed25519, ECDSA, and RSA at or above the threshold. Derive RSA bit length from the modulus multiple-precision integer's positive-magnitude bytes: bit length is eight times the byte count minus the leading zero bits of the most significant byte.

Define `pub fn parse_authorized_keys(text: &str) -> Vec<AuthorizedKeyEntry>`: iterate lines with their index; skip lines that are empty after trimming or begin with a hash; split each line into an options prefix and a key portion by locating the first whitespace-delimited token that starts with a recognized key-type prefix (a token beginning with `ssh-`, `ecdsa-`, or `sk-`) — everything before that token is `options_prefix` (kept verbatim, including its trailing separator), and the remainder is the key portion. Parse the key portion with the crate's OpenSSH public-key text parser; on any parse error skip the line entirely and continue (never push an entry, never panic, never log the line body). Populate `algorithm` from the key's algorithm name, `fingerprint` from the crate's SHA256 fingerprint type rendered in its standard textual form, `comment` from the parsed key's comment, and `weak_reason` from `weak_reason_for`.

Define `pub fn is_authorized_keys_path(path: &str) -> bool`: true only when the path is absolute, contains no parent-directory traversal segment, and its final path component is exactly `authorized_keys` or `administrators_authorized_keys`. This is the guard plan 64-03's rotation uses before writing anything, so it lives here next to the parser.

Define `pub fn authorized_keys_paths() -> Vec<String>`: under a Linux-or-macOS configuration gate, collect `/root/.ssh/authorized_keys` plus, for each direct child directory of `/home` (and of `/Users` on macOS), that directory's `.ssh/authorized_keys`; keep only paths that exist and are regular files; stop after `MAX_AUTHORIZED_KEYS_FILES` entries; return them sorted for deterministic ordering. Under any other configuration return an empty vector. A directory-read error must degrade to an empty result, never a panic.

Add an inline `#[cfg(test)] mod tests` implementing all eight behaviors, following the existing inline-test convention in this crate. Generate the RSA-1024, RSA-2048, DSA and Ed25519 fixture lines as literal string constants inside the test module — do not shell out to `ssh-keygen` and do not read any real host file. Never commit a private key into a fixture (project rule: never commit credentials).

| Boundary | Description |
|----------|-------------|
| host filesystem -> agent process | Arbitrary, possibly hostile or corrupt `authorized_keys` content is parsed by the agent. |
| agent -> backend (heartbeat) | Scanner findings leave the host and are persisted; anything placed in a finding is durable and visible in the operator console. |
| crates.io -> agent binary | A new third-party dependency enters a privileged security agent. |
